用户 10-14: 7 天额度一天不到用 42%, "只要完成效果一致可以灵活调整", 要求整理派任务时减少 token 的技巧。10-13/14 实测: 单个 Opus agent 30万–90万 token, 累计上下文大的 agent 被反复唤醒最贵 (D2 90 万)。

**1. 选对执行者 (最省)**
- 主会话几步 shell 能做完的 (跑验收、装卡、合并无冲突、看板加一行) 自己做, 不派 agent。
- 机械活 (看板/表格/日志整理/抽数据/固定流程) → Sonnet; 读日志判 PASS/FAIL、跑一条命令回报 → Haiku。
- 只有要深推理的 (RTL bug、方案取舍、复杂合并) 才用 Opus, effort high 只给 RTL/时序/全链路这类。
- 画电路板 → Codex (其余仍 Claude)。

**2. 任务说明写窄**
- 一个 agent 一件事, 写清"做什么/不做什么/判据/交付", 先小样本 (例: 先 1–2 min smoke 再 1 h)。
- 背景只给路径和结论 (哪个文件哪一节), 不让它自己大范围摸索仓库; 已知坑直接写进说明 (新克隆无执行位、D 盘 EIO、禁按名字杀进程、只按 PID)。
- 验收标准写成 verify.sh 一条命令, 判据写死, 避免来回问。

**3. 控制上下文**
- 交付复验过就 TaskStop; 返工尽量在同一轮说明里一次讲全, 不要多轮小改。
- 后续工作开**新 agent**并把要点写进说明, 不唤醒已累积 30 万+ 上下文的老 agent (返工例外: 小修在原 agent 上一次做完)。
- 并行 ≤5。

**4. 复验省法**
- 只跑关键项; agent 已在新克隆全量过、改动小的 (只改测试/文档) 不重复全量。
- 上板与离线可并行; 长任务用一个后台 Bash `while kill -0 PID; do sleep 60; done` 等结束只唤醒一次, 不反复轮询/重挂 Monitor。
- 读结果只 grep 判据行和末行, 不 cat 整个日志。

**5. 汇报安静模式**
- 中间过程不逐条转述; 只在要用户决定、真错误、结束时说话; 汇报先结论, 一屏以内。
- 子 agent 汇报也要求"结论 + 必要细节", 长细节写进仓库文件 (README/PROGRESS) 让需要时去读。
- 重复的进度/记忆/看板更新合并成一次提交。

**How to apply:** 每次派活前过一遍: 能不能自己做? 能不能 Sonnet/Haiku? 说明够不够窄? 有没有小样本? 判据是否一条命令? 相关 [[feedback-save-weekly-quota]] [[feedback-agent-label-task-id]] [[feedback-no-kill-by-name]]

- 10-15 用户: "你自主完成就行, 把结论同步就行, 记得提交代码, 有验证的记得打分支, 减少我的介入" —— 已批准的方向直接做到底 (派 agent→复验→合主线), 只同步结论; 只有需要人在场 (实转/接线) 或真正的取舍才找用户。
- 10-15 用户: 测试结果 (如实转 1 h) 直接记进项目跟踪文件 (zynq_pov/docs/progress: metrics/daily_log + 重新生成看板) 就行, 不用单独发给用户; 不要因等用户而阻塞, 记完直接做下一个任务。
