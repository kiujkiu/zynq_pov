给硬件同事写任务/下发件时, **只写大交付物和怎么算完成**, 不写实现细节。

09-11 用户对 rev.2 任务表(48 条任务 / 11 闭环, 每条带邮票孔分配、地排谐振计算、封装版本坑等)的原话: **"这里有点太详细了, 不需要, 我们只需要把大的交付物说清楚就行"**。随后同一轮里连续四次把决定权交给硬件:
- 验证板中的桥接 FPGA **自研还是直接买核心板, 由硬件自己评估**
- **动平衡不需要硬件来做**(不属于硬件的活别往表里放)
- 芯片目前**只锁定了 LED 驱动 2260**; 主 SOC 和桥 FPGA 的选型要**和采购确认价格和供货**
- 模组间接口的**通信速率计算放进去, 由硬件评估给最终结论**

**Why:** 硬件是来负责板级决策的; 表里把方案写死(比如预设 ACG525 核心板、写死 DR1V90)等于替他做了决定, 细节写多了反而淹没交付物。

**How to apply:**
- 结构: 交付物(板) → 验收判据 → 关键节点; 技术依据放配套文档/附录, 表里只留一句指引
- 还没定的东西写成"待硬件评估的交付物"(结论 + 依据), 不要预设答案; 我们手里的计算/估算作为**输入和参考值**附上, 明确"最终结论由硬件给"
- 芯片/关键器件选型的验收判据里必须包含**采购确认的价格、货期、供货**
- 只放硬件的活; 软件侧(固件移植/RTL/时序)、结构侧(动平衡)不进硬件表, 最多写一句分工
- **层级结构(用户 09-11 定)**: 最上层是"要做出的硬件版本"(这里是验证板 → 目标板两版; 先做简单的验证板是为了**让新同事熟悉环境 + 团队尽快有的用**) → 每个版本拆 **2~4 个小目标**, 要求**有明确交付物、能直接支撑版本目标、挑最有价值最有效的** → 内容多的版本**再打一层**(目标板按板分 LED 板线 / SOC 板线 / 整机联调) → 交付物
- **每个小目标都标支撑关系**: 「前置」(等谁) + 「支撑谁 · 提供什么」(交付给谁、交付什么), 并配一张支撑关系图(实线前置 / 虚线提供台架或输入); 版本目标由哪几个小目标直接支撑也要写明
