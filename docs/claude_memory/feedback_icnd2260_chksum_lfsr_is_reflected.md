# CHKSUM 推错了三周: 是反射型 0x8408, 不是 CCITT-FALSE (2026-09-01 上午, 已作废)

`icnd2260_lvds_tx.v` / `icnd2260_ack_rx.v` 从 2026-08 起用的都是

```verilog
fb = c[15] ^ b;  c = {c[14:0], 1'b0};  if (fb) c ^= 16'h1021;   // ❌ 错
```

即 CRC-16/CCITT-FALSE(左移, 回授取 MSB)。**这是错的。**

## 手册 P13 那张 LFSR 图实际画的是

渲染成 PNG 逐格看(`pdftoppm -r 300 -png`, 然后用 Read 看图):

- 数据从最左边的 XOR 进 **C15(标 MSB / x^0)**, 逐级**向右**移到 **C0(标 LSB / x^15)**
- 回授线从 **C0 的右侧**绕到底部、一路回到最左那个 XOR
- 抽头 XOR 插在 **C11→C10** 和 **C4→C3** 之间

⇒ 新位进 bit15 / 右移 / 回授取 bit0 / 掩码 `bit15|bit10|bit3` = **`0x8408`**:

```verilog
fb = b ^ c[0];   c = {1'b0, c[15:1]};  if (fb) c ^= 16'h8408;   // ✅ 对
```

**数值自检**(两条独立路径都算过):

| | 喂 "123456789" | 标准名 |
|---|---|---|
| 我们原来那版 | MSB-first ⇒ **0x29B1** | CRC-16/CCITT-FALSE |
| 按图那版 | LSB-first ⇒ **0x6F91** | CRC-16/MCRF4XX |

`VHEAD[31:16]=0x2C38`(9 颗/45 行/16bit): 原来发 **0xE9DF**, 按图应发 **0xFB97**。

## 为什么它值得单独记

`crc_step` 被**三处**消费, 每一处单独出错都足以让屏全黑:
1. 配置包尾 CHKSUM ⇒ 芯片丢弃每一条写寄存器指令(238 个寄存器一个都没进去)
2. 读寄存器指令 CHKSUM ⇒ 芯片从不回包 ⇒ **ACK 恒零**
3. `VHEAD[15:0]` ⇒ 芯片丢弃每一帧图像头 ⇒ 一个像素都不会亮

🔴 **所以"屏黑"和"零 ACK"从来不是两条互相独立的阴性通道 —— 它们共用同一个 CRC。**
2026-08-20 正是据"两条独立通道都阴性"把嫌疑逼到物理层的, 那个推理的前提不成立。

⚠ **但改完 CRC 屏仍然没亮**(2026-09-01 实测, `refl` 在 0/1 之间来回切四次, `ack_cnt`/
`ack_err`/`nbits` 全无差别)。⇒ 这是**必要不充分**: bug 是真的, 但不是唯一的 blocker。

## How to apply

- RTL 里 `crc_refl` 是运行时开关(VIO `g_dbg.o_crc_mode` bit0, INIT=1=按图那版), 可秒切二分。
- 收发两侧必须同源(顶层一根 `dbg_crc_refl` 同时驱动 tx 和 ack_rx)。
- ⚠ TB 的 CRC 已跟着改成同一形式 ⇒ **`icnd2260_lvds_tb.v` 从此不再是 CRC 算法的独立证据**,
  它只证明帧格/字段对齐/覆盖范围。算法的唯一依据是手册那张图。
- **仍未定死的两个自由度**: 喂入 LFSR 的比特序(线上序 vs 字节 LSB 先)、下行 CHKSUM 域的
  发送位序(手册注 1 说"所有域 MSB 先", 但 ACK 方向明写"从 LSB 开始回传")。
  共 4 种组合, `crc_lsb_tx` 是其中一维。

**Why**: 手册对 CHKSUM 只给了一张图、没给伪码或测试向量, 而 `pdftotext` 抽不出图的拓扑。
教训与 [[reference_lxb_gpio1_pinout]] 那次完全同构: **"符号图+连线"类信息必须渲染成 PNG 用眼睛看**。

# 🔴🔴 2026-09-01 傍晚更正: 本文的结论是错的

供应商 564MB 逻辑分析仪抓包解出来的真实线上 CHKSUM, **20 个配置包 20 个**都命中的是:

```c
t = ((r>>15)&1) ^ bit;  r = (r<<1) & 0xFFFF;  if (t) r ^= 0x1021;   // CCITT-FALSE
// 初值 0xFFFF, 按线上序(各域 MSB 先)喂, CHKSUM 域本身也 MSB 先发
```

**也就是 2026-08 原来那一版就是对的**, 本文当天上午的"修正"反而把它改错了。

## 为什么读图会读错 —— 这条教训比结论本身值钱

图**没有读错**: 三个互相独立、事先不知道结论、且被禁止读本仓库的 agent, 逐格读出的拓扑完全一致
(数据进 C15 / 向右移 / 回授取 C0 / 抽头在 C11→C10 与 C4→C3)。

**错在把"图上寄存器的命名"当成了"线上的串行化顺序"。**
同一串触发器, 叫哪一格 bit15 是制图习惯; 只有**串行化那一刻**才决定线上比特。
本文推的 `0x8408` 值配 MSB 先发 = 线上 `0x30C3`; 而真实线上是 `0xC30C`。
(⇒ `反射 0x8408 + LSB 先发` 与 `CCITT-FALSE + MSB 先发` 线上完全等价, 都对; 我选了第三种组合。)

**How to apply**:
1. 从 LFSR 图反推 CRC 时, **图只能定出多项式和初值, 定不出线上位序**。位序必须由别的证据定
   (手册注 1「所有域都是 MSB」, 或一段实测波形)。
2. **多个 agent 读同一张图达成一致, 不等于结论正确** —— 它只排除"看花眼", 对"图≠硅"和
   "串行化顺序"这两项零贡献, 而后两项才是风险大头。
3. 真正结案的是 [[reference_icnd2260_vendor_capture_decode]] 里那段波形。**一段抓包胜过十次读图。**

## 2026-09-09 结案: 形式一直是对的, **错在反射做了两遍**

E104 板上抓到真帧之后离线穷举, 命中的是
`poly=0x1021 init=0xFFFF refin=0 **refout=1** xorout=0`, 覆盖 = 前 40 位。
代回老代码, 三个历史读数**全部复现**:

```
C = MSB 先入 0x1021 / init FFFF / 前 40 位          = 0x5933
rev16(C)  (= refout=1 的结果)                       = 0xCC9A = 线上帧尾字段 ✅
反射 LFSR 0x8408 同样 40 位                          = 0xCC9A  ← **与 rev16(C) 完全相同**
REV_CRC=1 时接收侧的 f_crc_rx (= 反转后的帧尾)       = 0x5933  ← 上板读到 0x5933 ✅
反射 0x8408 + 只覆盖 55 位帧的前 39 位 (少收 1 位时)  = 0x9D02  ← 上板读到 0x9D02 ✅
```

⇒ 本文"是反射 LFSR"这句**没错**, 它和 "0x1021 + refout" 是同一件事的两种写法。
**真正的 bug 是同时打开了两个反射**:
- 模块**参数** `REV_CRC=1` ⇒ 接收侧把帧尾字段反过来 (0xCC9A → 0x5933)
- 运行时**输入** `crc_refl=1` (接在跳线上, 上拉 ⇒ 默认 1) ⇒ 计算侧用反射 LFSR (0xCC9A)

于是拿 `0x5933` 去比 `0xCC9A`, 永远不等。**任何一个单独打开都是对的。**

### 教训 (比"选错了组合"更普遍)

1. 🔴 **反射类开关不要有第二个**。位序反转是个对合 (自反) 操作, 做两次等于没做、做一次才对
   —— 一旦它散落在**两个不同的开关**里(一个编译期参数、一个运行时引脚), 代码里根本看不出
   "现在总共反了几次"。**把反射集中到唯一一处**, 接收侧永远保持"按线上顺序"的原始值。
2. 🔴 **默认值是上拉 = 1 的运行时开关, 等于一个没人复核的隐藏参数**。这个 `crc_refl` 接的是
   一个悬空跳线, 谁都没意识到它在默认状态下选了"反射"。
3. 单帧命中 (1120 组合里唯一命中, 偶然期望 0.017) 统计很强但**不是证明**。证明要换一个
   **payload 不同**的帧: 改读另一个寄存器地址 ⇒ DATA0 变 ⇒ CHKSUM 必然变 ⇒ 仍通过才算数。
