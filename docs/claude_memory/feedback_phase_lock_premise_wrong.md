2026-08-05, 分支 `feature/phase-lock` commit `7c65e5c`(已随 [[feedback_recv_setsockopt_rcvbuf_lock]] 合入主干)。
被推翻的是 [[project_pov3d_link_budget_status]] 里"翻页 1.0×、相位没锁"那一条。

## 原假设 vs 实测

假设: 一帧的活 46 ms 装得进 66.7 ms 一圈, 但起解相位随机 ⇒ 一半时候赔一整圈 ⇒ 7.5 fps。

实测推翻:
- 真实工况 5×20 s: rx **8.0**/s, flip **8.0**/s, **drop = 0 / 668 帧** ——
  收到的每一帧都上了屏, **相位可回收的量是 0**。
  "wait 33-39 ms" 不是错过的机会, 是 **flip 线程没帧可翻在空转**。
- "每圈翻中 0.53" 完全由 rx(8.0)/eng(15) 解释, 与相位无关: **供给只有需求的一半**。
- **随机相位不是稳定态**: 错过一次 → 翻页推后一圈 → 下一帧已在 ready 里等着 → 自己纠回来。
  8 rps 交错 A/B: off 98% 翻中 8.00/s, on 91% 翻中 **7.99**/s。

⇒ 真瓶颈在收包, 见 [[feedback_recv_setsockopt_rcvbuf_lock]]。机制保留但**默认 off**。

## 🔴 若将来真要开, 三条保险少一条就更差

1. **引擎没转就放行** —— 否则 RX 线程死等, 现象和"网络断了"一模一样(又一次误诊)。
2. **`body + dec >= 一圈` 就放行**。判据里**不能含 `t_hdr`**(等发送端的空闲) ——
   含了的话发送端 `--fps 10` 时 hdr 自动补到 (100ms − dec), 条件恒成立,
   **锁永远不生效且怎么调都看不出差别**。也**不能含 cpy**: cpy 在 flip 线程上,
   与下一帧收包并行, 收敛条件解出来只有 `body + dec <= rev`。
3. **回退相位量 `dec+cpy >= 一圈` 时取模会绕回错误相位** ——
   实测 delta@12 rps (dec 59 + cpy 34 > 一圈 83) 就是这么把 12.0 flip/s 锁成 11.0 的。

## 🔴 测量方法本身才是本轮真正的产出

`tools/phase_bench.py`: 同配置跑 N 次报**中位数/p5/p95/σ**, 不再对单次 DIAG 求算术平均。
这条 WiFi 上单次 20 s 窗口能在 8.0 与 12.0 帧/s 之间跳 —— **同一个配置**。
本轮就被骗过一次: 抬 `rmem_max` 后头一次量到 8.0→12.0, 交错 A/B(低/高/低/高/低/高)
复测两组**中位数都是 8.00**。

踩到的坑(都写进脚本注释了):
- **`journalctl` 是按 unit 累积的**, `-u povbench -n 2000` 会把上几次 run 的 DIAG
  一起拉回来(FLIP/FRAME 很密, 2000 行正好横跨两三次 run) ⇒ 对照组与实验组互相污染。
  改成按**本次启动的 `InvocationID`** 过滤。
- 空闲动画与推流共用同一进程同一日志, 靠 `dec 0.0/0.0ms` 滤掉空闲行
  (同 [[feedback_lz4_onboard_reality_check]] 的判据)。
- **板子跑 UTC / 开发机跑 CST, 不是时钟不同步, 是时区不同**, 同一时刻。
