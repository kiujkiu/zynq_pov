2026-08-25, PL lz4 解码上板后的 A/B 实测 (969 RPM = 16.15 rev/s, 圈周期 62ms)。

|          | rx      | flip     | drop | 实际上屏 |
|----------|---------|----------|------|---------|
| 流水线    | 15-17/s | 4-8/s    | 1600 | 4-8 fps |
| **串行**  | 10-12/s | 10-12/s  | **9** | **10-12 fps** |

串行下 **flip == rx, 一帧不丢**。

## 机制

流水线把 `pl_pending_settle` 推迟到「收到下一帧」才执行 ⇒ **帧就绪的时刻被 WiFi
`recv` 的抖动拖着走** (55-80ms 且方差大), 与 62ms 的翻页窗形成两个独立时钟的
拍频 ⇒ 持续相位漂移, 有时赶上有时整整错过一圈。

串行下解码完立刻去等窗口, 节奏天然跟着转速走 ⇒ 每圈稳定命中。

🔴 **收得快 ≠ 上屏多**。POV 的翻页机会是**转速决定的离散时刻**, 不是连续的 ——
在这种系统里, **抖动比吞吐更致命**。多收的那 5-7 帧全进了 drop。

## 成立条件 (很重要, 别无条件套用)

当初做流水线是对的: 那时解码 74ms **慢于**链路, 要把 55-80ms 的 recv 藏起来。
`fold_a` 把解码压到 55.5ms (< 62ms 圈周期) 之后, 藏 recv 的收益才小于失去
窗口同步的代价。

⇒ **解码若再变慢 (更高色深/更多槽/取消 fold), 要重新做这个 A/B。**

**How to apply**: 凡是「生产者节奏 vs 固定相位的消费窗口」的系统, 加流水线前
先问: 它会不会把生产完成的时刻**从确定的变成受上游抖动支配的**? 如果会,
吞吐涨了也可能净亏。判据要看**上屏率 (flip)**, 不能看收包率 (rx) ——
这两个数在故障时会朝相反方向动。

相关: [[feedback_phase_lock_premise_wrong]] 当年否决翻页相位锁定的理由是
`drop=0/668` (无可回收量); 现在 drop=1600、wait 24-38ms/帧, **前提已反转**。
