2026-07-28 核实: `stream/pc/povstream.py` 的发送循环是**严格 stop-and-wait**:
```python
sock.sendall(hdr + payload)   # 传输
ack = sock.recv(1)            # 阻塞等板端解码完成, 之后才发下一帧
```
⇒ **网络传输与板端解码完全串行, 无重叠**。每帧周期 = 传输 + 解码 + RTT。

实测量级 (144 帧机器人动画, 压缩后 ~140 KB/帧, 链路 28 Mbps):
- 传输 ~40 ms, 板端解码 ~64 ms (`dec=` 字段), 合计 ~104 ms → **~9.6 fps**
- 若重叠: 周期 = max(40, 64) = 64 ms → **15.6 fps (+62%)**

⚠ 分析日志时注意**区分是谁在推**: 若多台机器同时连, 帧间周期会被对方的 `--fps` 节奏污染,
不能全算到 ACK 头上。结构性结论靠**读代码**确认, 不靠时序统计。

## 设计文档已规划过 (04_sw_stream_26fps.md §3.3/§3.4/§4.4)

三项改造, **只做了一项**:

| 规划 | 现状 |
|---|---|
| WC 映射 `povmem.ko` (§3.4) | ✅ 已做, 日志 `frame map: WC via /dev/povmem` |
| 三缓冲 (bank C @ 0x10A00000) | ❌ 仍双 bank (A=0x10000000 B=0x10500000) |
| 双线程 + ACK 与翻页解耦 (§3.3) | ❌ 仍单线程 stop-and-wait |

§4.4 写了 "若页率贴不住 26 再加 window=2, 协议无需改, 板端 recv 缓冲天然吸收" —— **触发条件已到**。

## 三步方案 (每步独立可回滚)

**① 发送窗口 window=2** — 只改发送端十几行, 板端/协议零改动。
最多 2 帧在途, 窗口满才收 ACK ⇒ 传输与解码重叠, 周期 → max(传输,解码)。
风险: 板端 `SO_RCVBUF` 要能吸收 ~1.5 帧压缩数据 (~200 KB), 需确认。

**② 板端三缓冲 + 双线程** (§3.3 原方案) — RX/解码线程收完立即 ACK (不等翻页),
翻页线程独立轮询 slice 计数; `latest_ready` 原子交换, 被顶替 = 天然丢帧, 显示永不阻塞。
把 ACK 节拍从"翻页"解耦到"解码"。

**③ 双核并行解码** — A9 双核, 解码 64ms 是单核 zlib; 奇偶帧分两线程 → ~32ms (~31 fps)。
需第 4 个 bank (文档已预留 0x10F00000)。

## 收益上限

| 阶段 | 周期 | 帧率 |
|---|---|---|
| 现在 | 传输+解码+开销 | ~9.6 fps |
| +① | max(40,64)=64ms | **15.6 fps** |
| +② | 64ms 但节拍稳 | 15.6 稳定 |
| +③ | ~32ms | **~31 fps** |

🔴 **体积帧率上限 = 2 × 转速 = 32.5 fps** (16.24 rps), 所以做到 ③ 就撞机械上限, 再优化无意义。
建议先做 ①: 改动最小、收益占大头、能立刻验证"传输/解码重叠"这个假设。
