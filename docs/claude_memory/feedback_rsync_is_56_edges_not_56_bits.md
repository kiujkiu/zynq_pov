# 🎯 首光根因: RSYNC 发长了 4 倍 (2026-09-01)

**症状**: 屏全黑 + ACK 零回包, 整整两周, 两条"互相独立"的通道全阴性。
**根因**: `icnd2260_lvds_tx.v` 的 `S_RSYNC` 把 RSYNC 按 **4 沿/位** 发。

```
手册 §3.2: 「在 RSYNC 与 Configuration 阶段, 每 4 个时钟沿传输一位,
            比如 RSYNC, 数据如下: RSYNC = 0xFFFF0F0F0F0F0F」
```

**这句话里的"位"是逻辑位, 而 `0xFFFF0F0F0F0F0F` 已经是展开后的线上电平序列。**
RSYNC 的逻辑值只有 **14 位**(`0x3D55` = `1111_0101_0101_01`), 14 × 4 沿 = **56 个时钟沿**,
正好就是那 56 个十六进制位。

| | 线上沿数 | 开头连续 1 的个数 |
|---|---|---|
| 供应商实测(逻辑分析仪抓包) | **56** | **16** |
| 我们原来发的(56 位 × 4 沿) | **224** | **64** |

⇒ 芯片的帧对齐器**永远匹配不上** ⇒ 配置指令一条都不认 ⇒ 屏黑 **且** 读指令也不回包。
**一个 bug 同时解释两条症状, 且与物理层完全无关。**

## 修复

`S_RSYNC` 从 `os_phase` 那套 4 沿/位改成和 `S_VHEAD` 一样的 1 沿/位:
```verilog
bit_r[0] <= sr[55];  bit_f[0] <= sr[54];  sr <= {sr[53:0], 2'b00};
if (nbits <= 7'd2) begin ... end else nbits <= nbits - 7'd2;
```
⚠ **只有 RSYNC 是这样。Configuration 段确实是 4 沿/位**(抓包解码逐包 CRC 通过, 证明无误)。

## 🔴 为什么两周没抓到 —— TB 编码了同一个误解

`icnd2260_lvds_tb.v` 的"独立解码器"里 `D_RSYNC` 也按 4 沿/位解, 所以 DUT 和 TB 一起错,
**仿真一直给 PASS**。改完 DUT 后 TB 立刻报 `rsync_pattern_wrong` —— 这才是它第一次真正起作用。

这是本项目**第二次**踩同一个坑(第一次是 2026-08-20「读指令 DEVICE 写死 0xF, 两个 TB 都没抓到,
它们复制了我自己的误解」)。

**How to apply**: 自校验 TB 的"独立实现"只有在**依据独立**时才独立。凡是 DUT 和 TB 由同一个人
照同一句话写出来的, 它验的是自洽性, 不是正确性。**协议类推断必须有第三方证据**
(厂家波形 / 参考代码 / 测试向量), 否则 TB 通过不构成证据。

## 是怎么找到的 —— 两路独立线索在同一天交汇

1. **供应商的 564MB 逻辑分析仪抓包**(用户 2026-09-01 拿到): 解出 RSYNC 只占 56 个时钟沿
2. **手册全扫 workflow** 的规范性对账独立指出 "RSYNC 那半错了"

两路结论一致 ⇒ 当场改, 当场首光。见 [[reference_icnd2260_vendor_capture_decode]]。
