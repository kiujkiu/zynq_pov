2026-08-24 做 `half_scan` 半屏扫描，**同一类错误连栽三次**，每次都是仿真全绿、上板不对。

## 三次

1. **"远端 6 颗保持旧值"** —— 实际是**被推移**。移位链发 96bit，链上原有数据整体推走
   96 位，远端拿到的是上一次的近端数据，不是"不动"。屏上出现两份拷贝。
2. **漏给引擎 B 接 `half_scan`** —— `pov_dual_top` 有两个 `panel_engine` 实例，
   字符串替换只匹配了第一处。两屏扫描速度差一倍（16038 vs 31590）。
3. **行边界漏补跳地址** —— 半屏每 plane 只走 3 个 pair，plane 边界补了跳、
   **行边界忘了**，地址逐行累积错位。屏上表现为"**发什么内容都显示一样**"。

## 🔴 共同点：判据全在验时序，没有一个在验数据

第 3 次最典型，三个判据**同时给出假阳性**：

| 判据 | 有 bug 时 |
|---|---|
| 仿真 `frame_period = 16038` | ✅ 通过（只验拍数） |
| 仿真 `max fb_raddr < 1024` | ✅ 通过（错的 1008 也在范围内） |
| 上板 `duty = 0.333` | ✅ 通过（只验 OE 权重比例） |

**"时序对"和"读的地址对"是两件事**，前者全绿不代表后者成立。

## 怎么改的

新增 `T6r2`：不验范围，**直接验地址序列本身** —— 半屏一整屏必须恰好命中
`rows*3 = 162` 个 plane 基址 `{row*18 + plane*6}`。并按老规矩**把 bug 塞回去验测试有牙**：
塞回去 `T6r2` 当场 FAIL，修复版全过；`max fb_raddr` 也从错的 1008 变成正确的 969。

## 教训

- 改**协议层/寻址**的东西，光跑核的 TB 不够。仓库里其实有 `icnd2047_bfm.v`
  （12 级联 ×9 lane 的芯片行为模型），挂上去第 1 次那个错当场能抓出来
- **能证伪的判据才有价值**。定位第 3 个 bug 的是用户那句"内容换半边显示一样" ——
  在此之前我一直在用"看起来对不对"打转，那是证不了伪的。
  后来做的对照实验（内容放下半屏 vs 放上半屏，其余全同）才是决定性的
- 量具本身也会骗人：`oeprobe` 采样太慢漏沿，把 50MHz 的 aclk 量成 26MHz，
  我还拿它去"推翻"了 BD/约束/ps7_init 五条硬件证据，写进了文档和 commit。
  **edges 这类计数只会被低估不会被高估**，这个单向性本可以早点排除错误结论
