# 显示帧率这个量, 有两层陷阱 (2026-09-02, ICND2260 单颗测帧率)

## 陷阱一: 静态图案根本量不到显示帧率

我们把发送帧率从 40 一路拧到 **4032 fps**(62.5MHz 下的物理极限), 画面全程干净,
差点得出"芯片能显示 4032 fps"。**错的。**

芯片跟不上时只会**丢掉来不及显示的帧、继续显示最近一张完整的**。
而我们每帧内容一模一样 ⇒ **丢 90% 和一帧不丢, 屏幕上完全相同。**
⇒ 那条 4032 的曲线证明的是**链路/协议在 4032 fps 下没崩**(这也是真收获),
  但**显示帧率一个数都没测到**。

## 陷阱二: 🔴 "帧相位条纹 + 肉眼数亮条数"同样不成立

我设计的判据: 40 列切 8 条竖带, 第 k 帧只点亮第 (k mod 8) 条,
"亮着的条数 / 8 = 显示帧率 / 发送帧率"。

**在异步采样下不成立。** 芯片按自己的节奏取当前帧, 被采到的相位在 8 个值里游走,
**长时间下 8 条被采到的次数均等** ⇒ 不管芯片是 100 fps 还是 4000 fps,
**人眼看到的时间平均完全相同, 8 条都均匀亮着。**
(只有"整齐地每 N 帧一次且 gcd(N,8)>1"才会少亮几条 —— 那是特例, 不是常态。)

🔴 **可推广: 任何依赖时间平均的判据, 都对"采样率"这个量是瞎的。**
换图案、换颜色、换相位数都救不了 —— 这是原理性的, 因为长时间平均本来就相等。

## 唯一可行的读法: 同一个图案 + **短曝光**

```
手机专业模式快门 1/1000 s 拍一张:
   曝光窗口内芯片显示了 n 帧  =>  照片里 n 条带亮着
   显示帧率 ≈ n / 曝光时间
   100 fps -> 1 条    4000 fps -> 4 条    8000 fps -> 8 条(到顶, 换更短快门或更多条带)
```
**图案不用改, 改的是读取方式 —— 从眼睛换成快门。**
本质: 把时间维度折叠进空间维度之后, 还需要一个**时间上会分辨的读出器**才能解回来。

实现: `rtl/icnd2260_lxb_lvds_top.v` 的 `dbg_pat_mode == 3'd7`(mot_stripe/mot_ph 那段)。
