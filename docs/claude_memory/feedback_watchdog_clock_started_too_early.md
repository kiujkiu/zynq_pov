name: 看门狗把时钟起点设在 launch, 流水线下会误杀健康硬件
description: 超时预算被 recv 的 55-80ms 吃光 ⇒ 第一次 poll 就判死引擎; 而引擎无软复位 = 不可逆
type: feedback
---
2026-08-24 给 PL lz4 引擎加卡死看门狗时，防御措施自己变成了事故源。

引擎的失效模式是**静默卡死**（源字节耗尽但 `raw_len` 没到 ⇒ `busy` 恒 1、不置
`error`、不置 `done`），而 RTL **没有软复位**，只能整个 PL 复位。所以超时后
必须把引擎摘出派发池 —— 这个决定是不可逆的。

🔴 **Bug**: 超时时钟起点设在 `pl_sched_launch()`。但流水线下 RX 编程完 PL
就立刻去 `recv` 下一帧（WiFi 55–80 ms，重传时更久），等它回来第一次 poll 时，
「自 launch 起的墙钟」早就吃掉了大半预算 ⇒ **第一次 poll 就把健康引擎判死并永久摘除**。
一次网络抖动 = 不可逆地损失一个引擎。

**修法**: 时钟起点挪到 `pl_sched_wait()`，让预算约束的是
「**我们真正阻塞了多久**」而不是「墙钟过了多久」。真实硬件耗时另算，走 `PLDIAG` 的 `pl` 字段。

**Why**: 只在「流水线 + 链路慢」两个条件同时成立时触发，
串行跑 / 有线网 / 本地 SIM 都测不出来 —— 而这三种正好是开发时的默认环境。

**How to apply**: 凡是「超时 ⇒ 不可逆惩罚」的看门狗，先问一句
**这个时钟在计什么** —— 计「墙钟」几乎总是错的，
应该计「被观测对象真正占用我们的时间」。惩罚越不可逆，这个区分越要紧。
