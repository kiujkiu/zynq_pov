## 转接板网表（信号名直接用 FPGA 的 site 名标注，不用查排针脚号）

R_P/N=L3P/N(V22/W22)、G_P/N=L9P/N(Y20/Y21)、B_P/N=L7P/N(AA22/AB22)、
CLK_P/N=L8P/N(AA21/AB21)、DCLK=L23N(AA13)、SYNC=L12N(AA18)、ACK=L24N(AB15)、
EN_3V8=L19P(V14)、EN_2V8=L19N(V15)。两路 BL8032 出 3.9V/3.0V。

**两个要记住的设计意图**：
1. **两路电源的 EN 都归 FPGA 管且带 100k 下拉** ⇒ 复位态电源是关的，固件必须主动开；
   顺带这是**唯一的芯片复位手段**（RSTN 没引到连接器）。
2. **板子同时铺了 TTL 和 mini-LVDS 两条路**：差分对的 P 侧正好是芯片的 `SDI_R1/G1/B1`
   （球 D1/E1/F1），N 侧是 `SDI_R2/G2/B2`，另有独立单端 DCLK。
   ⇒ 一块板两种模式都能试。

## 🔴 2026-08-19 改口径：走 **mini-LVDS**，不是 TTL

用户确认「需要用 lvds 接口」。代码在分支 **`feature/icnd2260-lvds`**（从
`feature/icnd2260-dualface` 切出），TTL 那套保留作调试退路。

**能走 LVDS 的关键发现：鹿小班 BANK 33 的 VCCO 是可调的。**
逐脚核原理图 P1 的电源引脚矩阵：VCCO_35/34/13/0 都固定 `VCC3V3`，
**只有 VCCO_33 挂在 `VCCIO_ADJ`** 上（GPIO1 那 34 根 IO 正好全在 BANK 33）。
`VCCIO_ADJ` 由 U6（TPS563210 类，Vref 0.768V）产生，反馈 R13(上)/R14(下)：
```
现状 R13=33K  / R14=10K → 0.768×(1+3.3) = 3.302V  (网名 PG_3V3 ✓ 自洽)
改成 R13=22.6K(1%)      → 0.768×(1+2.26)= 2.503V  ⇒ LVDS_25 可用
```
⇒ **只换一颗电阻**。已用 Vivado 实跑 OBUFDS+LVDS_25 落在这四对 ball 上，
place/route 零错误，坐实可行。同 bank 单端信号跟着变 LVCMOS25。

⚠ 连带要确认（LED 板图纸不在手上）：2260 的 `VDDD` 是 2.8V 还是 3.8V ——
3.8V 的话 2.5V 驱不动 I_SYNC（VIH 2.66V），且 ACK_O 3.8V 灌进 2.5V bank 会吃钳位电流。

### LVDS 与 TTL 的四个实质差别（每条都能单独把屏搞黑）
1. **VCCO 必须 2.5V**（上面）
2. **转发时钟要 90° 移相**：mLVDS 的 tSTU/tHLD = 1/4 tLVCP ⇒ 芯片在**位中间**采样；
   TTL 是边沿对齐，**要求正好相反**
3. **第一通道是 B 不是 R**：§3 传输模式表「寄存器配置」列 —— TTL 走 SDI_R1，
   mLVDS 一律走 D0IP/N，而 D0 = SDI_B1（球 F1/F2）。第一通道独家发 VHEAD ⇒ 必须是 lane0。
   ⇒ 帧缓存字序 TTL 是 {B,G,R}、LVDS 是 {R,G,B}。**搞反不报错，只是红蓝对调。**
4. **寄存器表要改**：0x06[9]=1、0x1a[9]=1（§11 那份默认值是 TTL-3 通道）

### ACK 回传解调已实现 —— 首光判据从「屏亮不亮」升级成「LED2 亮不亮」
`icnd2260_ack_rx.v`（手册 P12 脉宽编码：空闲高 / start 低 >1µs / 每位先高 w1 后低 w2，
`w1>w2` 判 1）。序列器每 16 帧插一条读寄存器指令产生回包，顶层把 `crc_ok` 锁到 **LED2**。
⇒ **LED2 亮 = 链路通 + 芯片收到指令 + CRC 推断正确，三件事同时成立**。
比"屏亮不亮"硬得多（屏不亮还可能是电流/灰度/LED 板的事）。
🔴 回包里**数据高位先送，唯独 CHKSUM 从 LSB 开始回传**（手册原话），`REV_CRC` 参数可切。

### 分支矩阵（板子到了按这个二分，见 `docs/03_branches.md`）
主线 `feature/icnd2260-lvds`，四个变体每个只改一处：
`-ttl`（RTL 相同，只出 TTL 版 bit —— **3.3V，不用先换 R13 就能上板**）/
`-phase270`（CLK_PHASE 90→270，查采样相位）/ `-nocrc`（VID_CRC=0，查 CRC 推断）/
`-slow`（CLK_DIV 24→48 + XDC BITCLK_NS 必须同时改，分开速率与协议问题）。

### 三条「仿真过≠芯片认」的推断（上板要验）
- ~~CHKSUM = CRC-16/CCITT（poly 0x1021 / init FFFF / 高位先入 / 不反射不取反）~~
  🔴 **2026-09-01 证伪**：把 P13 那张 LFSR 图渲染成 PNG 逐格看，它是**反射型**
  （数据进 C15、向右移、回授取 C0、掩码 `bit15|bit10|bit3` = **0x8408**）。
  详见 [[feedback_icnd2260_chksum_lfsr_is_reflected]]。**这条错了三周。**
- 图像数据每颗芯片末尾各一个 CHKSUM，多通道每 lane 各算各的
- 「第一组差分对」= D0
⇒ 上板第一件事: 看 LED2。亮了这三条就一起坐实; 不亮就按分支矩阵二分。

## 原先定 TTL 3 通道的理由（已被上面取代，保留作退路依据）

- BANK 33 的 VCCO 是 3.3V，7 系列 HR bank **出不了 LVDS_25**，板上也没有 LVDS 驱动器
  ⇒ mini-LVDS 在这块板上走不通（量产形态才需要，见 [[reference_icnd2260_spec]] 关 2）。
- 手册 §11 的寄存器默认表**本身就是 TTL-3 通道**（`0xb4[5:4]=10`、`0x06[9]=0`、`0x1a[9]=0`）。
- 带宽 3×25MHz×双沿 = 150 Mbps ⇒ 单颗 1,628 fps，台面够用。

🔴 **100Ω 跨接电阻（R7~R10）的处理**：TTL 3 通道下 N 侧被芯片忽略，但电阻把 P/N 连着。
RTL 把 **N 侧驱动成与 P 侧同电平**（等电位、零电流）。**驱动成反相就是 33 mA/根。**

## 四个待确认项（会改设计）

1. ~~I_SYNC / ACK_O 的电平兼容~~ —— **2026-08-19 用户确认 LED 板上有 245 电平转换，
   这条不成立了**。仍要确认 **`LVDS_EN` 的接法**：走 LVDS 要拉**高**，走 TTL 要拉**低**（这根是两种模式的
   物理开关，接反了数据全丢），以及 **LED 板上有没有自己的 100Ω 端接**（转接板已经有一组，
   两组并联 Vod 减半）。
2. **TTL 的 tSU/tHLD 手册没给**（只有 mini-LVDS 的 1/4 tLVCP）。TTL 那套按「边沿对齐」实现，
   打不亮先翻 `DCLK_Q90`；LVDS 那套按 1/4 周期做了 90° 移相。
3. **默认寄存器表算出来只有 ~763 fps**（G = 64×32×8 = 16384，600M/(16384×48)）。
   台面够，跑 POV 必须重算 `0x00`/`0x01`。这正是发给厂家那份需求书问的事。
4. **ACK 回读没做**（脉宽编码解调）。「芯片到底活没活」最硬的判据，值得早做。

(记忆 `reference_anlogic_dr1_fs03_eval`: 「米联客 FS03-DR1 板 = 现有 FS03-Zynq 板的同构版」)

## 🔴 2026-08-20 屏侧排查: 挖出两个我自己的缺陷, 且都会把排查带偏

**① 读寄存器的 DEVICE 写死成 0xF。** 手册: `4'b1010` 是「读**指定**设备, 不支持广播」,
设备号 **第 1 颗 = 0**。序列器里 `cmd_device` 跟写广播共用 0xF ⇒ 一直在点名第 16 颗,
板上没那么多颗就永远没人回。**两个 TB 也没抓到 —— 它们只查了写指令的 DEVICE,
复制了我自己的误解。** 修完把旧 bug 塞回去验过有牙。

**② ACK 输入引脚没上拉。** 手册规定 ACK **空闲为高**, 而芯片没接时这根悬空。
悬空 CMOS 输入放大耦合噪声 ⇒ 解调器狂出垃圾帧。实测 **18,245 帧/秒**,
而我们每秒只问 83 次。
🔴 **这组数长得很像"找到 7 颗级联芯片"(dev 4/5/6/7/13/14/15 都有应答, data0 有值),
差点据此去协议层排查一整天。戳穿它的是速率 —— 回包不可能比提问还多。**
⇒ 教训: **任何"应答数 > 提问数"的观测, 先怀疑量具不是被测物。**
修: XDC 加 `PULLUP TRUE`; 解调器加 `frame_ok`(`ACK[3:0]==0b0010` 才算一帧);
错误计数从「按电平每拍加一次」改成沿触发(原值无意义)。

**加上拉后重扫 16 个设备号的结论**:
- 有效回包 **全 0** ⇒ 没有任何 2260 在应答
- 残留错误率 **≈669/s 且与设备号无关** —— 对得上 I_SYNC 的 662Hz,
  而 **ACK(J1.22) 与 SYNC(J1.23) 在连接器上相邻**
⇒ **ACK 悬空、被邻线耦合拽动 ⇒ 屏侧没有任何东西在驱动它。**
⇒ 这反过来**基本排除了「协议不认」**: 芯片只要活着且 ACK 通到 FPGA, 推挽输出会把线
  钉在空闲高电平, 邻线那点耦合拽不动。嫌疑收窄到 **ACK 物理通路没建立**
  (线没通 / 245 方向或供电 / VDDD 没上来 / RSTN 被摁住)。
⚠ **Altium 转接板 J1 上根本没有 RSTN** ⇒ 屏那边若无板上上拉, 芯片会一直在复位里。
  这条现在是头号嫌疑。
⚠ 布线教训: ACK 是弱上拉的慢速回传线, 旁边不该走 I_SYNC 这种周期性跳变信号。

**LED 板是供应商的客户样板, 拿不到原理图。** ⇒ 只要接口信息即可(不涉及他们的设计):
连接器脚位 / VDDD 电平 / LVDS_EN 是否硬件拉高 / 板上有无 100Ω 端接 /
**他们自己点亮用的寄存器配置** / 级联颗数 / 扫描行数与像素数 / RSTN 有无上拉。

## 🎯 2026-08-20 下午: 连接器其实是兼容的(我读错了脚号) + 灯板真实参数

🔴 **我上午那套「连接器不兼容、会短路」的分析是错的** —— 把灯板脚位图读成了
「左列奇数/右列偶数」, 实际是**列优先**(左列=1~20, 右列=21~40)。按列优先重对:
**19 个信号与地全部一致, NC 也全对上**, 转接板与灯板本来就是配套的。
⇒ 教训: 连接器脚位图先确认编号方式(行优先 vs 列优先), 这一步错了后面全错。

**灯板实际参数(用户确认)**: **9 颗级联, 每颗 40 像素 x 45 扫描行, 板上无端接**,
连接器上**没有 RSTN**(板内自处理), 有 4 根 SPI 是**板载 flash**(与 2260 无关,
2260 只有 I2C 的 SCL/SDA)。⇒ RSTN 与 SPI 两条嫌疑都划掉。

**唯一存疑**: 转接板 J1.1-5 供 VCC_3V8(3.92V) 而灯板标 2.8V; J1.16-20 供
VCC_2V8(2.96V) 而灯板标 3.8V —— **两路可能是反的**。若反了: VDDR 拿 3.92V
仍在 2.8-5V 内(不坏), 但 VDDGB 只有 2.96V **低于 3.5V 下限 ⇒ 绿蓝不亮**。
⚠ 用户尚未量 J1.1/J1.16 确认。

## 🔴 ACK 串扰源确认 = DCLK, 一次干净的单变量对照

| 模式 | DCLK | ACK 错误率 |
|---|---|---|
| LVDS | 恒 0 | **0 / 秒** |
| TTL | 25MHz 方波 | **50,241 / 秒** |

同板同线, 唯一变量是 DCLK 动没动。转接板上 **DCLK=J1.21 / ACK=J1.22 紧邻且无地**。
⇒ **下一版转接板必须在 DCLK/ACK/SYNC 之间插地**; TTL 模式下 ACK 不能当诊断用。
⚠ 之前那次「改速率看错误率」的实验同时改了几何, 是废的; 这次是意外拿到的对照。

**并且证伪了我自己加的一道闸**: 「头部码 ACK[3:0]==0b0010」挡不住**周期性**噪声
—— 垃圾帧能稳定凑出那 4 位, 于是 5 万帧/秒全部"合格", 计数器又一次长得像
"找到 7 颗芯片应答"。**只有 CRC 那道闸可靠**(crc_ok 从未置位)。
⇒ ack_frame_cnt 改成只数 CRC 通过的帧。

## 2026-08-26 供应商给了寄存器表 —— 结掉三条假设

供应商(映己鸿鹄)发来 `2260lvds.xlsx`：238 行 (`reg_num` 0~237 / `reg_data` 0xNNNN)，
是**他们实测点亮这块 40×45 样板**的 mini-LVDS 配置。
导入脚本 `tools/import_vendor_regs.py` → `rtl/icnd2260_regs_vendor.mem`（带自校验断言）。
完整差异分析见仓库 `zynq_pov/icnd2260/docs/05_vendor_regs.md`。

### 被证实的（我们推对了）

- `0x06[9]=1` / `0x1a[9]=1` 是 mini-LVDS 使能 —— 供应商 `0x06=0xaa44`、`0x1a=0x0a48`，
  **`0x1a` 与我们自推的 LVDS 版一字不差**
- `0xb4[5:4]=10` = 3 通道 ⇒ **三对差分都要发数据**，不是只用 D0
- `REG_COUNT=238` 与他们一致 ⇒ "写多了把芯片写崩"不成立

### 🔴 因此被排除的死路（别再回头查）

**"寄存器配错所以不亮"这条假设已死。** 配置逻辑我们理解对了。
⇒ 不亮的根因被逼到**物理层 / 时序 / 通道映射**上。

### 我们**不可能**从手册推出来的 48 处

三个颜色块 `0x20/0x30/0x40` 里 `+9/+a/+c/+d` 四个偏移**三块取值互不相同**
⇒ 与这块板实际 LED 的正向压降/效率绑定的**每色标定值**。
手册 §11 那张表原文写明是 **TTL-3 通道默认值**，通用值，不含板级标定。
**教训：黑盒样板的驱动配置，标定类参数只能要，推不出来。**

### ⚠ 这份配置只有 704 fps

`0x00=0x493c` ⇒ 灰度分组数 74、N=8；`0x01=0x0020` ⇒ Width_X=32
G = 74×32×8 = 18,944 ⇒ 600MHz/(18944×45) = **704 fps**，离 9,000 fps 差一个数量级。
先用它点亮，再按 `docs/04_fps_sweep.md` 压 `0x00`/`0x01`。
⚠ **降 G 会不会连带影响那些每色标定值，不知道** —— 要压帧率时得再问供应商。

### 仍然没解决（4 条，全在协议层）

配置/VHEAD 是否走 B 对(D0) / RSYNC 是否 4 沿每位 / 转发时钟相位 90° / CHKSUM 多项式位序。
⇒ **这 4 条只能靠一段供应商实测波形验证**，继续催 Q1(波形) 和 Q5(通道映射)。
见 [[feedback_led_panel_blind_bringup]]。

用户重焊了板对板接插件并测过无焊桥。烧 `icnd2260_lvds_dbg_div48` 复测:

### 三条新结论(各自独立成条)
1. **CHKSUM 是反射型 0x8408** → [[feedback_icnd2260_chksum_lfsr_is_reflected]]
   已修，且做成运行时开关(`crc_refl`)。**但改完屏仍没亮 ⇒ 必要不充分。**
2. **ACK 静默证明不了任何事** → [[feedback_ack_silence_is_not_evidence]]
   菊花链是手册明写的可选功能，样板可能压根没接；且读出通路自身有未定位缺陷
   (扫设备号出的"回包"两次落在不同设备号上，且回包速率超提问上界 830 倍)。
3. **链路天花板 ~1310 fps + 我们跑在供应商工作点的 1/7** → [[project_icnd2260_link_ceiling_and_clock]]

### 这次加进 RTL 的两个运行时开关(都在 VIO 上, 不用重编)
- `dbg_pn_inv[3:0]` —— 差分对 P/N 极性 {ck,r,g,b}。**P/N 对调 == 数据取反**
  (接收端看 P−N，屏侧接反就是 −(P−N))，所以能做成运行时开关，16 种组合秒切。
  探针名是 **`dbg_pn_inv`**(顶层网名，**不带** `g_dbg.` 前缀 —— VIO 命名不统一，

- `g_dbg.o_crc_mode[1:0]` = {`crc_lsb_tx`, `crc_refl`}，INIT=0x1。

`led[0]` 原来接自由计数器 `hb[24]` ⇒ **tx 挂死也照常慢闪**，是假判据。

3. **上电那 25.2ms 无时钟窗口**违反手册 §3.2「时钟不停」——

# 🎯🎯 2026-09-01 18:20 首光 —— 根因是 RSYNC 发长了 4 倍

**屏亮了。** 从 2026-08-19 第一次上板到今天，整整两周全黑，根因**只有一个**：

> `S_RSYNC` 把 `0xFFFF0F0F0F0F0F` 当成 56 个**逻辑位**、每位再发 4 个时钟沿 = **224 个沿**；
> 而它本来就是**线上电平序列**，只占 **56 个时钟沿**（逻辑值其实只有 14 位 `0x3D55`）。
> ⇒ 芯片帧对齐器永远匹配不上 ⇒ 配置一条不认 ⇒ **屏黑 + 零 ACK，一个 bug 解释两条症状**。

详见 [[feedback_rsync_is_56_edges_not_56_bits]]。改完当场亮。

## 今天一并结掉的推断（全部由供应商抓包实证，见 [[reference_icnd2260_vendor_capture_decode]]）

| 推断 | 结论 |
|---|---|
| CHKSUM 算法 | ✅ **CRC-16/CCITT-FALSE**（0x1021 左移 / init 0xFFFF / MSB 先入 / CHKSUM 域 MSB 先发），**20 个包 20 中** |
| ~~CHKSUM 是反射型 0x8408~~ | ❌ **本日上午的误判**。三个盲测 agent 读图一致，但**图上 C15/C0 的命名与硅上的串行化顺序不是一回事**；抓包直接推翻。见 [[feedback_icnd2260_chksum_lfsr_is_reflected]] 的更正节 |
| `VHEAD[15:0]` | ✅ **是校验和**（实测 `A5A5_0930_91C4`，CRC(0x0930)=0x91C4）。p.12 那句"等于 VHEAD[31:16]"只适用于 TTL |
| RSYNC 图样 | ✅ `0xFFFF0F0F0F0F0F`，但**只占 56 个沿** |
| 配置段 4 沿/位 | ✅ 正确（抓包逐包 CRC 通过） |
| 转发时钟 90° 移相 | ✅ 手册 DS9 时序图 + 抓包一致 |
