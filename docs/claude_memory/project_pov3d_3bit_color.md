分支 **`feature/3bit-color`**（从 `feature/icnd2260-dualface` 切出），仓库 `mlkpai_fs03/`。
起点 1-bit/7.2°/单色 → 08-24 **3-bit / 双面偏心 / 2.54° / ~9.4fps** → **08-25 加 PL 解码+fold_a 后 969RPM 下 10-12 fps**(见文末)。

## 架构：行内 BCM（不是屏级）

每行连续发 plane0/1/2 再进下一行。**屏级 BCM 在 POV 上是错的** —— 三遍之间转子转过
12°，三个位平面落在三个不同角度，颜色会沿角度方向分离拖尾。行内的三个平面在 23µs
内完成，角度差 0.06°。

行周期 195 拍 = FETCH1 + LOAD1 + SHIFT192 + LWAIT + DISP1；`LWAIT = max(0, oe−111)`。

## 🔴 权重与位序是一体的，改一个就是坏的

`LWAIT` 里那个 **111 来自"OE 收完还要等行驱推进 80 拍"**，与移位窗无关。而
**plane 边界不推进行驱** ⇒ 只有 plane2 受 111 限制，plane0/1 上限是移位窗 192。
实测：`w0=187`/`w1=187` 都不加拍，只有 `w2=187` 让 frame_period 31590→35694。

⇒ 最大权重要放在不受限的 plane0 ⇒ **host 侧 plane0 装 MSB**，权重 **184/92/46**（4:2:1）。
占空 **0.550** vs 1-bit 的 0.5692 = **96.7%，亮度几乎无损**（旧的 LSB-first + 27/54/108
只有 57%）。⚠ 位序改了权重没跟着改 ⇒ 码值1(108沿) 比 码值2(54沿) 还亮，上板复现过，
而且因 `pov_rxd` 每 256 次重申寄存器，现象还会飘忽。

## 🔴 aclk 是 50 MHz —— 我误判成 25 并写进过文档

`oeprobe` 采样 0.5µs 而 plane 周期 3.9µs，每周期才 7~8 个点，**漏沿漏掉近一半**，
算出 26MHz。改配置让采样变快后立刻跳到 39.9MHz 下界。**edges 只会被低估不会被高估**，
这一条就能排除 25MHz。BD/约束/ps7_init 那五条硬件证据一直是对的。
⇒ 面板 1-bit 刷新 4748Hz、3-bit 1583Hz；DCLK = aclk/2 = **25MHz（手册上限）**，
线速率 50Mbps —— `fast` 一直就在跑设计值。

## half_scan：拿垂直分辨率换角分辨率

`0x0C sub01 [18]`：每行只发 96bit ⇒ 行周期 195→99，整屏 31590→**16038**，槽数翻倍。
⚠ 三件必须同时做，缺一不可：
1. **两个引擎都要接**（漏了 u_eng_b ⇒ 两屏速度差一倍，转起来角度对不上）
2. **`oe` 上限掉到 18** ⇒ 必须把 `row_cfg.adv_high` 压到 25（=500ns@50MHz，ICND1028
   下限，上板双向验证可用），上限才回到 57
3. **地址每行要补跳 3**（plane 边界和**行边界**都要）
⚠ 上半屏必然出现一份差一个扫描行的拷贝：**移位链推移，不是"远端保持旧值"**。
   datasheet 的 REG1/REG2 只有电流增益/白平衡/消影/开路检测，**没有级联深度配置**，
   所以"只发一半就只亮一半"做不到，只能接受拷贝、只看其中一半。
⚠ 内容压缩要用 **max 不是平均**：表面内容垂直稀疏，平均会把亮线和黑底混一起，
   实测平均码值 2.43→1.40、码值7占比 17.7%→6.3%，屏上暗一倍。
⚠ 半屏垂直 2:1 压缩而半径不压 ⇒ 立体像必然压扁（倾斜 30° 视在变 16°，看着像"中间
   拐弯"）。只能靠把半径也缩一半（`--cyl-radius 0.23`）恢复比例。

## 圈级 BCM：技术上全赢，闪烁一票否决

三个位平面摊到连续 3 圈，每屏只扫 1 遍 ⇒ **角分辨率不掉**，`dec+cpy` 295→35ms，
帧率跑满转速。但 11rps 下图像重复率仅 **3.7Hz**，用户实看**闪烁不可接受**。
要可用需转速 ≥150rps，机械上封死。代码保留（`pov_rxd --ring-bcm`），别再走一遍。

## 其他实测数字

- 3-bit 载荷反而更小：1-bit 双面 720 片 8.85MB vs 3-bit 双面 100 片 3.69MB = **÷2.4**
  （槽数砍掉的比色深加上的多）
- 感知非线性是 3-bit 的物理上限：码值 1 在人眼已有 **41%** 亮度，0→1 的感知跳变是
  6→7 的 4.3 倍。**搜遍全部权重组合最多改善 4%** —— 调权重救不了，要根治只能加 bit
- `PVS_FRAME_RAW_MAX` 8.85→10.49MB，**三处必须同改**：`protocol.h` /
  `povstream.py` 的 `FRAME_RAW_MAX` / **`pov_boot.sh` 的 povmem size**（手写常量，
  漏改 = mmap 覆盖不到 bank C 尾部 = 静默越界写，我就漏了这处）
- 🔴 **改 `row_cfg`(行驱时序) 必须先 `auto_en=0`**：对着正在跑的引擎改会把行驱卡住，
  `EG_IDLE` 等不到 `!rd_busy` ⇒ 永远进不了 FETCH。现象是 `auto_en=1` 但 OE 零边沿、
  `frame_period=0`，极像"新 bit 坏了"，我差点误判去回滚。`auto_en` 关再开即复位。
- `0x24` 读写不同义：写 = `row_cfg`，读 = `POV_CTRL` 影子 ⇒ **row_cfg 无法回读确认**

## 🔴 引擎会在运行时切换色深/扫描模式时**死锁**（一天撞三次）

触发: 运行时改 `bpp_mode`(sub01[16]) 或 `half_scan`(sub01[18])。典型序列 ——
`pov_rxd` 启动时还没收到帧, 用默认值写 sub01(bpp3=0) ⇒ 引擎 3-bit→1-bit;
推流后收到 3-bit 帧又切回去 ⇒ **切换瞬间卡在 EG_IDLE**。

现象极具误导性: `auto_en=1`、STATUS 一切正常、`frame_period` 冻在一个**残留值**
(见过 5508 / 0), 但 `oeprobe` 的 **edges = 0** —— OE 一个边沿都不动。
第一次撞上时我以为是新 bitstream 坏了, 差点回滚 SD 卡。

**判据**: 光看 `frame_period` 和 STATUS 会被骗, 必须看 `oeprobe` 的 **edges**。
**workaround**: 任何色深/扫描模式切换之后, `auto_en` 关再开:
    pw(0x0C, 0xC1000000); sleep(0.4); pw(0x0C, 0xC1000003)
**根治**: RTL 里让 `bpp_mode`/`half_scan` 变化时自动回 EG_IDLE 重新起跑。未做。

⚠ 另一条同类的: **改 `row_cfg`(行驱时序) 也必须先 `auto_en=0`** —— 对着正在跑的
引擎写 `adv_high`, 行驱会卡在中间态, EG_IDLE 永远等不到 `!rd_busy`。已写进
`pov_boot.sh` 的写入顺序。

## 三方权衡: 角分辨率 ↔ 空间分辨率 ↔ 形状比例

| 配置 | 有效分辨率 | 角分辨率 | 亮度占空 |
|---|---|---|---|
| 全屏 142 槽 | **160×180** | 2.54° | **0.550** |
| 半屏 142 槽 (不等比例) | 160×90 | 2.54° | 0.333 |
| 半屏 142 槽 + 等比例 | **80×90** | 2.54° | 0.333 |
| 半屏 283 槽 + 等比例 | 80×90 | **1.27°** | 0.333 |

🔴 **全屏用满槽数(142)和半屏 142 槽角分辨率完全一样, 但空间分辨率翻倍、亮度高 65%**
—— 我一度只给全屏配 100 槽(3.6°), 白白让半屏显得更优。半屏真正的优势只有
"能到 283 槽(1.27°)", 代价是 2×2 的马赛克颗粒(用户实看"颗粒感过了")。
⇒ 除非确实要 1.27°, 否则**全屏用满槽数**是纯赚。

⚠ 颗粒感的归因方法: 用 `tools/pov_preview.py` 把**实际发送的字节**按真实角度投影
叠加成"转起来的样子"。实测 `--no-dither` 与有抖动几乎无差 ⇒ 颗粒不是 3-bit
量化也不是抖动, 而是 `--half-aspect` 把水平也压一半后的 2×2 放大。

# 🎯 2026-08-25 续: PL 硬件解码 + fold_a, 帧率 5.5 → 10-12 fps

本文原来收在 08-24 的"3-bit / 双面偏心 / 2.54° / ~9.4fps"。第二天两件事又把它推了一档。

## PL 三引擎 lz4 解码 (commit `7efe755`)

三个引擎挂 HP3/HP1/HP2, AXI-Lite `0x40020000/30000/40000`。
**解码 74 ms/帧(0.95 B/clk), 828/828 帧全走 PL, fb=0, 超时 0 次。**
改造前 `dec 158ms + cpy 80ms = 238ms/帧` ⇒ 5.5 fps。详见 [[project_lz4_pl_decoder]]。

🎯 **顺带定了本文那桩 aclk 悬案**: 两条独立证据 —— `rev_period 4522362 ÷ 11.06 rev/s`,
以及 `CYCLES 3.69M ÷ 74ms` —— 都指向 **aclk = 50 MHz**。本文上面那段推断被上板坐实。

🎯 **`pair_miss` 基线 = 0 且三引擎全速打 DDR 后仍是 0.0/s**。
风险评估的推断(面板在 HP0 独立 DDRC 口 + 纯读, DDRC 拥塞时读优先于写 ⇒ 面板是被偏袒的一方)实测站住。
⚠ **但这条归因只对 Zynq 成立, 别搬到 DR1**: "拥塞时读优先于写"是 **AMD 明文**;
而**安路对 DR1 确定否认**("不是简单固定读优先或写优先", 且没有最小带宽/最大延迟保证)
⇒ **这个 `pair_miss=0` 不能当 DR1 的预期**, 见 [[reference_dr1_hp_backpressure_and_ot]]。
⚠ 但读这个计数器要小心: 16 位且只有 PL 复位能清, **只能冷启动后测增长率**
([[feedback_pair_miss_sentinel_was_broken]])。

## fold_a (commit `970edce`)

**帧 10.47 → 7.85 MB**(213 片 = 面A 71 + 面B 142), 解码量 −25%, **74 → 55.5 ms**。
🔴 **必须配 `--stream-split even --stream-workers 3`**: 213 片跨面切成 71/71/71 才均分;
按面切会切成 71/142, makespan 被 142 那条封顶 ⇒ **收益全丢且无任何报错**
([[feedback_fold_a_needs_even_stream_split]])。

**3-bit 与 fold_a 天然正交**: plane 换算在镜像**之后**, 三个位平面各自被同一个 (lane,row) 置换。
`half_slices = n_slices>>1` 不是硬编码 180 (142 ⇒ 71)。
⚠ 镜像置换路径在现役配置(`mirror_a=0`)下**从未被激活过**, 这是唯一真正"新"的东西, 画面对不对只有眼睛能判。

## 🔴 串行胜过流水线 (同 commit, A/B 实测)

| | rx | flip | drop | 实际上屏 |
|---|---|---|---|---|
| 流水线 | 15-17/s | 4-8/s | 1600 | 4-8 fps |
| **串行** | 10-12/s | **10-12/s** | **9** | **10-12 fps** |

串行下 **flip == rx, 一帧不丢**。**收得更快, 上屏反而更少** ——
流水线把 settle 推迟到"收到下一帧", 帧就绪节奏被 WiFi recv 拖着走, 与 62 ms 翻页窗失去同步。
⚠ **只在"解码比一圈快"时成立**, 解码若再变慢要重新评估([[feedback_pipeline_breaks_flip_window_sync]])。
默认已改为 `--no-pipeline`。

## 现役工况 (969 RPM)

**16.15 rev/s / 圈周期 62 ms / 10-12 fps / `flip == rx` / drop 9。**

🔴 **一个没人算过的账**【推算, 未上板验证】: 3-bit 整屏 **1583 Hz**,
16.15 rev/s 下每圈只画得出 `1583/16.15 ≈ 98` 个角度, **而配置是 142 槽/面**。
(142 对应的是 `7efe755` 那次的 11.06 rev/s: `1583/11.06 ≈ 143`, 精确吻合。)
⇒ **08-25 提速之后, 142 槽里可能有约 1/3 没机会上屏。**
不影响帧率(面板不满足只掉角分辨率), 但影响"该渲多少片"。值得顺手量一次。
