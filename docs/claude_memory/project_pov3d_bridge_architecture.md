# 转子侧串化桥架构 (2026-08-31, 用户提出 + 供应商选型手册核算)

用户原话: **"高速接口连接 CPLD, 2 个 CPLD 各驱动 1 块屏幕, 需要能同步, 满足速度要求就行"**。
按 `0807_安路科技选型手册中文版V202607.pdf`(供应商给的, 微信文件目录下)逐表核算 ⇒ **成立**。

## 🔴 先澄清一个词: 这不是被否掉的那个"外扩 CPLD"

[[project_pov3d_final_target_chip_verdict]] 否掉的是 **"当扇出用"**(比特率守恒, 扇出只复制
比特不减比特率)。而那条同时写明: **"唯一成立的例外是转子侧串化桥"** —— 用户提的正是这个。
**架构没问题, 只是器件类别要改口**:
- **安路没有 CPLD 产品线** —— 最小的 EF2(XWFN42/LGA42, 4.2×4.2mm) 也是 FPGA。
- 桥片必须在 950-1250 Mbps 上做**源同步接收 + 相位对中**, 要 **ISERDES/IDELAY**。
  ✅ 安路 FPGA 有: PH1P 选型表注 2 明确写 "CCLK 复用后**不支持 ISERDES、OSERDES、IDDR、
  ODDR 功能**" —— 反证这些模块存在。

## 数字 (605 片/圈 · 900 RPM · 双面 48 颗 · 每颗 1.3824 Mbps/片)

```
每面数据率 = 24 颗 × 1.3824 × 605 = 20.07 Gbps      (双面 40.15, 与旧账吻合)
```

| 段 | 対数 |
|---|---|
| **主控 → 桥**(每面), @**1250** Mbps/対(DR1/PH1A 真 LVDS) | 17 数据 + 1 时钟 = **18** |
| 同上 @**950** Mbps/対(7020 的 OSERDES 上限) | 22 + 1 = **23** |
| **双面合计** | **36 対**(1250) / **46 対**(950) |
| **桥 → 屏**(每面), 24 链 × 3 数据対 + 外置时钟扇出 1 | **73** |
| 同上, 每链自出时钟 | 72 + 24 = **96** |
| **单颗桥片总対数** | **91**(外扇时钟) / **114**(自出时钟) |

## 🎯 最大的收获: **墙②(板级引出)第一次在纸面上通过**

FS03 的 CEP1+CEP2 只引出 **96 信号 = 48 対**(逐脚核过)。
原方案要 192 対 ⇒ 差 4×, 是[[project_pov3d_final_target_chip_verdict]]里"换 FPGA 一根线
都不多给你"的那堵墙。

**桥架构下主控只要 36-46 対 ≤ 48 対** ⇒ ✅ **过了, 而且主控一颗芯片都不用换**
(7020 与 DR1 的 96 対都绰绰有余)。

🔴 **但 7020 与 DR1 在这里第一次不再打平**:
- DR1 真 LVDS **1250** Mbps ⇒ 36 対, 对 48 対余量 **1.33×**
- 7020 OSERDES **950** Mbps ⇒ 46 対, 余量 **1.04×** —— **加 10% 帧同步/对齐开销就不够了**

⇒ 🎯 **这是"换 DR1"迄今为止第一个纯技术上的正当理由**(此前只有供货/成本/国产化)。

**线束也一起解了**: 长线束从 **384 根**(192 対) 降到 **72-92 根**;
192 个精密终端电阻从"甩在转子上"变成"焊在桥板上, 离屏几厘米"。

四条独立对账全中(DS300 表 1-1-2 与手册逐个吻合):

| 器件/封装 | 手册那栏 | 数据手册原文 | 真対 |
|---|---|---|---|
| EG4A20BG256 | 196/**90** | `196/(39+51)` | **39** |
| EG4X20BG256 | 193/**89** | `193/(53+36)` | **53** |
| EG4X20LG144 | 107/**47** | `107/(25+22)` | **25** |

| **EG4S20CG324** | **215/104** | **`215/(50+54)`** | **50** |

⇒ 🔴 **看选型手册那一栏会把真差分対高估约一倍。必须回查各系列数据手册的括号拆分。**
而 EG4 的**仿真 LVDS 输出只有 166 MHz ≈ 332 Mbps**, 连屏要的 333-340 都差一点
⇒ **那 54 対仿真対驱不了屏, 可用的只有 50 対真対。**

### ② 但"EG4 会把墙②又立回来"这句**作废** —— 我用错了口径

原文算的是 `40.15 Gbps ÷ 800 = 54 対 > 48`, 那是 **16-bit 上行口径**。
而本文后来已经改成 **8-bit 上行 + 桥做 8→16 扩展**, 上行总量只有 **20.07 Gbps**:
```
20.07 Gbps ÷ 800 Mbps/対 = 26 数据対 + 4 时钟 = 30 対  ≤ 48  ✅ 不超
```
⇒ **EG4 的 800 Mbps 上限在 8-bit 口径下不再撞墙②。死因 2 只剩"要多分几颗桥"。**

## 🔴🔴 2026-09-01 再更正: "仿真対 332 < 333 所以驱不了屏"**判严了**, EG4 用 **2 颗**就够

用户指出: **屏侧时钟本来最高就是 166-170 MHz**, 所以 166 MHz 的仿真 LVDS 够用。**对的。**

### ① 332 vs 333 是 0.3%, 而且 166 MHz 在屏的合法区间正中

屏手册 `tLVCP = 6~50 ns` ⇒ **合法时钟 20~170 MHz**。166 MHz **完全合规**, 只比上限低 2.4%。

```
每链能力 = 3 対 × 332 Mbps = 996 Mbps
每颗需求 = 1.3824 × 605 片 = 836.4 Mbps
⇒ 占用 84.0%   (对比 340 Mbps 时是 83.6%)  ✅ 仍余 16%
```
⇒ **605 片/圈在 166 MHz 下照样成立。**链路帧率天花板从 1312 fps 掉到 1281 fps, **无意义**。
🔴 **我之前把"332 < 333"当硬门槛是错的 —— 那 0.3% 不是墙。**

### ② 更关键: **仿真対只在"输出"时受限, 作输入照样 800 Mbps**

DS300 §2.7 原文: **「True LVDS 与 Emulated LVDS 均可作为 LVDS25 标准输入, 最大输入频率
400 MHz(800Mbps)」**。
⇒ **上行入口不挑真/仿真**, 104 対里任意 14 対都能当 800 Mbps 输入。

### ③ ⇒ EG4S20CG324 **2 颗就够, 余量 1.2×**

| 用途 | 対数 | 用哪种 |
|---|---|---|
| 出屏 | 24 链 × 3 + 1(喂外置时钟扇出) = **73** | 54 仿真 + 19 真(混用) |
| 上行入 | 10.04 Gbps ÷ 800 = 13 + 1 = **14** | 真/仿真皆可 |
| **合计** | **87 対 ≤ 104** | **余量 1.20×** |

SoC 侧: 2 面 × 14 = **28 対** ≤ 48(FS03) ≤ 60(GEG400) ✅
⇒ **"要 4 颗"那条作废。**

⚠ **EG4A20BG256 (39+51 = 90 対) 仍然不推荐**: 87/90 只余 **3.4%**, 太薄; 且 17×17 比 15×15 大。
**要用 EG4 就用 EG4S20CG324。**

### 🎯 ④ 意外收获: 仿真 LVDS 的**共模可调**, 正好解掉 VOCM 那条老问题

真 LVDS 的 VOCM 由芯片定死 **0.9/1.25/1.4 V**, 对屏要的 **VIC 1.1~1.3 V** 是"典型值正中、
两端超窗", 一直是要问 FAE 的头号电气问题。
而**仿真 LVDS 的输出摆幅与共模由外部 3R 网络 + VCCIO 共同决定**。
⚠ **措辞要准**: DS300 这一段只明说"改变电阻网络值来**降低功耗或者改善噪声容限**";
**把共模钉到 1.2 V 是我按 3R 分压推的, 不是手册原话**。EF3 手册在 MLVDS 那节倒是明写了
"用...电路来调节差分信号的共模电压...不同 VCCIO 对应的偏置电阻值不同"。
⇒ **可行性高但必须找 FAE 确认 + 自己算一遍分压**, 别当成已知。
⇒ 🎯 **可以按设计把共模钉在 1.2 V 正中, VOCM 那条问题在桥→屏这段消失。**

## 原始判决存档 (口径已过时, 见上方更正)

**死因 1: 真差分対不够。** DS300 表 1-1-2: EG4A20BG256 = `196/(39+51)` ⇒ **真 LVDS 只有 39 対**
(EG4X20BG256 是 53, LQFP144 版只有 25)。单驱一面就要 **73 対输出**, 差 1.9-2.3×。
拆成 4 颗各管 12 颗屏驱? 每颗要 37 出 + 14 入 = 51 対, EG4X20 的 53 対**只余 4%** —— 但见死因 2。

**死因 2(更硬): 🎯 上行対数由「主控发送能力」与「桥片接收能力」中**较慢**的那个决定。**
EG4 的 True LVDS **收发都封顶 400 MHz = 800 Mbps**(DS300 §2.7 原文), 而
**Emulated LVDS 输出只有 166 MHz**(≈332 Mbps, 连屏要的 333 都差一点)。
```
双面总量 40.15 Gbps ÷ 800 Mbps/対 = 50 数据対 + 4 时钟 = 54 対
```
⇒ **超过 FS03 引出的 48 対** ⇒ **换 EG4 会把刚刚推倒的墙②又立回来**。
对比: PH1A/PH1P 的 HR LVDS25 收发都是 **1250** Mbps ⇒ 32 数据 + 4 = **36 対** ✅;
HP LVDS18 是 1500 ⇒ 28 対。

⇒ **桥片的 LVDS 线速率不是"够 333 就行"** —— 它同时决定上行要占主控多少対,
而上行対数正是这个架构成立的唯一理由。**≥1250 Mbps 是硬门槛, 800 Mbps 不合格。**

⇒ **推荐 PH1A60GEG324 + 一颗外置 LVDS 时钟扇出**; 不想要扇出芯片就上 **PH1A90SBG484**。
⚠ **价格全部未询** —— 上表按対数排, 不是按价排。

## 同步怎么做

- 两颗桥片挂**同一路参考时钟 + 同一路帧/切片同步脉冲**, 各自用它复位行/切片计数器
- 转子索引(顶部光电对射)由**主控统一分发**, 不要两颗各自采
- 两路上行**等长布线**
- **双面差异逻辑留在主控侧**(现役 `PHASE_B=180` + `mirror_a/b` 已经在做), 桥片保持"哑" ——
  哑桥才好验证、好复用、好换料

## DR1 ↔ PH1A60GEG324 的接口怎么定 (2026-08-31)

**结论: 源同步并行 True LVDS, 单向下行, 每面独立一组。SERDES 不可选 —— 两颗都没有**
(选型手册 PH1A60GEG324 的 Serdes 列是 `-`; DS1200 全文 GT/PCIE/SATA 零命中)。

### 🎯 第一件事不是选接口, 是把 8→16 bit 扩展放进桥片

2260 线上是**固定 16-bit**, 但 [[reference_icnd2260_spec]] 已经算过
「DDR 里按 8-bit 存, 出口左移对齐到 16-bit」只要**几十个 LUT**。
把这几十个 LUT 放在**桥片**里, 上行带宽直接减半:

| 上行口径 | 每面 | 800 Mbps/対时的数据対/面 | 双面合计(含时钟) | 板级 48 対 |
|---|---|---|---|---|
| 16-bit(纯哑桥) | 20.07 Gbps | 26 | **54 対** | ❌ 超 |
| 10-bit | 12.55 Gbps | 16 | **34 対** | ✅ |
| **8-bit** | **10.04 Gbps** | **13** | **28-30 対** | ✅ 余 1.6× |

🔴 **所以"桥做位宽扩展"不是可选优化, 是让保守线速率(800)下架构仍然成立的前提。**
纯哑桥只在线速率跑满 1250 时才勉强成立(36 対) —— 而线速率恰恰是最没把握的那个数。

### 接口规格 (建议值)

| 项 | 值 |
|---|---|
| 物理层 | True LVDS25 (DR1 侧 / PH1A60 侧都是 HR bank @VCCIO 2.5V) |
| 方向 | **单向下行**(DR1 → 桥) |
| 每面 | **13 数据対 + 1 时钟対 + 1 同步対 = 15 対** |
| 双面合计 | **30 対** (板级引出 48 対, 余量 1.6×) |
| 线速率 | **800 Mbps/対** (对 1250 上限降额 36%) |
| 内部时钟 | 200 MHz (1:4 gearing) |
| 编码 | **无**(源同步转发时钟), 上电送训练码型做 bitslip 对齐, 对齐后回读 ACK |
| 回读通道 | 单端 SPI 或 UART, 几 Mbps 足够(桥状态/对齐标志/错误计数/温度) |
| 同步 | 两颗桥**共用**同一路 sync; 转子索引由 DR1 统一分发 |

### ✅ 一个白捡的简化: DR1 与 PH1A 的 LVDS 共模**逐格相同**

DR1(DS1200 V1.0 表 3-14) 与 PH1A(DS900 表 3-1-13) 的 **VOCM 输出 = VICM 输入 = 0.9/1.25/1.4 V**
—— 同一族 IO 库, **发送端共模正好落在接收端窗口正中**。
且 PH1A 有**片内 100Ω 差分端接**(RT 80/100/120)。
⇒ **DC 耦合直连, 零外部端接电阻**。
🎯 **VOCM 那个老问题在这一段不存在** —— 它只存在于**桥 → 屏**那一段(2260 要 VIC 1.1~1.3)。

### 🔴 由此撤回一条: **"DR1 上行比 7020 好"说反了**

原文写"DR1 真 LVDS 1250 vs 7020 OSERDES 950 ⇒ DR1 赢, 这是换 DR1 第一个纯技术理由"。
**引脚能跑 1250 不等于 fabric 喂得动 1250** —— 线速率 = gearing × f_logic:

| | gearing | 跑 800 Mbps 要的内部时钟 | 跑 950-1250 要的内部时钟 |
|---|---|---|---|
| **DR1 (ODDRx2)** | **4:1** | **200 MHz** | 237-312 MHz ❌ 不现实 |
| **XC7Z020 (OSERDESE2)** | **8:1**(可扩到 10:1) | 100 MHz | **119 MHz @950 ✅** |

而 DR1 PL 迄今实际收敛过的最高频率是 **100 MHz**(axi_hp_arb, 余量 43%), 上板 RTL 是 50 MHz。
**200 MHz 比任何做到过的都高 2×。**
⇒ 🔴 **7020 的 8:1 OSERDES 反而让上行更容易**; "换 DR1 的第一个技术理由"**作废**,
回到"换安路只有供货/成本/国产化"。

### ✅ 但架构不受影响 —— 因为 8-bit 口径留了足够余量

| DR1 上行线速率 | 数据対(双面 20.07 Gbps) | +时钟 | 板级 48 対 |
|---|---|---|---|
| 800 Mbps (4×200 MHz, 要冲) | 26 | **30** | ✅ 余 1.6× |
| 600 Mbps (4×150 MHz, 稳妥) | 34 | **38** | ✅ 余 1.26× |
| 500 Mbps (4×125 MHz, 保守) | 41 | **45** | ⚠ 余 1.07× |

⇒ **8-bit 口径下, 即使 DR1 只敢跑 500 Mbps 也还过得去。**
🔴 **但 16-bit 口径在任何一档都不成立**(要 52-82 対) ⇒ **"桥做 8→16 扩展"从优化升级为必需, 二次确认。**

### "能不能在 DR1 上做出 Zynq 那样的 8:1" —— **不能, 但不需要**

原语端口列表实证(`dr1_logic_io.v`, 端口名直接暴露位宽):
```
DR1_LOGIC_ODDR    : d0,d1        ⇒ 2:1
DR1_LOGIC_ODDRx2  : d0,d1,d2,d3  ⇒ 4:1   ← 硬上限, 没有 x4/x8
DR1_LOGIC_IDDRx2  : q0..q3       ⇒ 4:1
```
⇒ **fabric 必须在 `线速率/4` 上跑, 没有绕法**: 想 8:1 就得 fabric 每拍出 8 bit,
而 ODDRx2 只收 4 bit。**"fabric 里再做一级 2:1 mux"不成立** —— 那级 mux 本身就在
ODDRx2 的输入时钟域上, 省不掉。

**⚠ 唯一可能的例外(待实测)**: `dr1_phy_ioclk.v` 是专用 IO 时钟网络。若最后一级 4:1
能放进 IOCLK 域, 通用 fabric 就能跑更慢。但 EG4 手册明写 **"IOCLK 不能驱动逻辑资源
(PLB、ERAM), 因为 IOCLK 时钟网络只能覆盖同一组/时钟区域内的 I/O 列"** ⇒ 只能驱 IOL 寄存器,
做不了 mux ⇒ **大概率不通, 但能用 TD 综合实测(我自己能跑)**。

### ✅ 但不需要 —— 8-bit 口径下"拿对数换速率"全档都过

| DR1 fabric | 线速率 | 双面数据対 | +时钟 | ≤48 対? |
|---|---|---|---|---|
| **125 MHz**(现役量级) | 500 | 41 | **45** | ✅ 1.07× |
| **150 MHz** | 600 | 34 | **38** | ✅ 1.26× |
| 200 MHz(要冲) | 800 | 26 | **30** | ✅ 1.60× |

⇒ **不追 Zynq 的速率, 多用几対就行。**

### 🎯 而且这条反过来说明: **桥架构让"主控选谁"变得不重要了**

原来 192 対是死结, 现在只要 30-45 対 ⇒ **7020 / DR1V90GEG484 / DR1V90GEG400 全过**。
⇒ **主控可以按供货与成熟度选, 不用按引脚选。** 而按成熟度, **Zynq 明显领先**:

| | XC7Z020 | DR1V90 |
|---|---|---|
| 串化 | **OSERDESE2 8:1**, 950 Mb/s 只要 **119 MHz** fabric ⇒ 双面 **26 対** | ODDRx2 **4:1**, 800 要 200 MHz ⇒ 30-45 対 |
| HP 口 | **4**(现役用满) | 2 |
| WiFi | **持续 110-125 Mbps 已确立** | 从未确立 |
| PL lz4 三引擎 | **已上板跑通(08-25)** | HP1 08-27 才刚验 |
| 真差分対 / 板级 | 96 / 48 | 96 / 48 (打平) |
| 国产化 | ❌ | ✅ |

⇒ **换 DR1 的理由回到只有供货/成本/国产化** —— 与 [[reference_port_to_other_fpga_deps]] 第 5 条一致。

### "上行能不能用 HDMI 或更快的?" —— **两颗手册里 TMDS/HDMI 命中都是 0**

| 手册 | `TMDS|HDMI` 命中 | `SERDES|transceiver|PCIE|SATA|Aurora` 命中 |
|---|---|---|---|
| EG4 DS300 | **0** (差分标准表 2-7-1 只有 **LVDS / LVPECL**) | 0 |
| DR1 DS1200 V1.0 | **0** | **0** |

⇒ **HDMI 在这两颗上不是"能不能用", 是根本没有这个 IO 标准。**

**而且就算用 LVDS 硬凑 TMDS 波形, HDMI 反而更慢**:
1. TMDS 是 **8b/10b 编码 ⇒ 20% 带宽白扔**; 自定义源同步是 0 开销。
2. HDMI 的速度靠 **10:1 串化**, 而 **DR1 最高 4:1** ⇒ 1080p60 的 1.485 Gbps/lane
   需要 **371 MHz** fabric, 做不到。
3. HDMI 只有 **3 条数据 lane** ⇒ 20.07 Gbps ÷ 3 = **6.7 Gbps/lane**, 比需求高一个量级。

### 🔴 通用结论: **IO + gearing 就是天花板, 换任何"标准接口"都逃不出去**

PCIe / USB3 / SATA / Aurora / 10GbE / JESD204 全都要**高速收发器**, 而
**DR1 和 EG4 都没有**(DS1200 全文零命中)。这些协议最终也得由同一套 IO 发出来
⇒ **换协议不改变物理天花板, 只增加编码开销。**

**真要更快只有两条**:
- (a) 桥片换 **PH1A90SBG484**(4×10.3125 Gbps SERDES + PCIe Gen1/2/3) —— 🔴 **但链路两端都要有
  SERDES 才有用**, 而 DR1 没有、**XC7Z020 CLG484 也没有 GTP**(7Z015/7Z030 以上才有,
  见 [[reference_zynq7020_no_pcie]]) ⇒ **不成立**, 除非主控也换成 PH1A/PH1P —— 那就丢了 WiFi/Linux。
- (b) **降需求**: 605 → 315 片/圈(2 颗/链), 上行直接减半。

### ✅ 但不需要更快, 而且自定义源同步反而更适合

8-bit 口径下 **500 Mbps/対 就够**(45 対 ≤ 48), 对应 **125 MHz** fabric —— **现役量级**。
且自定义源同步比 HDMI **简单得多**: 无 8b/10b、无 CDR、无热插拔协商、**延迟确定**
—— 对本项目这种硬死线架构是优点不是缺点。

### 桥片要不要外挂 DRAM/SRAM? —— **不要, 单芯片就能工作**(但有个前提)

**前提: 主控按输出顺序发。** 哑桥只做 解串 → 8→16 扩展 → 24 链分发,
**不做重排** ⇒ 只需要每链一个小弹性 FIFO(跨时钟域 + 字对齐), 24 链合计 **几 Kb**,
片上随便放。**这正是"桥保持哑"这条设计原则的现金价值。**

**要缓存整片才需要大存储, 而那不该做**:
```
单颗每片 = 40px × 3 × 16bit × 48扫 = 92,160 bit = 11.25 KB
一面 24 颗 = 2,211,840 bit = 270 KB/片
一面数据率 = 20.07 Gbps = 2.51 GB/s
```
| | 片上存储合计 | 存得下 270 KB? |
|---|---|---|
| EG4S20 | ERAM 1088 Kb + Dis-RAM 157 Kb ≈ **155 KB** | ❌ |
| PH1A60 | ERAM 3160 Kb + Dis-RAM 676 Kb ≈ **480 KB** | ✅ 单缓冲够, 双缓冲不够 |

🔴 **而 EG4S20 那块内嵌 SDRAM 救不了数据通路**: DS301 §4 —— **2M×32bit (EM638325),
32 位总线, 最高 200 MHz, 峰值 800 MB/s**。而一面要 **2.51 GB/s** ⇒ **差 3.1×**。
⇒ 它对**流式数据通路没用**; 但 8 MB 空间对**测试图案/标定表/日志**很方便(白送的)。

| 件 | 说明 |

但确实不需要任何外挂 DRAM/SRAM。**

### EG4A20 行不行? —— **能跑满 800 Mbps 才行, 一档都不能降 ⇒ 不建议**

上行対数随线速率变(每桥, 8-bit 口径 10.04 Gbps/面), 而出屏固定 **73 対**:

| 上行线速率 | fabric(4:1) | 入対 | **总対** | **EG4A20BG256**<br>39真+51仿=**90** | **EG4S20CG324**<br>50真+54仿=**104** |
|---|---|---|---|---|---|
| 800 Mbps | 200 MHz | 14 | **87** | ✅ 余 3 対(3.4%)<br>真 22+14=36 ≤ 39 | ✅ 余 17<br>真 19+14=33 ≤ 50 |
| 600 Mbps | 150 MHz | 18 | **91** | ❌ **超 1 対** | ✅ 余 13 (真 37 ≤ 50) |
| 500 Mbps | 125 MHz | 22 | **95** | ❌ | ✅ 余 9 (真 41 ≤ 50) |
| 400 Mbps | 100 MHz | 27 | **100** | ❌ | ✅ 余 4 (真 46 ≤ 50) |

🔴 **决定性差别: EG4S20CG324 有 4 档降速余地, EG4A20BG256 一档都没有。**
而 **"EG4 的 55nm fabric 能不能跑到 200 MHz" 恰恰是整个设计里最没把握的假设**
(4:1 gearing ⇒ 800 Mbps 必须 200 MHz)。**把方案押在它跑满上, 是拿最不确定的一条当前提。**

其余差别(都指向 EG4S20):

| | EG4A20BG256 | **EG4S20CG324** |
|---|---|---|
| 封装 | 17×17 BGA256 1.0mm | **15×15 CG324 0.8mm**(转子上更小) |
| 内嵌 SDRAM | 无 | 64Mb(数据通路用不上, 但存图案/标定表方便) |
| 生态 | 少 | **国产开发板遍地, 最好买** |
| 単端余脚 | 196−180 = 16 | 215−208 = 7 |

⚠ 単端余脚这一项反而 EG4A20 多(16 vs 7), 但**差分対才是瓶颈**, 単端只用来接
SPI/UART/复位/LED, 7 根够。

⇒ **要用 EG4 就用 EG4S20CG324。EG4A20 唯一的场景是"确证 fabric 能稳跑 200 MHz
且方案再不会有任何增项" —— 这两条现在都不成立。**

**链路上限 = min(DR1 发, EG4 收) = min(4 × f_DR1, 800 Mbps)**

**每面载荷(8-bit 口径) = 24 颗 × 1.3824 Mbps/片 × 605 片 ÷ 2 = 10,036 Mbps**

|---|---|---|---|---|---|---|---|---|
| **200 MHz** | 800 | 13 | 14 | **28** | **56** | ✅ 余 **1.71×** | 14 → 33/50 | 87 |

(要独立同步対再 +1 対/面 = **+2 対 / +4 脚**)

🎯 **两条结论**:
1. **瓶颈在主控与板级那一侧, 不在 EG4S20** —— EG4 侧四档全过(87~100 / 104)。
2. 🔴 **DR1 fabric 必须落在 125~200 MHz 之间**: 低于 125 MHz 板级脚不够,

—— 板级余 1.33×、EG4 侧余 1.14×, 而 150 MHz 只比现役 axi_hp_arb 的 100 MHz 高 50%,
比 200 MHz 现实得多。

600 Mbps 差分只剩 24 根地(每対 0.67 根), **偏少**; 800 Mbps 那档剩 40 根(每対 1.43 根)才舒服。
🔴 **待查: FS03 的 CEP1/CEP2 有没有专用 GND 脚(不占那 96)** —— 查原理图数 GND 引脚即可。
**若地要从 96 里出, 可用窗口会从 125-200 MHz 收窄到 175-200 MHz**, 那 EG4A20 的

| **差分小计** | **14 対 = 28 脚** | **18 対 = 36 脚** | **22 対 = 44 脚** |
| 同步対(可做带内, 省掉) | +1 対 = +2 脚 | 同 | 同 |

**⇒ 一组 = 18 対 = 36 根信号(推荐档)。DR1 出两组 = 36 対 = 72 根。**

### 🎯 配置线: 让 DR1 加载 bitstream, 省掉两颗 Flash

EG4 支持**从动串行**配置(DS300: 从串/从并/主并/MSPI/JTAG)。让 **DR1 当加载器**:

| 信号 | 根数 | 说明 |
|---|---|---|
| CCLK / DIN | 2 | **两颗可共用**(EG4 支持 Flow Through 级联; ⚠ CG324 是否支持待查) |
| PROGRAMN | 1-2 | 复位配置 |
| DONE | 1-2 | 配置完成回读 |
| 回读 UART/SPI | 1-2 | 桥状态/对齐标志/错误计数 |
| **合计** | **≈ 6 根单端**(两面共用, 不是每面) | |

✅ **收益**: 省掉 2 颗配置 Flash + 各自的走线; bit 更新只改 DR1 文件系统里的文件,
不用碰转子上的 Flash —— 与 [[feedback_dr1_load_bit_without_jtag]] 的思路一致。

**✅ 实证(DS301 表 5-1 "EG4S20 配置模式及引脚")**: EG4S20 支持 **SS 从动串行, `M[1:0]=11`**,
配置引脚 = **PROGRAM_B / INIT_B / DONE / CCLK / DIN(`D0_DIN_MISO`)** 共 **5 根**
(⚠ `D0_DIN_MISO` 要 pull-up 到 VCCIO)。CCLK 频率范围**自 2.5 MHz 起**(DS300`:3435`,
上限同族是 24 MHz, 从动模式下由 DR1 驱动, **上限待确认**)。

🎯 **两颗桥跑的是同一份 bit**(A/B 面差异靠引脚/寄存器区分) ⇒ **DIN 可以直接并联**,
不必用 Flow Through 级联(也就不用在两块屏板间连转发线):

| 信号 | 根数 | 接法 |
|---|---|---|
| CCLK | 1 | 两颗共用 |
| DIN | 1 | **两颗并联**(同一份码流) |
| PROGRAM_B | 1 | 共用 |
| INIT_B | 1 | 开漏, 线与共用 |
| DONE | 1-2 | 线与共用(1) 或分别回读(2) |
| **合计** | **5-6 根**, 两面共用 | |

**加载时间**: bit 约 1-4 Mb(EG4S20 19,600 LUT 量级, **实测看 TD 出的 .bit 大小**),
@24 MHz CCLK ⇒ **几十至一百多 ms**, 并联加载两颗不翻倍。

### ⚠ 不要 Flash 的代价, 和一个零成本的对冲

| | 代价 |
|---|---|
| 上电顺序 | **DR1 Linux 起来并推完 bit 之后才有画面**; 桥片在那之前是空的 |
| 单点故障 | 🔴 **DR1 挂了屏彻底黑** —— 连自检图案都跑不出来; 有 Flash 的话桥至少能独立自检 |
| 依赖链 | 又多一条, 而 [[feedback_dr1_reboot_loses_everything]] 已经吃过"重启即丢"的苦 |

✅ **收益(在转子上尤其大)**: **改 bit 不用碰转子** —— 不用停机、拆罩、拆屏板去烧 Flash,
只换 DR1 文件系统里的文件。900 RPM 平台上这一条价值很高,
与 [[feedback_dr1_load_bit_without_jtag]] 同一个思路。

🎯 **建议: 屏板上留 SPI Flash 焊盘 + `M[1:0]` 跳线, 但不贴(DNP)。**
先走 DR1 加载; 万一上电时序或可靠性出问题, 贴一颗 Flash 改跳线就切回 MSPI。
**成本 = 几个焊盘 + 2 个跳线电阻位, 零 BOM。**

**⇒ DR1 侧总 IO(推荐档): 72 根差分信号 + 约 6 根单端 = 78 根**, 对板级 96 根余 18 根做地
(每対 0.5 根, ⚠ 偏少); 若走 800 Mbps 档则 56+6 = 62 根, 余 34 根地(每対 1.2 根, 舒服)。
🔴 **地够不够仍取决于 CEP1/CEP2 有没有专用 GND 脚 —— 这条待查, 见下节。**

### 🔴 由这份预算逼出的两条硬约束

**① ACK 必须做 mux, 不能 24 根直进。**
24 链头各一根 ACK 直进 = 24 根单端 ⇒ 总脚 **221 > 215, 超**。
经 8:1 mux 压到 6 根才放得下(与 [[reference_icnd2260_spec]] 的 "48 路 ACK 经 8:1 mux = 6" 同法)。
首期不做 ACK 回读则再省 6 根 —— 但 ACK 是"芯片活没活"最硬的判据
([[project_lxb_icnd2260_bringup]] 用它做首光判据), **不建议省**。

**② 那 18 対"真 LVDS 直驱屏"的共模要外部偏置。**
仿真対只有 54 个而下行数据要 72 対 ⇒ **必有 18 対走真 LVDS**, 而
EG4 真 LVDS 的 **VOCM = 0.6/—/1.4 V**(DS300 表 3-1-15, 典型值未给) 对屏要的 **VIC 1.1~1.3 V**
没有保证。⇒ **这 18 対要各加一组偏置电阻**(约几十只), 或整颗换 PH1A60GEG324(全真差分,
VOCM 典型 1.25 在窗内)。

### 仿真 LVDS 到底是什么 / 在本方案里干什么

**真 LVDS** = 芯片内有**专用电流模式驱动器**(约 3.5 mA 恒流源, 在接收端 100Ω 上得 350 mV 摆幅,
共模由芯片定)。占面积耗电, 所以厂商只在**部分 IO**上做(EG4 = **左/右两侧**)。

**仿真 LVDS(LVDS25_E)** = **没有那个驱动器**, 拿两个普通 LVCMOS 反相输出 + **外部 3 只电阻**
把 2.5V 大摆幅**衰减**到 LVDS 的几百 mV:
```
真 LVDS  : FPGA ─[电流源]─ P/N ─ 100Ω(片内端接) ─ RX      外部元件 0
仿真 LVDS: FPGA ─[LVCMOS]─ RS ─┬─ P/N ─ 100Ω ─ RX        每対 3 只电阻(RS×2 + RP)
                               RP
```
⚠ **"仿真"只在发送侧有意义** —— 作**输入**时两种脚都是真的差分接收器
(DS300: 真/仿真均可作 LVDS25 输入 800 Mbps), 只是仿真脚**没有片内 100Ω, 端接要外挂**。

### 🎯 在本方案里: **仿真対是把下行缺口补上的那半, 而它够用纯属屏侧速率低**

EG4S20CG324 只有 **50 対真**, 而下行到 24 颗 2260 要 **73 対** ⇒ **真対根本不够(50 < 73)**。
**是那 54 対仿真把缺口补上的。**

| 段 | 要求速率 | 仿真対(≤332 Mbps)干得了吗 |
|---|---|---|
| 上行 → DR1 | 600 Mbps | ❌ **必须真対** |
| 下行 → 2260 | **332 Mbps** | ✅ **正好够** |

⇒ 🔴 **整个 EG4 方案能成立, 全靠"屏侧只要 332 Mbps, 恰好落在仿真対能力之内"这一条。**
**若屏侧需要 400 Mbps, 仿真対全废, EG4 立刻出局**(50 対 < 73 対)。
这也正是 PH1A60 不需要仿真対的原因 —— 它有 100 対真的, 直接够。

### 仿真対的四项代价

| | |
|---|---|
| 元件 | **162 只电阻/桥**(54 × 3) |
| 速率 | 输出封顶 **166 MHz ≈ 332 Mbps**(真対是 400 MHz ≈ 800) |
| **功耗** | 🔴 **能量真的烧在电阻上**: 按 DS300 表 2-7-2 的 RS=150/RP=140 档,
每対约 **17 mW** ⇒ 54 対 ≈ **0.95 W/桥**, 双桥 **约 2 W**(真対 18 対只 ~70 mW)。**转子靠滑环供电, 这条要进功耗预算。** |
| 信号质量 | 边沿/EMI 不如电流模式驱动; 但**共模由外部网络设定 ⇒ 可控**, 反而是对屏 VIC 窗口的优势 |

### "屏是 170M 双沿, 332M 够吧" —— **够, 但余量只有 1.19×, 且要装下全部降额**

✅ **数字上确实吻合, 而且比想象的更贴**:
```
屏手册 tLVCP min = 6 ns  ⇒  1/6ns = 166.67 MHz  ⇒  双沿 333.3 Mbps
EG4 仿真 LVDS 输出上限   =   166.00 MHz          ⇒  双沿 332.0 Mbps
                                                    差 0.4%
```
(⚠ 屏手册另一处写"最大 170 MHz", 与 tLVCP 6ns **自相矛盾 2%** —— 这条早记在

```
每链能力 = 3 対 × 332 Mbps = 996 Mbps
每颗需求 = 1.3824 Mbps/片 × 605 片 = 836.4 Mbps
⇒ 占用 84.0%,  余量 = 996/836.4 = 1.19×
```

| 线速率 | 每链能力 | 占用(605 片) | |
|---|---|---|---|
| 332 (仿真上限) | 996 | **84.0%** | ✅ 但顶着规格跑 |

⇒ 🎯 **一句话对照: 同样 605 片/圈, 仿真対余量 1.19×, EG4 真対 2.9×, PH1A60 真対 4.5×。**
**"够"是真够, 但它是三者里唯一没有降额空间的那个。**

⇒ 🔴 **没有引脚表就画不了板。** 要用 GEG400 必须先向安路要**新版 DS1200 或 GEG400 引脚表**。

### ⚠ 连带一个未知数, 而且它正压在墙③上

**GEG400 能不能引出 32-bit DDR?** 芯片侧 DDR 专用 bank 支持 **8~32 bit**(DS1200 §2, 行 883-887),
但**位宽能不能全引出是封装的事**, 而手册里没有 GEG400 这一页。
而 32-bit DDR 正是把 2.13 GB/s 变成 4.26 的唯一办法([[reference_dr1_datasheet_draft_vs_v10]]:
"DDR 芯片支持 8~32bit 而两块开发板都只贴一颗 16bit ⇒ 换板子有用换芯片没用")。
⇒ **若 GEG400 只能出 16-bit DDR, 那省下的封装成本是拿墙③换的, 不划算。**
**这是问 FAE 的具体问题, 和 SERDES gearing 并列。**

### ⚠ 工作流代价: 没有 GEG400 的现成开发板

FS03 是 **GEG484**。选 GEG400 等于**从第一天起就得自制板**, 失去"先在 FS03 上把桥架构验通"这条路。
⇒ **合理排序: 先在 FS03(GEG484) 上验证桥架构与上行链路, 量产版再缩到 GEG400。**
反正上行只用 30-46 对, 两个封装都过, **验证结果可以平移**。

## ✅ 2026-09-01 交叉验证: 桥架构正是链路天花板那篇给出的出路 (c)

[[project_icnd2260_link_ceiling_and_clock]] 独立算出同一个数: **170 MHz 规格上限 = 340 Mbps/lane**
(与本文桥→屏用的 333-340 一致), 并列出突破 9000 fps 的三条出路:
**(a) 降线上位宽(手册没定义, 必须问厂家) / (b) 减像素或扫描行 / (c) 拆成多条并行链路**。
🎯 **本文的桥架构就是 (c)**, 而且它把 (c) 的代价(主控引脚爆炸)用串化解掉了 ——
两篇是从两个方向撞到同一个结论上的。

⚠ 顺带澄清一处容易混的: 本文"桥做 8→16 bit 扩展"**不依赖 (a)** ——
屏侧拿到的仍是合法的 16-bit, 8-bit 只存在于 **SoC→桥** 那一段。
⇒ **上行减半这个收益不用等厂家答复就能拿。**
