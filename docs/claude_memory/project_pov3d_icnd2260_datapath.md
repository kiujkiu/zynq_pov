上位: [[project_pov3d_hls_slicer_arch]] (切片器) / [[reference_icnd2260_spec]] (屏侧)。

## 🔴 一: 现在 WiFi 上跑的是**渲染好的切片**, 不是点云

`mlkpai_fs03` 的 PVS1 协议 (`stream/protocol.h`):
```c
#define PVS_MAGIC "PVS1"       // 16B 头 + zlib(打包好的切片位图)
raw_len = n_slices × 0x3000    // 360 片 = 4,423,680 B; 720 片双面 = 8,847,360 B
```
`povstream.py`: **PC 上 `gen_anime_slices` 渲染 → pack → zlib → TCP → 板子只解压+送屏**。
**板上完全不做几何。**

点云那条 (`PPCL` + `pov_project_batch` HLS) 在**另一个代码库 `zynq_pov`** 里,
不是板上跑的东西。⚠ 本对话中一度把两者混为一谈, 别再犯。

## 🔴 二: "点云 36 Mbps" 这个数偏乐观 4 倍

那是按 **3 万点**算的 (zynq_pov 的压缩流格式)。实际模型文件 (`point_t` 16 B/点):
```
zynq_pov/anime_points.bin   1,600,000 B = 100,000 点   范围 x[-30,30] y[-40,40] z[-20,20]
zynq_pov/globe_points.bin   2,063,104 B = 128,944 点   范围 ±60
```

### 占据体素实测 (voxelize 到 160×180×160 / 192×216×192)
| 模型 | 占据体素 | 点→格压缩 |
|---|---|---|
| anime (坐标只到 ±30, **没放大到填满屏**) | **19,939** | 5.02× |
| globe (±60) | **128,944** | 1.00× (每点独占一格) |

⚠ 半径预算是 79 px。按表面积 ∝ 尺度² 外推到满屏: anime ×6.9 → 138K,
globe ×1.73 → 223K ⇒ **满屏模型约 13-22 万占据体素** (外推值, 非实测)。

## 传输预算 (按 15 万体素 × 6 B/格 = u32 索引 + RGB565)

| 内容帧率 | 未压缩 | zlib+索引delta (估3×) | 现链路 20 Mbps | SDIO 200 Mbps |
|---|---|---|---|---|
| 30 Hz | 216 Mbps | ~108 | ❌ | ✅ |
| 10 Hz | 72 | ~36 | ❌ | ✅ |
| 5 Hz | 36 | ~18 | ⚠ 贴边 | ✅ |
| 2 Hz | 14 | ~7 | ✅ | ✅ |

⇒ **现链路 20 Mbps 只够 2-5 Hz 内容**。见 [[feedback_wifi_throughput_bottleneck_isolated]]。

## 🔴 三: 体素网格本身**不可能实时传**
9.2 MB (160×180×160) / 15.9 MB (192×216×192) 每帧 ⇒ 30Hz 要 2.2 / 3.8 Gbps。
**所以体素化必须在板上做**, 不能像切片那样 PC 算好推过来。

## 🔴 四: 反直觉 — 对现在这块 1-bit 屏, 传几何比传压缩切片**还贵**

```
现 PVS1:   720 片 × 0x3000 = 8.85 MB raw → zlib 33.7× → 262 KB/帧
传体素表:                                          450~900 KB/帧
```
1-bit 切片压得太好。⇒ **在现平台上换成"传点云 + 板上体素化"是倒退。**

几何路线只在 **ICND2260 目标**上划算:
```
目标切片: 603 片 × 2 面 × 82,944 B = 100 MB/体积帧 → 压 30× = 3.3 MB → 800 Mbps ❌
传体素表:                                                0.45~0.9 MB → 108~216 Mbps ✓
```
⇒ 几何省 **4-7 倍**, **这才是换架构的理由** (不是"点云更小"这种笼统说法)。

## ✅ 关键解耦: 内容帧率 ≠ 体帧率

屏必须 **30 Hz 体刷新**(防闪烁, = 900 RPM, 见 [[project_pov3d_final_target]]),
但**模型姿态**可以 5-10 Hz 更新 —— 人眼看旋转物体感知不到差别。
**这是唯一能让链路过关的手段**, 且完全是软件侧决定。

## ✅ 板上"体素化"其实只是 scatter, 不是真 voxelize

PC 端现有实现 (`gen_anime_slices.py`) 用 **180 万采样点 + ssaa=3 覆盖率**做抗锯齿,
把覆盖率折进体素颜色 (`acc/cnt` 平均 + 边缘按覆盖率调暗)。

⇒ **PC 保留采样与抗锯齿, 只把结果的"占据体素表 (索引+RGB565)"发过来**;
板上只需把表 scatter 进网格。抗锯齿信息已经编码在颜色里, 不丢。
⇒ 板上那一步是 **~15 万次散写 + 清上一帧的脏格**, 不是三角形采样。ARM 就能干。

⚠ 清网格别整块 memset (15.9 MB × 30Hz = 477 MB/s) —— 留上一帧的索引表,
只清那 15 万格 (60 KB/帧), 便宜 265 倍。

## 三个要分开验的东西 (一次隔离一个变量)
1. **切片器几何** ✅ 已过 (csim 对拍逐位相同, 见 [[project_pov3d_hls_slicer_arch]])
2. **上板成像** — 一次性推 9.2 MB 静态体素 + 板上 `phase++` 转, 绕开链路与 scatter
3. **scatter + 链路** — 最后接上, 也是最硬的一环
