## 🔴 先定口径 (这一点反复搞混过)

```
体帧率 = 2 × 转速          (穿轴屏转半圈遍历所有平面方向)
内容帧率 ≤ 转速            (一圈只能翻一次页)

⇒ 体帧率 30Hz 只需 **900 RPM (15 rps)**, 内容帧率上限 = **15 fps**
```
🔴 **900 RPM 就达标, 不需要 1800。** 我一度建议 1800 RPM —— 那**只是为了给翻页那一级凑 2× 余量**,
不是达标需要。用户明确: **只能 900 RPM, 再高振动太大。**

⚠ 两个面**由同一次翻页更新** (一帧载荷同时含面A+面B 的切片), 不是两条独立 15Hz 流水线。

## 🔴 翻页 1.0× 的真因是**相位没锁**, 不是转速不够

`dec+cpy = 48 ms < 66.7 ms` **本来就够**。问题是解码启动相位相对转子随机漂移:

| 情况 | 结果 |
|---|---|
| 完成相位**对准**窗口 | 48 干活 + 18.7 等 = 66.7 ✅ 每圈翻中 |
| 相位**随机** | 48 + 平均等半圈 33 = 81 > 66.7 ❌ 两圈一帧 → **7.5 fps** |

**没有中间态: 翻中就 15 fps, 翻不中直接掉一半。** 实测 16.1 rps 下只翻中 ~2/3 窗口。

⇒ **解法是翻页后立刻开始解下一帧** (相位锁定), 纯软件。
⚠ 这同时解释了长期没查清的 "`wait` 平均 31 ms 为何没被 `window=2` 重叠掉" ——
**window 管的是在途帧数, 不管解码启动相位。**

## 🔴 面板 0.88× — 本轮才浮出来的一级, 之前的余量表里根本没有它

### 🎯 2026-08-10 板上实测定案: 面板一级是 **0.247×**, 每圈只显示 **89** 片

实测 2D 刷新 **1335 Hz**(不是 4748, 也不是按模型重算的 2393), 见
[[project_pov3d_refresh_vs_rpm]] §08-10 实测。

| | 账上写过 | 模型重算 | **实测** |
|---|---|---|---|
| 2D 刷新 | 4748 Hz | 2393 Hz | **1335 Hz** |
| 每圈显示切片 @15rps | 316 | 160 | **89** |
| 面板级余量 | 0.88× | 0.44× | **0.247×** |
| 有效角分辨率 | 1.14° | 2.26° | **4.04°** |

🔴 **现在渲的 360 片里有 3/4 根本没机会上屏**, 链路/解码/memcpy 为它们付的代价全白付。

🔴 **面板这级"不满足"与别的级不是一回事**:
- 别的级不满足 ⇒ **掉帧率**(内容 fps 下降)
- 面板不满足 ⇒ **掉角分辨率**, 帧率不受影响

内容仍是 15 fps 在更新, 只是每圈画得出 89 个角度而非 360。**这不是"通信速率不够",
是显示端画不过来** —— 链路那边其实在超量供货。

⇒ **立刻可做且零风险**: 把 `n_slices` 从 360 降到面板真能显示的量级,
链路/解码/memcpy 全线成比例减负, **画面质量一点不损失**(那些片本来就没上屏)。

⚠ 但"降级是 bit29 造成的"仍是**推断不是实测** —— 实测行周期比 RTL 模型长 1.79×,
模型已经错过一次。别在没做"翻 bit29 再测"那个对照实验之前, 把 2× 收益当成已知。

### ⚠ 2026-08-10 早些时候的模型重算 (已被上面的实测取代): 不是 0.88×, 是 0.44×

`pov_boot.sh:38` 的 bit29=1 ⇒ `ddr_slow=1` ⇒ 面板刷新其实是 **2393 Hz 不是 4748**
(位语义反转, 见 [[feedback_reg_bit_semantics_reversed]] / [[project_pov3d_refresh_vs_rpm]])。

| | 本节原写 | 实际 |
|---|---|---|
| 面板刷新 | 4748 Hz | **2393 Hz** |
| 每圈显示切片 @15rps | 316 | **160** |
| 面板级余量 | 0.88× | **0.44×** |
| 有效角分辨率 | 1.14° | **2.26°** |

⇒ 下文"要 360 片/圈需 1.14×"实际是 **2.26×**;
但 **翻 `B8→98` 一个字符就能拿回 2.0×**(占空比守恒 ⇒ 亮度不变, DDR 带宽也不变),
之后面板级从 0.44× 回到 0.88×。**这是全表里最便宜的一级。**
🔴 前提: 07-27 换 trans_v12 引脚图后 50 Mbps 没有点屏记录, 翻之前必须重测 SI。

⇒ 也意味着**现在渲 360 片是多传了 2.25× 的数据**(改 fast 后 1.14×)。
把 `n_slices` 匹配到面板真实能力, 链路/解码/memcpy 全线成比例减负 ——
`dec+cpy` 那个 1.39× 的余量能直接翻倍。

```
面板刷新 4748 Hz (oe=111, 已是免费亮度上限, 见 project_pov3d_refresh_vs_rpm)
900 RPM = 15 rps
⇒ 每圈能显示的**不同**切片 = 4748/15 = 316 片   而现在渲 360 片
```
**渲多少片都一样, 每圈只显示得了 316** —— 有效角分辨率被**面板刷新率**锁死在 1.14°,
不是被切片数锁死。

### 因此"多切片提角分辨率"在现平台上收益为零
用户提过一个正确的观察: 360 片 = 每片 1°, 转子真实角度与最近切片有 **±0.5° 量化误差**
(最外圈 75mm 处 = ±0.65mm ≈ ±0.7 像素); 切 720 片降到 ±0.25°。
**逻辑成立, 拐点也正好是我们算过的像素匹配数** (503 片/圈 @160px 屏 / 603 @192px 屏,
见 [[project_pov3d_final_target]])。

🔴 **但 900 RPM 下面板只显示 316 片, 切 360/503/720 有效角分辨率全是 1.14°**,
多切的部分根本没机会上屏, 而数据量/解码/链路的代价是实打实翻倍的。
```
要显示 720 片/圈 @15rps ⇒ 面板需 10,800 Hz = 现在的 2.3×
要显示 360 片/圈 @15rps ⇒ 面板需  5,400 Hz = 现在的 1.14×   ← 最小的一步
```
⇒ **想要更细角分辨率, 该投的是面板刷新率, 不是切片数。**

## 下一步优先级 (2026-08-05 定, ⚠ 第 1 条已被 08-06 结果取代)

1. ~~**相位锁定**~~ ❌ **前提是错的, 别再投时间** ([[feedback_phase_lock_premise_wrong]])。
   15fps@900RPM 是靠**修收包**拿到的 ([[feedback_recv_setsockopt_rcvbuf_lock]])。
   ⇒ 现在的第 1 优先级是 **flip 线程的 cpy 26.1 ms**(原第 3 条)
2. **面板刷新 4748 → 5400 Hz** —— 让渲的 360 片能完整显示 (PL 扫描拓扑)
3. **干掉 20 ms memcpy** —— dec+cpy 1.39× → ~2× (双核并行拷 / PL330 DMA / 三缓冲流水)
4. ICND2260 主线 (scatter 内核 / 屏驱 RTL)

⚠ **1-3 全是现平台(PVS1 切片流)的优化, 而 ICND2260 目标架构根本不传切片。**
投不投这些时间取决于是先把现有这套做到位, 还是直接推新架构。
