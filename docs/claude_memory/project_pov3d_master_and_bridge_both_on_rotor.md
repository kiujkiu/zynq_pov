# 主 FPGA 与桥片 FPGA 都在转子端 (2026-09-07 用户澄清)

## 🔴 更正的对象

`HW_SPEC_2026-09-04.html` 里写的是"主控 → 每面 20 対差分 + 配置线, **排线, 上转子**",
隐含**主控在固定侧**。**这是错的 —— 主控也在转子上。**
[[project_pov3d_bridge_architecture]] 里"桥→屏…上转子 / 主控→桥 一根排线"的表述同样含糊, 已就地标注。

## 后果一: 跨旋转界面的只剩电源

上行(主控→桥片)是**转子上的板对板链路**, 短、可用正规连接器、可控阻抗 ⇒ 800 Mbps 反而更容易。
跨界面的只有: **电源(滑环)** + 光电索引(非接触) + WiFi(非接触, 但天线在转子上转)。

⇒ **滑环要过 2260 阵列 43 A(规格上限) + 主控板 + 2 颗桥片。转子供电这个空白的重要性升级**,
因为它现在是**唯一的电气跨界**。(记忆库里关于转子供电仍是一个字都没有。)

## 后果二: 主↔从 FPGA 压缩的最大理由没了 ⇒ 压缩暂不做

原本把"**穿过转子的线更少**"列为压缩的第一价值 —— **不成立**, 那些线不跨界面。
剩下的价值只有"BG256 上做 12-bit(93 対 → 压缩后可能 ≤88)"和"时序余量"
(已 SWNS +0.106 收敛, 不缺)。

⇒ **结论: 压缩暂时不做**, 纯优化项且要动有实测背书的 slicer IP。

✅ 但"**不发填充**"那 10% 还是要做: 4×6 排布下 6 颗覆盖 240 而真实 216,
**46,080 → 41,472 px**, 链路占用 **96.2% → 86.6%**, 零解码代价。

📌 压缩的技术结论留档(将来要做时直接用): 内容占用率仅 **1.7%**
(bonsai 13.6 万体素 / 800 万格), 一片约 700 个亮点 ⇒ 稀疏表 28 kbit vs 全光栅 995 kbit = **35×**;
**关键是按 2260 扫描顺序发**(slicer 的 `slot[px][py]` 正好是列优先 = 2260 要的顺序),
那样桥片只需小 FIFO 填黑, 不需要帧缓存
(EG4A20 只有 1,088 kbit BRAM, 双缓冲 1,326 kbit 装不下)。

## 后果三: 🔴 主控板要扛 68~136 g 离心 (之前完全没考虑)

- **USB WiFi dongle** —— USB 连接器靠摩擦力固定, 136 g 下会不会脱? 多半要灌胶或改焊接式模块
- **FS03 是核心板**, 板对板连接器(0.5mm B2B)**不是按这个加速度设计的**
  ⇒ **可能直接否掉 FS03 方案**, 或要求加固定螺柱 + 灌胶
- DDR 颗粒、大电容、晶振都要按 136 g 校核

## 后果四: 质量与动平衡

现状**限速 ≤850 RPM 而目标 900**, 动平衡已是瓶颈。主控板(含 DDR/屏蔽罩/连接器)再挂上去,
质量与不平衡量都增加。**放哪儿?** 放轴心则到两面屏板走线对称, 也利于平衡。
