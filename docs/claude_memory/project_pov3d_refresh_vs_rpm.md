# 🎯 2026-08-20 结案: 本文 08-10 那一整轮结论(1335 Hz / 2393 Hz / bit29 降级)**全部作废**

**因为本文自己在"待改"一节要的那个寄存器做出来了。** commit `ff003fd`(08-20)
把 `panel_engine_2047.v` 的 `frame_period_o` **引出到 `R 0x28`** ——
刷新率从此是**寄存器直读**, 不再需要示波器/探针/仿真模型。

**读数**(`docs/design_icnd2047/05_3bit_bcm.md:167`): `R 0x28` = **10530 拍**(1-bit) →
**31590 拍**(3-bit), **精确 3.00×**, 且运行时可来回切。

`10530 拍 = 195 × 54`, **正是本文下面那张仿真表里 fast + oe≤111 的 195 拍行周期。**
@50 MHz ⇒ 210.6 µs ⇒ **2D 刷新 4748 Hz**。

| | 本文写过 | 结局 |
|---|---|---|
| 4748 Hz (最早的账 + 仿真表) | "不是现役数字" | ✅ **它才是对的** |
| 2393 Hz (08-10 按 bit29=slow 重算) | 曾当作正解 | ❌ 作废 |
| 1335 Hz (08-10 板上 oeprobe 实测) | 曾判为"唯一可信" | ❌ 作废 |

**两条支撑**:
1. **bit29 已在 08-20 翻成 fast 并上板验证通过**(commit `ac4948e`, 实测 **2.07×**)
   ⇒ 降级模式不再是现役状态。移植到 DR1 时**显式写死 `bit29 = 0`**。
2. **aclk 确认是 50 MHz**(不是 25)。08-20 一度误判成 25 并写进过文档, 08-25 两条独立证据
   坐实 50: `rev_period 4522362 ÷ 11.06 rev/s`、`CYCLES 3.69M ÷ 74ms`(commit `7efe755`)。

⚠ **08-10 那两个探针数(行 13.87 µs / 斜率 3.83)至今没有复盘。**
最可能的解释【推断, 没人重跑过】: **同一个 oeprobe 欠采样问题** ——
[[project_pov3d_3bit_color]] 记着同一支探针因"采样 0.5 µs 而 plane 周期 3.9 µs,
每周期才 7~8 个点, 漏沿漏掉近一半"把 aclk 算成 26 MHz;
而 4748 Hz 下行周期正是 **3.9 µs**, 落在同一个欠采样区间。
**漏沿只会把周期测长, 不会测短** —— 方向也对得上。
⇒ 教训: **间接探针在采样率不足时给出的是"看起来很实"的错数**, 而它当时还压过了仿真和账面。
真正终结争议的是**把量直接引成寄存器**([[feedback_verdict_design_before_blaming_dut]] 同源)。

## 现役刷新率 (2026-08-25)

| 配置 | 整屏拍数 | @50 MHz | 2D 刷新 |
|---|---|---|---|
| 1-bit 全屏 | 10530 | 210.6 µs | **4748 Hz** |
| **3-bit 全屏 (现役)** | **31590** | **631.8 µs** | **1583 Hz** |
| 3-bit half_scan | 16038 | 320.8 µs | 3117 Hz 【推算, 未实测】 |

🔴 **一个新的、没人算过的账**【推算, 未上板验证】: 现役 969 RPM = **16.15 rev/s**
⇒ 每圈只画得出 `1583 / 16.15 ≈ 98` 个角度, **而配置是 142 槽/面**。
(142 对应 08-25 早些时候的 11.06 rev/s: `1583/11.06 ≈ 143`, 精确吻合。)
⇒ 提速到 969 RPM 之后, **142 槽里可能有约 1/3 没机会上屏**。
不影响帧率(面板不满足只掉角分辨率), 但影响"该渲多少片" ——
对 DR1 意义更大(载荷直接按比例减), 见 [[project_pov3d_nslices_match_panel]] / [[project_dr1_parity_plan]]。

## ~~🔴 2026-08-10 重大修正: **4748 Hz 不是现役数字**, 现役大概率是 2393 Hz~~

下文所有数字的**前提是 `ddr_slow=0`(全速 50 Mbps)**, 而 `pov_boot.sh:38` 写的
`0xB8366F01` **bit29=1 ⇒ ddr_slow=1 ⇒ 25 Mbps 降级**。⇒ 现役 = slow+oe111 = **2393 Hz**。

**成因是位语义反转, 不是手误** (详见 [[feedback_reg_bit_semantics_reversed]]):
v5 RTL 里 bit29 = `dclk_fast`(1=全速, 当时写对了); 07-14/15 换 2047 双沿核后同一位
反转成 `ddr_slow`(1=降级), 而 `pov_boot.sh` 此后被改过三次都原样带着 `B8`。

| | 下文写的 | 实际(slow, oe=111) |
|---|---|---|
| 行周期 | 195 拍 | **387 拍** |
| 整屏 | 210.6 µs | **418.0 µs** |
| 2D 刷新 | 4748 Hz | **2393 Hz** |
| 967RPM 每片扫描 | 0.81 遍 | **0.41 遍** |
| 08-03 那次 oe 优化收益 | +39% | **+18.3%** |

🔴 **`oe=111` 这个"免费亮度上限"在 slow 下也是错的**: slow 的免费上限是 `2·oe ≤ 303`
⇒ **oe ≤ 151**。现在等于刷新率没拿到, 还白扔了 40 个沿的亮度。

**行周期通式**: `fast: 195 + max(0, oe−111)` / `slow: 387 + max(0, 2·oe−303)`。

## 🎯 2026-08-10 板上实测: bit29=1 坐实, 但**实测刷新是 1335 Hz**, 模型也不对

FS03 上电后跑只读探针 (`/dev/mem` O_RDONLY + PROT_READ, 不写任何寄存器):

| 证据 | 结果 |
|---|---|
| A 板上 `/home/uisrc/pov_boot.sh:38` | `pw(0x0C, 0xB8366F01)` ⇒ **配的就是 slow**。开机日志 `=== pov_boot v5` 确认跑的是它 —— 关掉了"板上脚本≠仓库脚本"这个口子 |
| B `devmem 0x40010000` | `0x00011AF1`, **bit7 ddr_slow = 1** ⇒ **降级模式坐实**。同读 `0x24` = `0x01680005`, `n_slices=360` 解码正确 ⇒ 板上 bit 确实是 08-01 之后那版, bit7 语义成立 |
| C OE 行节拍 | **row 13.87 µs / OE低 7.96 µs / 占空比 0.574 / 2D = 1335 Hz** |

**占空比精确吻合 oe=111**: 理论 slow 是 222/387 = **0.5736**, 实测 **0.574**
(fast+oe111 是 0.5692) ⇒ oe=111 确认, 且占空比这一项**偏向 slow**。

🔴 **但绝对行周期比模型长 1.79× (13.87 µs vs 模型 7.74 µs), 四个候选全对不上。**
- 两个独立仪器一致: Python 版(dt=1.70 µs)测 13.58, C 版(dt=0.47 µs, **29.5 样本/行**)测 13.87
  ⇒ **测量可信, 是模型错了。**
- `create_panel_proj_v6.tcl:60` `PCW_FPGA0_PERIPHERAL_FREQMHZ {50}` ⇒ aclk 配的是 50 MHz。
- 13.87 µs × 50 MHz = **693 aclk**, 而 slow+oe111 模型是 387。差 306 拍, 无法用 oe 解释
  (oe 箝位 187 ⇒ slow 最大行周期 458 拍)。
- 模型出自 `sim/tb_2047_core.v` —— **只测了核, 没测集成系统**(双引擎 + fetch + 实际 fb 通路)。

⇒ **三个数里, 唯一可信的是实测的 1335 Hz。** 4748(账上) 和 2393(agent 2 按模型重算) 都别再用。
⇒ 面板一级余量比重算的 0.44× **还要差**: 每圈只显示 1335/15 = **89 片** (渲 360)。

## 🎯 oe 扫描: 不碰 bit29 也能测出它的效果 —— 结果是**还有一个 ~1.9× 没人知道**

**方法**(`mlkpai_fs03/tools/oe_sweep.sh`): `ddr_slow` 的作用就是把 OE 窗从 `oe` 拍变成
`2·oe` 拍(`icnd2047_panel_core.v:97`)。⇒ **扫 oe 看 OE 低宽的斜率**: 2 = slow 生效, 1 = fast。
**改 oe 只动亮度不动链路速率**, 风险远低于把 50 Mbps 打到屏上, 所以不必翻 bit29。

| oe | OE低(拍) | 行(拍) | 2D(Hz) |
|---|---|---|---|
| 80 | 285.0 | 690.0 | 1342 |
| 95 | 329.5 | 671.5 | 1379 |
| 110 | 392.0 | 690.0 | 1342 |
| 125 | 455.5 | 705.0 | 1313 |

最小二乘: **OE低 ≈ 3.83·oe − 27**。

🔴 **模型说 slow 的斜率应该是 2, 实测 3.83 ≈ 2 × 1.9。**
而绝对行周期那边的偏差是 1.79×。**两处独立测量给出同一个 ~1.9× 的时间膨胀**
⇒ **bit29 最多解释 2×, 另外还有一个 ~1.9× 完全不在模型里。**

已排除的解释:
- **时钟**: 三重确认 50 MHz —— SLCR `FPGA0_CLK_CTRL=0x00400500`(IO PLL 1000/5/4) +
  tcl 请求值 + **实现后 `system_wrapper_clock_utilization_routed.rpt`: 单时钟
  `clk_fpga_0` period 20.000 ns, 3062 slice loads**(全设计一个时钟域)。
- **`q_gap`**(`icnd2047_panel_core.v:132` = `row_cfg[30:25]`, 6 位 ≤63, 每行加 2×):
  最多 126 拍, 解释不了 306 拍, 且**根本不影响 OE 低宽**。
- **OE 计数被 tick 门控**: `:223` 明写「与 FSM 解耦; **单位=拍**」, 不受 `tick` 影响。
- **BCM/位平面**: FSM 是 `IDLE→FETCH→LOAD→SHIFT→LWAIT→DISP`, **一行一个 OE**, 没有位平面。

⚠ 剩余嫌疑(未验证): `disp_ready = oe_done && adv_fired && !rd_busy && !row_go_r` 里的
**`rd_busy`(行驱动 `row_drv_icnd1028` 推进耗时)** —— 核的 tb 很可能把它 stub 掉了;
以及 `dual_en=1` 时两个引擎争用共享资源。
🔴 **`eg_state_o` 在 `panel_engine_2047.v:94` 是悬空的** ⇒ 看不到拍花在哪个状态。
这是这个设计里**第三个"规划了没接出来的观测口"**(另两个: `frame_period_o`、`0x20`)。

## 另外两条直接可用的结论

1. **调 oe 换不来刷新率**: oe 80→125 行周期基本不变(690±15), 2D 钉在 **~1340 Hz**。
   ⇒ 面板那 0.247× 的缺口, **靠调 oe 补不了**。
2. **免费亮度上限实测 ≈ 125 而不是 111**: 行周期到 oe=125 才开始抬头(705)。
   现役 111 已接近最优, 但还有一点白扔的亮度。

**仍未做的决定性实验**: 翻 bit29 后重扫 oe —— 斜率若从 3.83 掉到 ~1.9 就同时证明
"ddr_slow 生效且是 2×"与"另有 1.9× 膨胀"。
🔴 那是**把链路速率翻倍**, 属 SI 风险(07-27 换 trans_v12 引脚图后 fast 没有点屏记录)。

## 🔴 结论一: overlap 是架构固有, oe≤111 免费

`oe ≤ 111` 时行周期恒 195 拍 —— **OE 显示窗完全藏在下一行的 192 拍移位里**,
一拍不多花。这就是 overlap (靠 ICND2047 内置双缓存)。超过 111 才插 LWAIT 等待拍。
⇒ **111 是免费亮度上限**; 当前跑 187 = 用 **39% 刷新率**换那 68 沿额外亮度。

## 🔴 结论二: 当前转速下无论 oe 取多少都扫不满

```
每片预算 (16.22 rps) = 171.3 µs
最快扫描 (oe≤96)     = 210.6 µs   → 最好也只有 0.81 遍
当前 (oe=187)                     → 0.59 遍, 41% 的行根本没显示
```
要扫满一遍, 转速须降到: **oe≤96 → 13.19 rps 以下** / oe=187 → 9.49 rps 以下。

设计文档按 13 rps / 213.7 µs 定预算, **正卡在 oe≤96 那条线上 —— 文档是对的, 是实际转速跑超了**。
体积帧率 = 2×转速, 13.19 rps 已对应 26.4 fps (达标) ⇒ **再加转速无收益, 反而丢行**。

## ✅ 2026-08-03 定案: oe_window 187 → **111**, 已固化

**111 才是免费亮度上限, 不是 96** —— `LWAIT = max(0, oe-111)`, 所以 `oe≤111` 行周期
恒 195 拍。之前打算用的 96 白扔了 15 个沿的亮度, 刷新率一点没多拿。

| | oe=187 (旧) | **oe=111 (现)** |
|---|---|---|
| 行周期 | 271 拍 (含 76 拍 LWAIT) | **195 拍** |
| 整屏扫描 | 292.7 µs | **210.6 µs** |
| **2D 刷新率** | 3417 Hz | **4748 Hz (+39%)** |
| 967RPM 每片扫描 | 0.58 遍 (42% 行不显示) | **0.81 遍** (19% 不显示) |
| LED 电流 | 基准 | **约 −29%** (给 5V 轨让余量) |

**寄存器写法** (`0x0C` subcmd=`2'b10` + `cfg_we`(bit27), `oe_window` 在 **[15:8]**):
```
pw(0x0C, 0x000001FF)   # sdi_mask
pw(0x0C, 0xB8366F01)   # [15:8]=0x6F=111, [24:16]=54 行, bit29 dclk_fast, bit28 overlap
pw(0x0C, 0xC1000003)   # auto_en + use_fb
```
旧值 `0xB836C001` ([15:8]=0xC0=192, 引擎内部箝位到 187)。已写进 `pov_boot.sh`。

### 4748 Hz 是当前架构天花板
卡在每行 **192 拍移位 = 1728 列 ÷ 9 lane @50MHz aclk**。再上只有两条路:
提 aclk (受 ICND2049 FCLK 25MHz 上限约束, 要重核分频) 或 加 lane 数
(9→18 → 9500 Hz, 但要多 9 个 PL IO + 改屏侧接线)。**都不是软件能解决的。**
