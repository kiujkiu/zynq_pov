## 🔴 物理真相 (这才是该记住的, 不是那三个数)

由数值验证过的恒等式 (6/6, 且不加镜像时 0/6):
```
render(θ, −d, mirror_u) ≡ mirror( render(θ+180, +d, mirror_u) )
```
⇒ `PHASE_B=180 + mirror_b=0` 等价于 **面B 垂距取负 且 手性相对面A 翻转**。

**为什么两个同时翻**: 面A 从 −X 侧看、**面B 从 +X 侧看** —— 观察方向相反会**同时**
翻转 (a) 偏移量相对 n̂(θ) 的符号 (b) 左右手性。我最初把面B 按"跟面A 同一套约定 +13.4"
渲, 两个都错, 恰好被这个寄存器组合补偿回来。

⇒ **渲染侧的根治办法**: 面B 应渲成 `axis_off = −13.4mm` **且** `mirror_u` 相对面A 取反。
那样 `PHASE_B=0 / mirror_b=0` 就原生正确, 不需要任何寄存器补偿。**代码未改, 见下方待办。**

## ✅ 已固化 (原来是手工 devmem 写的, 一重连就丢)

`PHASE_B=180` 现在写死在两处, 不再依赖手工操作:
- `pov_rxd.c` 的 **`PHASE_B_DUAL` 常量** (DUAL_FACE 帧用它, 原来硬编码 0)
- `pov_boot.sh` 的 `pw(0x1C, 180)` (冷启动即正确)

🔴 **同源事故 (机制仍在, 值得记住)**: `PHASE_B` 是**只写**寄存器, `pov_rxd` 靠内部
影子跟踪且"影子==目标就短路不写"。2026-08-03 我手动 `devmem 0x1C 180` 装 anime 后,
再推双面流时 pov_rxd 认为"影子已是 0"而不写 → **硬件 180 / 软件以为 0** → 屏B 内容
整整转了 180°, 现象是**两屏显示两个不同的 3D 体**, 查了很久。
⇒ **只写寄存器 + 影子跟踪 + 外部手动改写 = 静默不一致。** 以后要么别手动碰,
要么改完同步通知持有影子的进程 (重启它最省事)。
(`POV_CTRL` 有 `R 0x24` 影子回读可避免此类问题, `PHASE_B` 没有对应读口。)

## 排错时用得上的判据

| 现象 | 病因 | 改哪 |
|---|---|---|
| 两个体, 各绕各的中心 | 面B 偏移符号错 | `PHASE_B` 翻 |
| 形状对但左右反 | 手性错 | 对应的 `mirror_a/b` 翻 |
| 一面正常一面异常 | 只有一面的配置错 | 只动那一面 |
| 转向相反 | 🔴 θ 方向错 | **必须重渲** (`θ→−θ`), 翻镜像救不了 |
| 糊成一团 | `locked=0` 没锁相 | 提转速 |

⚠ `--swap-faces`(我加在 pov_rxd 上的调试开关) **对 `FOLD_A` 帧无效** ——
`fold_a_en` 是引擎A 专属, 换过去引擎A 会拿 360 片数据做半圈折叠。要对调必须渲 720 片。

## 📊 顺带实测到的链路真值 (决定路线的关键数)

⚠ **作废**: 那个 28 是 `DEFAULT_LINK_MBPS` 硬编码常量, 不是实测。2026-08-04 实测真值 **~20 Mbps**, 见 [[feedback_wifi_throughput_bottleneck_isolated]]。

| 目标 | 需要 | 28 Mbps 够不够 |
|---|---|---|
| 720 片双面 @30fps | 63 Mbps | ❌ 差 2.2× |
| 540 片折叠 @30fps | 47 Mbps | ❌ 差 1.7× |
| **720 片双面 @13 fps** | 28 Mbps | 刚好吃满 = **现有链路天花板** |

⇒ **双面路线在现链路上上限约 13 fps**, 跟解码/FPGA 都无关, 瓶颈纯在无线。
板端双核并行解码实测 `dec_avg≈78-88ms` (8.85MB → 约 110 MB/s), 不是瓶颈。

## 空闲动画: 上电就有画面, 有推就显示推的 (2026-08-03 实现)

`pov_rxd --idle-anim /home/uisrc/anim.pvs --idle-fps 8`:
无客户端时由 pov_rxd 自己按 `poll` 超时逐帧播预压缩容器, 有连接自然让位
(`accept` 前先 poll, 超时才播一帧)。**单进程独占 DDR**, 无端口争抢。
容器用 `tools/make_idle_anim.py` 生成 (36MB/120帧, 已 gitignore, 随时可重生成)。

实测 **rx=54 flip=54 drop=0** —— 本地播放节奏与翻页窗匹配, **零丢帧**;
对比网络推流因速率与翻页窗不匹配丢 48-85%。

### 🔴 三个真实踩过的坑

1. **`face_job_t.codec` 存的是协议 flag 位** (`PVS_FLAG_ZLIB = 1<<1 = 2`),
   按"1 = 第一种编解码器"的直觉写 `codec=1` 正好命中 `PVS_FLAG_RLE`
   ⇒ 每帧 `RLE decode failed` 静默 return, **日志一个字都没有**,
   表现为"容器加载成功但一帧不播"。**在 x86 sim 上加三行打印 10 秒定位**,
   比在板上盲试快一个数量级 —— 这类问题一律先下 x86。
2. **容器载荷必须是 PVS1 线上 payload 原样**。DUAL_FACE 要求
   `[u32 comp_len_A][zlib 面A][zlib 面B]` **两条独立流**; 我图省事
   `zlib.compress(整帧)` 压成一条 → 板端读到垃圾 `clen_a` → 静默丢帧。
3. **`pov_boot.sh` 与 `povrxd.service` 都在起 pov_rxd** → 抢 9500 端口,
   service 无限重启 (`NRestarts=191`), 但状态是 **`activating` 而非 `failed`**,
   日志只有一行 `bind: Address already in use`, 不查重启次数根本发现不了。
   ⇒ 已从 boot 脚本移除, 统一 systemd 托管。
