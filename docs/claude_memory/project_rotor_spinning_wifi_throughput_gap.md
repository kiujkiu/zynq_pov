# 待办: 转子旋转状态下的 WiFi 吞吐测量 (2026-09-17 立项)

## 为什么这是个空白, 而不是"应该差不多"
**所有已有的 WiFi 吞吐数都是静态测的**, 条件是: 天线静止、**信号 -30 dBm(基本贴着)**、专用点对点 AP、
信道 48 上**零其他流量**。具体: DR1V90 原版 91.7 / 打补丁 136 / UDP 裸收 ~130;
DR1M90 原版 **≥158**(台架顶, CPU 还余 33%); 同板有线 **941**。
⇒ **这些是上界, 不是产品数。**

🔴 **旋转天线的周期性衰落不是猜测, 是本项目已经独立判定过的效应**:
[[reference_dr1_board_naming_verdict]] / `dr1v90/docs/BOARD_NAMING.md` §4 当初判死"按名字找板子"那套
mDNS/广播方案, 其中**单独就够判死的一条理由**正是:
"名字查找跑在**无 ACK、无重传的 802.11 组播**上, 而 povsh 跑在**有 ARQ 的单播**上
⇒ 旋转天线的周期性衰落会让**『名字』比『连接』更容易断**"。
⇒ 既然当时认定旋转会显著改变链路可靠性, 就不能假设它不改变吞吐。

## 旋转会引入的几个机制 (待实测量化, 目前全无数据)
1. **周期性衰落**: 极化失配、天线方向图、结构件遮挡都随转角变化 ⇒ 每转一圈信号起伏一次(或多次)。
   对 TCP 的危害不只是平均信噪比下降, 还有**速率自适应来回切档 + 重传**, 二者都吃吞吐。
2. **转速相关**: 现役目标 900 RPM = 15 转/秒 ⇒ 衰落周期约 67 ms, 与 TCP 的 RTT/拥塞窗口时间尺度**同量级**
   ⇒ 可能落在最难受的频率上(比慢衰落更伤, 因为拥塞控制来不及收敛)。
3. **无线供电的辐射噪声**: 转子供电是**无线供电 48 W**([[project_pov3d_rotor_wireless_power]]), 开关电源在同一空间工作,
   噪声可能落在 2.4/5 GHz 附近或其谐波上。静态台架上这个源**没有开**。
4. **天线安装**: 转子上金属/碳纤结构件、屏体本身都会改变方向图; 现在连天线放哪都还没定。

## 为什么必须早做
吞吐直接决定内容预算(分档 / 帧率 / 片数 / 编码 / 传几何那一整套, 见 [[project_wifi_300m_target]] 的载荷规划)。
**若旋转吃掉 30~50%, 那么 280 的静态上限在产品里就是 140~200** —— 会推翻现在按静态数做的所有载荷规划。
⇒ 这个数越早拿到, 返工越小。

## 怎么测 (建议口径)
- **先静态后旋转, 同一套工具同一个口径**, 只把"转/不转"作为唯一变量(否则分不清是旋转还是别的)。
  工具: `ksink`(带真实接收负载) + `iperf3`, 都已在卡上; 判据见 `measure/03_wifibw/board/ksinkbw.sh`。
- **转速要扫**: 至少 0 / 300 / 600 / 900 RPM 四档 —— 因为机制 2 说明这可能不是单调的。
- **不要只看平均吞吐**: 必须同时记 **每秒吞吐曲线**(看有没有转速同频的周期性凹陷)、
  `iw dev wlan0 station dump` 的 **tx retries / tx failed / rx bitrate 变化**、以及 TCP 重传数。
  只报一个平均值会把"周期性深凹"和"整体略降"混成同一个数。
- **无线供电要分别开/关各测一组**, 把它的噪声贡献单独摘出来。
- 🔴 **上转子前必须先把板子的供电问题解决**(见 [[project_dr1m90_wifi_retest]]): 现在射频上电就约 50% 概率复位,
  上了转子没法插串口也没法插网线, **失去一切调试手段**; `dr1v90/docs/BOARD_NAMING.md` 已经记过
  "必须在板子还能插串口的时候做完, 上了转子就没有第二次机会"。

**Why:** 静态台架数和产品数之间隔着"旋转"这一跳, 而本项目已独立认定旋转会显著改变链路; 载荷规划全建在静态数上。
**How to apply:** 报 WiFi 吞吐时必须注明"静态/贴着/独占空口"; 谈产品可行性前先补这组旋转实测。
