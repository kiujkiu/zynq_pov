## 为什么现架构做不到 (输入全是实测, 结论是推算)
按 TCP 有效载荷持续 300 Mbps = 37.5 MB/s 算:
1. **USB 2.0**: MT7921 USB 封装每个 1448 B 的 TCP 段占 1596 B(效率 0.907) ⇒ bulk IN 要 41.3 MB/s; 规范极限 53.2 MB/s, 最好的 USB2 实机约 40 MB/s; 不开聚合理论值只有约 300 ⇒ 零余量。
2. **DR1V90 单核**: 要 2.59 万包/s; 板上 recv 拷贝实测 14 ms/MB ⇒ 光拷贝占 52% 核 ⇒ 每包剩 18 µs, 现在 148 µs ⇒ 要快 8 倍。
DR1M90 双核只解决第 2 条, 第 1 条照样卡。

## 定的主线 (待 2a 纸面验证)
PC 有线 → 专用 AP → WiFi 单跳 → 转子上的前端 SoC(PCIe WiFi 网卡 + Linux 终结 TCP/PVS1) → **RGMII 1G 板对板 MAC 直连** → DR1 PL 只收 MAC + CRC + 帧头解析 → lz4 引擎。
RGMII 是 DR1 上唯一不需要 SERDES 的千兆接口(DR1 无 SERDES ⇒ SGMII/2.5G/USB3/PCIe 都进不了)。前端候选只列了类别(RK3568 / i.MX8M Plus + AX210), **没调研具体模组**。
阶段: 0 定口径+有线 AP 复测 / 1 驱动补丁保底(到不了 300) / 2 前端桌面 bring-up(转发 ≥330 持续 10 min)→ PL 收包核 → 接入 / 3 下游对账。

## 未决
- **300 服务什么内容没确认**: 现役切片流翻页上限 16 fps, 最重的 cyl2 @16fps 也只要约 94 Mbps ⇒ 300 大概对应终极目标的实时切片(266-837 Mbps)。
- **下游吃不下**: PL 三引擎实测约 147 MB/s 解压输出, 按 cyl2 的压缩比 10.8× 算入口只有约 110 Mbps ⇒ 链路到 300 后必须重算引擎数和 DDR 带宽。
- DR1 PL 有没有 IDELAY 未知 ⇒ 靠前端开 `rgmii-txid` 规避。

## 同日追问「200 能做到吗」(推算, 未实测)
200 Mbps = 25 MB/s ⇒ USB2 要 27.6 MB/s(规范的 52%, 实机最好值约 70%) **纸面不再是墙**; DR1V90 单核仍要每包快 **4-7×**(pov_rxd 按 14-25 ms/MB 算占 35-63% 核, 每包剩 22-38 µs, 现 148)。
🎯 **200 下多出一条 300 时不成立的路**: 前端 SoC 经网线/RGMII 接 DR1 **PS 千兆口 eth0, MTU 9000** ⇒ 只有 2.8 千包/s, 每包预算 134-233 µs(> 现 WiFi 路径全部开销 148) ⇒ **不用写 PL MAC**; 300 时同一笔账光拷贝就占 52-94% 核, 不成立。前提: **DR1 GEM/驱动支持巨帧(未查)**。
✅ **09-15 源码核查(另一窗口)**: DR1 网口不是 GEM, 是 **eqos0 = `snps,dwc-qos-ethernet-4.10`(stmmac, CONFIG_DWMAC_DWC_QOS_ETH=y), RGMII, rx/tx-fifo-depth 16384, snps,tso**; stmmac 在 DT 未给 `max-frame-size` 时 `plat->maxmtu = JUMBO_LEN = 9000`(stmmac_platform.c:471-474), GMAC4 的 `ndev->max_mtu = JUMBO_LEN`(stmmac_main.c:7274) ⇒ **软件上支持 MTU 9000**, 板上 `ip link set eth0 mtu 9000` 仍待实测。
🔧 **USB 封装开销用实测帧布局重算**: 每帧占 round_up(RXD0 len,8)+4(1400/1400 样本), 1448 B TCP 段约占 1540 B(×1.064, 不是 ×1.10) ⇒ 300 Mbps 需 USB 载荷约 39.9 MB/s、250 需约 33 MB/s; 结论不变(300 贴实机极限, 250 在 dwc2 软件调度的主机上也很勉强)。
🔧 **"DR1M90 只解决第 2 条"偏乐观**: 250 时单核每包预算只剩 10-26 µs(实测约 150), 要快 6-15×, 双 A35 也给不了; 另一窗口估算 DR1M90 在同一 USB 网卡上约 85-125 Mbps(推算)。
决定性实验(无新硬件): PC 2.5GbE 直连 DR1 eth0, MTU 1500/9000 各测, 接收端 ksink 额外 10 ms/MB; 发送端必须绕开 WSL2 NAT(否则巨帧被切回 1500)。并行: 加载 rx_agg+GRO 测 WiFi。顺序: 补丁过 200 ⇒ 结束 / 不过但 eth0 巨帧过 ⇒ 前端+以太网 / 都不过 ⇒ PL 直收。

**Why:** 用户定的目标; 此前的讨论全在驱动补丁上找空间, 但补丁的天花板远低于 300。
**How to apply:** 讨论 DR1 WiFi 提速到 300 时, 别再在 USB/驱动/换 DR1M90 上找答案; 驱动补丁(rx_agg/GRO)只作保底。替代路线是轴心光链路([[reference_wireless_link_alternatives]])。相关: [[project_dr1_hp_port_shortage]] [[project_lz4_pl_decoder]] [[project_pov3d_rotor_wireless_power]]


## 🎯 2026-09-18 回填: 今天的实测第一次把"前端 SoC + 以太网进 DR1"这条路的**两端都验证了**
本文 09-15 把这条路列为主线, 随后因用户约束("产品里 DR1 只能直接挂 WiFi 网卡, 不加前端模块、不加板间有线链路")**出局**。
但 09-18 在 DR1M90 上量到的数, 恰好补上了当时缺的两块证据(见 [[project_dr1m90_wifi_retest]]):
1. 🎯 **DR1 侧接收能力已证实**: 同一块板 **eth0 持续跑满 941 Mbit/s 线速**(20 s 无复位, 用 1.28/2 核);
   同速率对照 **158 Mbit/s 时有线只要 0.20 核, WiFi 要 1.34 核 ⇒ 6.7×**。
   ⇒ 本文 §57 "前端 SoC 经网线接 DR1 PS eth0 ⇒ 不用写 PL MAC" 那条路, **DR1 这一端不再是假设, 是实测**。
   (巨帧 MTU 9000 在 DR1V90 上 09-15 已实测被接受; DR1M90 未单独验。)
2. 🎯 **瓶颈归因已闭合**: WiFi 卡在 159 **不是 USB 主机**(U 盘实测 dwc2 能搬 **264 Mbit/s**)、
   不是空口(协商 1200.9)、也不是 SoC 通用能力(eth0 941) ⇒ **是 mt76+mac80211 的每包成本**
   (stock mt76-usb **不做 GRO**, 每个 802.11 帧单独走完整协议栈)。
⇒ **"换一颗 WiFi 解析能力强的芯片"这个说法要翻译准确**: 关键不是 CPU 更快, 而是**脱离 USB**
  —— 换成 PCIe 网卡或集成 WiFi MAC 的前端, 才能拿到有线那种 DMA 环 + 中断合并 + GRO 的代价曲线(≈6× 便宜)。
  单纯换更强的 CPU 只能压 p(每包成本)那一项, 而 A35 单核本来就弱于 A9。
🔴 **但这条路该不该走, 现在是需求问题不是技术问题**: 链路 159-210 已经比下游 **PL 解码入口 110 Mbit/s** 快 1.4-1.9 倍,
  比 24 芯片屏的规划载荷 32.5 Mbit/s 快 5-6 倍 ⇒ **换架构买来的容量目前没有消费者**。
  且用户那条"不加前端模块/不加板间链路"的产品约束若仍成立, 技术优劣不影响结论。


## 🎯 2026-09-18 用户澄清拓扑的两条硬约束 —— 这改变了"要不要拆 SoC/FPGA"的问法
用户原话:
1. **因为帧率要求, 当前只能用 LVDS 的 LED 驱动芯片**(即 ICND2260 走 mini-LVDS)
2. **LVDS 只能用 FPGA 来驱动, 因为确实有 73 路 LVDS 下行**
⇒ 🎯 **FPGA 是显示侧的硬需求, 不是链路侧的选择。** 架构问题因此**不是"要不要 FPGA"**, 而是 **"谁来喂 FPGA"**。
与既有记忆一致: 桥架构里 桥→屏 = **24 链×3 + 外扇时钟 = 73 対**(自出时钟则 96), 主控→桥 @1250Mbps 只要 18 対/面(双面 36),
FS03 引出 48 対够用([[project_pov3d_bridge_architecture]])。
🔴 **重要的连带事实: 桥片被选型成"哑桥"且无 DDR**(如 PH1A60GEG324 "无DDR无SERDES正好当哑桥") ⇒
  **帧缓冲(8.85 MB/帧)必须待在主控侧** ⇒ 即使把 WiFi 挪到前端 SoC, **也不能顺手把 DR1 省掉**,
  除非前端 SoC 自己带足够 DDR 带宽并承担 lz4 解码 + 组帧 + 翻页。
⇒ 拆分的真实代价 = 多一条**片间链路**; 而今天实测 **DR1 的 eth0 持续 941 Mbit/s**(1.28/2 核) ⇒
  1 GbE 对下游(PL 入口 110 Mbit/s)绰绰有余, **这条链路不是新瓶颈**。


## 🎯 2026-09-18/20 架构评估收口: 当前选择对当前范围是相对优的, 不建议现在换
用户排除**复旦微**(贵 + 供货风险)。讨论了两个替代拓扑, 结论如下。

**先厘清一个决定性的结构事实**: 压缩流 **~110 Mbit/s** vs 解码后 **40.15 Gbit/s**(每面 20.07×2) —— **差 365 倍**
⇒ "SoC 解码完再传给 FPGA" 不可能(40 Gbps 跨不了片) ⇒ **解码 + 帧缓冲 + 驱 36 対 LVDS 必须绑在同一颗芯片里**
⇒ 拆分点**只能在压缩流那一侧**。

| 方案 | 形态 | 判定 |
|---|---|---|
| **A: WiFi 芯片 + 纯 FPGA** | MT7981B/MT7986A(集成 WiFi MAC, 不走 USB) ──RGMII/GbE 110-300 Mbit/s──► FPGA(解码+帧缓冲+驱36対) ──► 桥×2 | 🎯 **唯一能改变 WiFi 成本曲线的方案**; 且 **FPGA 不需要 PS ⇒ 可以是纯 FPGA**, 记忆里"安路目录里『要 IO』=『变成纯 FPGA』没有中间选项"的死结自动解开, 器件面宽很多且更便宜。代价: **FPGA 要外挂 DDR**(帧缓冲 8.85 MB×3 ≈ 27 MB, 一整块新 PCB + 控制器 IP)、**lz4 解码要移植**、**两颗芯片的功耗** |
| **B: 换一颗更好的独立 SoC** | 要 80K+ LUT / 36 対 @1250M / DDR / WiFi 不走 USB | 🔴 **排除复旦微后没有明显更好的**: XC7Z020 **无 GTP ⇒ 与 DR1 在 WiFi 上同一档**; 再往上 7030(GTX+PCIe 硬核)/ZU+ 价格功耗都跳档 |

**为什么不建议现在换**(三条, 都有数):
1. 当前余量充足: 链路 159(余 33% CPU ⇒ ~210) vs PL 入口 **110** ⇒ 1.4-1.9×; vs 规划载荷 32.5 ⇒ 5-6×
2. 🎯 **天花板不在 WiFi**: 记忆原文 "**DR1 上限在 DDR/PL 不在 WiFi**, 直喂切片器读 DDR 随尺寸³增长, RGB565 下屏只能再大 ~1.10×, 更大屏要换 SoC/DDR"
   ⇒ **逼着换架构的会是"屏做多大", 不是"WiFi 多快"**
3. 桥架构本身被两条独立路径撞到同一结论(対数账 + 帧率天花板的出路(c)), 且 **DR1 1250Mbps 36対余1.33× vs 7020 950Mbps 46対余1.04×** 是"换 DR1"迄今第一个纯技术正当理由
**A 的触发条件**: 内容需求越过 ~200 Mbit/s。在那之前投两颗芯片+新 DDR 设计+解码移植, 收益为零。

**比选型更该先做的三件事(排序)**: ① **修 PL 解码器**(09-15 连推 37 帧卡死, 09-17 坐实根因是内核 ccm_dcache_op 开中断被软中断改 CSR —— **当前唯一真正挡路的**) ② **算功耗预算**(48W 总/屏 29W/电子约 19W, 无线供电没余地, 这个数**从没算过**) ③ **测转子旋转下的吞吐**([[project_rotor_spinning_wifi_throughput_gap]])。
