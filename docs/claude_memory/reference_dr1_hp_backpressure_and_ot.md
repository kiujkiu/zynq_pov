# HP 反压与仲裁: 厂商答复 + 我们 RTL 的实际承受力 (2026-08-27)

## 厂商明确的三条

1. 🔴 **没有最小带宽/最大延迟保证**。原话: "DDRC **没有**硬件机制直接保证某个端口的
   绝对最小带宽或绝对最大延迟"; "文档未给出反压信号拉低的**最大持续时间规格**"。
   只有**超时防饥饿** —— 那是**防饿死**, 不是**保时限**。
2. 🔴 **"DDRC 拥塞时读优先于写"确定不存在**。厂商: "不是简单固定读优先或写优先",
   并主动点名"读写方向切换、写队列批量排空、Bank/Row 冲突**仍可能导致读延迟尖峰**"。
   ⇒ Zynq 上 `pair_miss=0` 的归因里, "DDRC 读优先于写(AMD 明文)"这一半**在 DR1 上没了**。
3. ✅ 公共缓存内部**读缓存 / 写缓存 / OT 能力三者相互独立** ⇒
   **lz4 的写洪水吃不掉面板的读缓存条目**。

## 🎯 新旋钮: 带宽分配的货币是 OT, 不是时钟频率

厂商: "带宽分配取决于**仲裁权重、Outstanding(OT) 占用和 Burst 长度**,
而**不是接口时钟频率**"。按这把尺子量:

| | HP1 侧最大在途 | 相对面板(2 笔) |
|---|---|---|
| 方案 A (2 引擎 × MAX_OUTST_W=2) | **4 笔** | 1:2 劣势 |
| 方案 C (3 引擎) | **6 笔** | 1:3, **比 A 更不利** |

⇒ 🔴 **原来 A/C 的差别只被描述成"两个参数 + Fmax 收敛风险", 现在多了一条
   与性能相关的方向性判据, 而且对 C 不利。**
⚠ 反向的一面: A 的 lz4 在 100 MHz 发 AW 的**速率**是 C 的两倍;
   **深度与速率哪个主导, 厂商没说。**

✅ 好消息: 面板侧 `MAX_OUTST` 是 **3 位计数器(上限 7), 现在只用 2**
(`rtl/axi4_to_axi3_hp.v:47/101`) ⇒ **提它只改一个参数, 不动 RTL 宽度**。
而 `axi_hp_arb` 的 `w_can/r_can` 是**逐主判据、没有全局上限**(`:229/:323`)。
🔴 但注意 UG1214 `:3523`: **HP 口 outstanding 硬上限是 8 读 / 8 写** —— 加引擎时要一起算。

## 🔴 `ddr_slice_fetch256` 能扛反压, 但扛不住"久", 而且失效方式最坏

- **能扛**: `m_axi_rready` 在 F_R 恒为 1(`pov_dual_top.v:790`), 从不反压上游,
  反压只被转换成时间; 天然吃得下稀疏 rvalid(每拍最多写一个 fb 字)。
- 🔴 **扛不住久**: 模块内**没有任何 deadline / watchdog / abort**。
  `err_cnt` 只数 RRESP 错误、不中止(`:831-832`)。
- 🔴 **fb 是单缓冲**(`:543-545`, pov_en 时取帧引擎独占写口, 无 per-face 双缓冲)
  ⇒ 取帧引擎直接写面板正在读的那块
  ⇒ **失效表现是「撕裂 / 显示在错误角度」, 不是报错、不是挂死**。
- 🔴 **永久反压**(HP1 配错 / PS 侧寄存器没写导致静默不应答)⇒ FSM 永远停在 F_AR 或 F_R,
  **只有 PL 复位能救**。

⇒ 这正好解释了为什么"PS 侧那几个寄存器没写"特别危险: **它的症状不是报错, 是画面撕裂。**

## ⚠ 观测缺口: 反压我们一个计数器都没有

- `axi_hp_arb` 的 `r_stall_cnt`/`w_stall_cnt` 只数 **"AR/AW 被自己的在途上限挡住"** 的拍数
  (`:157-158`), **不是 HP 口的反压**
- `axi4_to_axi3_hp` 里 grep `stall` **零命中**
- `measure/01_hpbw` 只数 beats/cycles(吞吐), **不做归因**

⇒ **上板出 `pair_miss` 时, 分不清是「HP 压 arready」「rvalid 稀疏」还是「我们自己的 OT 上限」。**
**上板前该补。**
🎯 顺带: UG1214 揭示 **XMON 自带 `A*RESPTIME_MAX` 响应时间寄存器**(0xF8440000),
那正好能从 PS 侧给出这个归因 —— 见 [[reference_dr1_ug1214_ps_facts]]。

## 🔴 未决: M2/M3 按地址还是按 master (手册与厂商答复直接冲突)

| | 说法 | 出处 |
|---|---|---|
| 厂商在线答复 | 路由**完全由地址决定**; 512MB 全在低 4G ⇒ **必然都走 M2、必然竞争**; **没有寄存器能改** | 知识库检索 |
| **UG1214 图 14-1** | **XPI0=APU/RPU · XPI1=NPU+others · XPI2=HP0 · XPI3=HP1**, **按 master 固定分配** | `:7275-7280` |

两者不可能同时对。**必须让厂商指出手册里描述"按地址决定 M2/M3"的具体章节。**
⚠ 我们两条 HP 通路的 33 位地址 **bit[32] 在 RTL 里是硬零**
(`axi_hp_arb.v:279/390`, `axi4_to_axi3_hp.v:66`), 就算想走高 4G 也没有物理内存。

厂商给的规避建议(若"按地址"成立): 把其中一路的数据**迁到 OCM**
(HP0/HP1 访问 OCM 走独立的 M0/M1 出口, 不竞争 DDR 公共缓存), 或在 PL Master 与 HP 之间
**加 AXI Data FIFO** 吸收突发。
🎯 OCM 是 **256 KB**, 而渲染那条路算出的"切片片上双缓冲"只要 **83 KB** ⇒ **装得下**。
