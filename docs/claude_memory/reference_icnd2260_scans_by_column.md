# 芯片是按列扫描的, 这决定了量具的方向 (2026-09-02)

## 证据

【实测】1/8000 s(125 µs)快门拍单颗 40x45:
**约 20 条细竖线, 每条贯穿色块全高(45 行), 横向铺满整块。**
同机位 1/2000 s(500 µs)则是**均匀一片**。

```
任意时刻: 点亮**一列**(该列 45 行同时亮) -> 扫到下一列
1/2000 (500 µs) -> 40 列全扫完 -> 均匀
1/8000 (125 µs) -> 只扫到约 20 列 -> 20 条贯穿全高的竖线
```
若是按**行**扫, 短曝光下该看到**横带**, 不是竖线。

## 🔴 后果: 竖条纹量具从设计上就是坏的

`dbg_pat_mode=7` 的帧相位条纹原本做成**竖**的(40 列切 N 条),
而芯片扫描也是竖的 ⇒ **两个结构在同一空间方向上, 原理上无法分离。**

这解释了当天所有判读混乱:
- 8 条的图案数出 11~15 条
- 1/8000 下"只该亮 1/4 面积"却横向铺满
- 同一配置两个快门算不出一致的帧率

**⇒ 相位必须按「行」分组(横带), 与列扫描正交才可分离。**

## ⚠ 横条纹的实现要绕开关键路径

两次实现都把时序推坏: 行计数器压在与 `mot_col` 同一条关键路径上
(WNS 从基线 -0.471 掉到 -0.740 / -0.934 / -1.105)。
失败路径起点是 `u_seq/pix_addr_reg[*]`, 经 12 位比较进这些计数器的**同步复位脚**。
**下次换个思路**: 让行号直接由 `icnd2260_seq` 提供(它本来就在数行), 或把相位判断整体后移一级流水,
不要在 top 里再数一遍。

## 量具本身是好的(已验证)

【实测】把发送帧率降到 20 fps, **亮带确实在一格一格地跳** ⇒ `mot_ph` 推进正常、
列分组正确。**所以问题只是方向, 不是逻辑。**
⚠ 注意: 亮带**每帧跳一格**, 所以跳格速度 = 发送帧率(不是帧率÷相位数)。
判据用**转一圈的周期** = 相位数 ÷ 发送帧率, 比数格子稳。
