# 供应商 mini-LVDS 抓包的解码方法 (2026-09-01)

样本: `2026-09-01_17-15-39.bin`, **564,845,680 字节 = 282,422,840 个样本**,
**裸数据, 每样本 2 字节小端 = 16 通道**(DSLogic U2Pro16 导出, 没有随附元数据 ⇒ 采样率未知)。

## 通道映射(实测判定)

| ch | 是什么 | 判据 |
|---|---|---|
| 0 / 1 | **一对差分 D0(P/N)**, ch0 = P 侧空闲为 0 | 99.98% 互补 |
| 2 | **转发时钟**, 半周期精确 16 样本(周期 32), 全片不停 | 1765 万次跳变 |
| 3 | **I_SYNC**, 每 3,333,315 样本跳一次 = 一帧, 全片 84 帧 | — |
| 4 / 5 | 每帧各 10 / 6 次跳变 | 未定 |
| 6~15 | 恒 0, 没接 | — |

## 解码配方

```python
import numpy as np
a=np.memmap(F,dtype='<u2',mode='r')
seg=np.asarray(a[E-2000:E+3_400_000]).astype(np.uint16)   # E = ch3 的某个跳变点
ck=(seg>>2)&1; e=np.flatnonzero(np.diff(ck))+1            # 每个时钟沿
sp=np.clip(e+8,0,len(seg)-1)                              # 沿后 8 样本 = 单元中央
u0=((seg[sp]>>0)&1).astype(np.uint8)                      # 每时钟沿一"格"
```
- **RSYNC** = 格串 `"1"*16 + "00001111"*5` (56 格, **一格 = 一个时钟沿**)
- **配置段**: 每 4 格一位, 取组内第 2 格
- **VHEAD / 视频段**: 每格一位
- **包边界**: 用 CRC 当判据自校验(配置包首位是 0, "跳过连续 0"会跳进包里去 —— 踩过)

## 从这份抓包实证到的(全部逐位命中)

1. **CHKSUM = CRC-16/CCITT-FALSE**: `t=(r>>15)&1^bit; r=(r<<1)&0xFFFF; if t: r^=0x1021`,
   初值 0xFFFF, 按线上序喂, CHKSUM 域也 MSB 先发。**20 个包 20 中。**
2. **RSYNC 占 56 个时钟沿**, 开头连续 1 = 16 个 ⇒ 见 [[feedback_rsync_is_56_edges_not_56_bits]]
3. **VHEAD[15:0] 是校验和不是拷贝**: 实测 `A5A5_0930_91C4`, 而 CRC(0x0930)=0x91C4
   ⇒ 手册 p.14(mLVDS) 对, p.12 那句"等于 VHEAD[31:16]"只适用于 TTL
4. **对方的配置节奏**: 每帧写 16 个寄存器, OFFSET 按 `60,70,80,90,A0,B0,C0,D0,E0,00,10,20,30,40,50`
   循环, 15 帧走完 0x00~0xED 全部 238 个 ⇒ **整张表可以完整还原**
5. ⚠ **这段抓包是另一块板**: `VHEAD[31:16]=0x0930` ⇒ 扫描行数 10 / 16bit / **级联 1 颗**。
   还原出的表与 `2260lvds.xlsx` **差 53/238 处**(含 `0x00/0x01/0x03/0x04/0x06/0x15/0x1a` 全部关键项),
   其中 **`0x1a[9]`: xlsx=1 而抓包=0** ⇒ 我们"`0x1a[9]` 是 mLVDS 使能"的推断存疑
   (`0x06[9]` 两边都是 1, 那一位站得住)。

**How to apply**: 以后再拿到抓包, 直接套上面的配方。**一段波形能同时验证 CRC、帧格、
寄存器表和帧结构, 比问十个问题都管用** —— 值得主动向供应商要。

## 2026-09-01 深挖: 一帧的完整段表 + 时钟标定

**采样率 = 1 GSa/s [推断]**: 文件本身没有绝对时间锚点。定它的唯一依据是数据手册
`tLVCP 6.00~50.00 ns`(1/tLVCP 20~170 MHz) —— 实测时钟周期 32.0009 样本, 要满足
tLVCP ≤ 50 ns 就得 f_s ≥ 640 MSa/s, 而 DSLogic U2Pro16 最高 1 GSa/s ⇒ 唯一解。

⇒ **供应商 mini-LVDS 时钟 = 31.25 MHz, I_SYNC = 300 Hz。**
   我们跑 20.833 MHz(CLK_DIV=48), **只比手册硬下限 20 MHz 高 4.2%**(tLVCP 48ns vs 上限 50ns),
   而手册对 LVDS 的**建议默认值是 50 MHz**。⇒ 建议 `CLK_DIV=32` (= 31.25 MHz, 与供应商逐 ppm 一致)。

### 一帧段表 (格 = 一个时钟沿; c0 = RSYNC 第一个 `1`; 84/84 帧一致)

| 段 | 起(格) | 长(格) | 编码 |
|---|---|---|---|
| 帧首 IDLE | I_SYNC 沿在 −136 | 128 (**恰好 64 clk**) | — |
| RSYNC 字段 | −8 | **64** | 4 格/位 (= 16bit `0x3D55`, 前 8 格是 0) |
| CMD/DEVICE/OFFSET/LENGTH | 56 | 96 | 4 格/位 |
| 寄存器数据 | 152 | 64×(LEN+1) | 4 格/位 |
| 配置 CHKSUM | 1176 | 64 | 4 格/位 |
| **IDLE** | 1240 | **192 (= 96 clk)** ← 手册只写"≥64" | — |
| VHEAD | 1432 | 48 | **1 格/位** |
| Video Data | 1480 | 6400 | **1 格/位** |
| **Video CHKSUM** | 7880 | **16** | **1 格/位** |
| 帧尾 IDLE | 7896 | 剩余 | — |
| **一帧** | | **208,326 格 / 104,163 clk** | 突发占空 **3.85%** |

⚠ **采样点要用"沿后 +4 样本"**。用格中点(+8)会有 51/84 帧把视频 CHECKSUM 读错 ——
发送端把每帧最后一格截短到 10~11 样本。

### 🔴 ch4 / ch5 不是 ACK

它们是**供应商控制卡自己的协议字段边界标记**: 每帧沿位置与上表逐格吻合(误差 0 格),
且 `LENGTH=13` 的那 6 帧里后 5 个沿**整体前移正好 128 格** —— 接收端不可能知道发送端写了几。
排除 ACK 的五条: 沿数太少(10/6 vs ACK 最少 112)、锁在转发时钟上(ACK 是自定时)、
相位领先 lane0、84 帧里 CMD 全是 `0b0101` 写指令(**读指令 0 次**)、ch6~15 全片恒 0(探针没接)。

⇒ **我们至今仍未见过这颗芯片的任何真实回传。** 这份波形对"ICND2260 会不会回 ACK"提供零信息。
   要拿到回包必须同时: 发 `CMD=0b1010` 读指令 + 探 ACK_O(B4) + 链路先通。
