2026-07-30 用户问"换安路 DR1V90M 的移植难度", 做了依赖盘点。**结论: RTL 很干净, 风险全在 PS 侧。**

## RTL 依赖 (在用约 1600 行: pov_dual_top + icnd2047_panel_core + row_drv_icnd1028 + ddr_slice_fetch)

| 依赖 | 数量 | 说明 |
|---|---|---|
| **ODDR 原语** | ~~14 处~~ → **4 处例化 / 12 实例** | ⚠ 唯一硬骨头; 2026-08-06 重数并已移植完, 见 [[project_dr1_rtl_port_step1]] |
| 其他原语 (BUFG/MMCM/RAMB/DSP48/XPM…) | **0** | BRAM 与时钟全是推断的 |
| Xilinx IP | 3 (processing_system7 / smartconnect / proc_sys_reset) | 看新平台形态 |

盘点方法: `grep -ohE "\b(ODDR|IDDR|BUFG|MMCME2|RAMB|XPM_[A-Z_]+|DSP48)[A-Z0-9_]*" vivado/hdl/*.v | sort | uniq -c`

**ODDR 为什么关键**: 那 14 处是双沿输出核心, DCLK 用 `SAME_EDGE` 把边沿推迟半拍(10ns)
落在数据眼图中点, 是 50 Mbps/lane 能成立的原因 (setup/hold 名义 10/10ns vs 芯片要求 5/5ns)。
换平台不是改个原语名 —— **不同厂商 DDR 输出原语的 clk→out 延迟/抖动/占空比失真都不同,
必须重做时序收敛并重测眼图**。

## PS 侧才是工作量大头

现依赖 Zynq-7020 **硬核 Cortex-A9 双核 + Linux 6.6**:
`pov_rxd`(C, TCP+zlib+写DDR) / `povmem.ko`(WC 映射) / mt7921u WiFi / systemd 三个服务 /
`/dev/mem` 访寄存器 / AXI HP 口共享 DDR。

移植难度**完全取决于新平台形态**:
- **硬核 ARM + 官方 Linux BSP** → 基本可平移, 主要是重编内核/改 devicetree/DDR 地址重规划
- **仅软核 (RISC-V)** → Linux 能跑但性能另说。当前解压一帧 64ms 是 A9@667MHz 的成绩,
  软核大概率跑不动 ⇒ **整个推流架构要重设计**
  ⚠ **2026-08-26 补**: DR1V90 是**硬核** RISC-V @800 MHz(不是软核), 实测整帧慢 A9 **2.15×**
  ([[project_dr1_riscv_verdict]])。"推流架构要重设计"这条判断**方向对了**, 而重设计的结果
  就是**把解码整个搬进 PL** —— 之后 CPU 快慢基本不再进入关键路径
  ([[project_dr1_pl_decode_removes_both_walls]])。
  ⇒ **通用教训: 软核/弱核平台的出路往往不是"选个更快的核", 而是把热点搬进 PL。**
- **纯 FPGA 无处理器** → 外挂 MCU 或控制逻辑全搬进 RTL, **是重做不是移植**

## 🔴 2026-08-26 追加的第 6 个维度: **PS 的 HP slave 口数量**

本文原来的清单**漏了这一条**, 而它在 DR1 移植里升级成了头号问题。

写这篇时(2026-07-30)现设计只用 **1 个 HP**, 所以口数看着无关紧要 ——
本文只在 [[reference_anlogic_dr1_fs03_eval]] §3 顺带记了句"Zynq 有 4 个, DR1 只有 2 个,
以后 4×IP 并行要留意"。**2026-08-25 那个"以后"到了**: Zynq 上 PL lz4 三引擎落地,
HP0 = 面板纯读, HP1/HP2/HP3 = 三个引擎**各独占一口** ⇒ **4 个口全满**。
DR1 只有 2 个 ⇒ 三个引擎的读+写要挤进面板剩下的那一个。
详见 [[project_dr1_hp_port_shortage]]。

**教训: "现设计只用 N 个"不等于"移植只需要 N 个"** —— 要按**目标架构**的用量盘,
不是按写文档当天的用量盘。同理还要问:
- **N:1 AXI 汇聚 / 位宽转换有没有现成 IP?** Vivado 白给 `smartconnect` /
  `axi_protocol_converter`, **安路 TD 没有对等物**(未查证有无替代), 要手写。
- **DDRC 入口拓扑和读写仲裁策略是什么?** Zynq 侧"HP1/HP2 共享一个 DDR 入口"
  和"拥塞时读优先于写"这两条是 AMD 文档写明并被上板实测印证的,
  正是面板没被解码器饿死的原因; 换厂商这两条都要重新查。

## 换平台前必须先问清楚

1. 有无硬核处理器? 架构/核数/主频  2. 有无官方 Linux BSP + 内核版本
3. DDR 控制器硬核还是软 IP, 位宽带宽  4. 双沿输出原语叫什么 + datasheet 时序
5. **换的动因是什么?**
6. **PS↔DDR 的高带宽从口有几个 + 有没有现成的 N:1 汇聚 IP** (2026-08-26 新增, 见上)

🔴 第 5 条最重要: 若是供货/成本 → 移植是必须的; **若是性能不够 → 先确认新平台真能解决**。
~~按当前实测, 瓶颈是 **推流逐帧 ACK**(软件) 和 **转速与刷新率不匹配**(机械+配置)~~

⚠ **2026-08-26: 这两个具体的瓶颈都已经在 Zynq 侧解掉了**(逐帧 ACK → 08-06 修
`SO_RCVBUF` 后 `rx==flip`; 刷新率 → 08-20 翻 bit29 + R0x28 直读结案),
现役瓶颈换成了**翻页相位**。**但那句话的道理原封不动地成立且被再次证实**:
这三个瓶颈没有一个是换 FPGA 能解决的。**换安路的正当理由仍然只有供货/成本/国产化。**
