2026-08-04 用户提出两个亮度需求, 逼出了一次拓扑核查。**结论推翻了我自己前一轮的方案。**

## 🔴 硬件做不到"按半径调亮度" (两个独立原因)

### 原因一: 一个扫描行同时点亮 3 个不同半径
屏是 **3 区并行扫描** (`pack_obs.STRIPS = [(0,53,6),(53,53,3),(106,54,0)]`,
9 lane = 3 区 × 3 色)。行索引 r 同时从三个区各选一个 X:

| 扫描行 | 点亮的 X | 对应半径 \|u\| (px) |
|---|---|---|
| r=0 | 52 / 105 / 159 | **27.5 / 25.5 / 79.5** |
| r=26 | 26 / 79 / 133 | **53.5 / 0.5 / 53.5** |
| r=52 | 0 / 53 / 107 | **79.5 / 26.5 / 27.5** |

区0 半径 = 27.5+r (递增), 区2 = 79.5−r (递减) —— **趋势相反**, 一个 OE 值不可能
同时补偿。r=26 那行更极端: 轴心 0.5px 与外圈 53.5px 共享同一亮度。

### 原因二: 整屏只有一个 OE
`led_panel_chain.md`: **连接器侧只有一组 DCLK/LAT/GCLK(OE)**, 屏内 245 扇出到
**108 颗 ICND2049 同拍**。连"按区分别给 OE"都做不到。

### ⇒ 三种硬件手段全部出局
| 手段 | 粒度 | 能否做径向 |
|---|---|---|
| `oe_window`(0x0C[15:8]) / `oe_window_b`(0x20) | **整屏**(A/B 可不同) | ❌ |
| 逐行 OE 表 (要改 RTL) | 一行 = 3 个不同半径 | ❌ **拓扑决定, 改 RTL 也没用** |
| ICND2049 逐通道增益 | 按**高度**(180 通道) | ❌ 方向不对 |

⚠ **我 2026-08-04 一度给出"RTL 加逐行 OE 表 = 无损方案, 1-2 小时"的建议, 是错的。**
下次再想到这条路, 先看上面那张表。

## ✅ 可行的唯一路径: 数据域抖动密度 (`--radial-comp`, 已实现)

1-bit 内容的"亮度"= 点亮密度。在 `render_slice` 出 float 图后**逐列乘增益**再进
`to_1bit`, 增益低的列点亮像素变少 ⇒ POV 积分后看着暗。**逐像素粒度, 绕开扫描拓扑。**

### 补偿的两个物理效应
① **径向 1/r**: 半径 r 处每转扫过周长 2πr, 光摊到更大面积 ⇒ 强度 ∝ 1/r, 轴心过亮。
   增益 ∝ r。
   🔴 **偏移面上屏第 u 列的真实半径是 √(u²+axis_off²) 而非 |u|** —— 穿心面
   (axis_off=0) 才退化成 r=|u|。面B 照搬 |u| 会把整条曲线搞歪。
② **双面覆盖阶跃**: 面A 穿心覆盖 r≥0, 面B 覆盖 r≥13.4mm ⇒ r<13.4 只被面A 照到
   (1×), 外面两面都照(2×)。**只补穿心面的内圈** —— 面B 全部像素都在双覆盖区
   (它最小半径就是 off), 再加倍就错了。

实测增益: 面A `0.120..1.000`(含 2× 补偿, 边界阶跃 1.74×), 面B `0.177..1.000`。

### 实现时踩的坑
- **归一化顺序**: 先 clip 到 floor 再叠加 2× → 阶跃被地板吃掉(轴心仍 0.120, 等于没补)。
  必须**先叠加再归一化**。
- **floor 不能省**: 纯 ∝r 让 r→0 处全黑, 轴心会消失。默认 0.12, `--radial-floor` 可调。
- **对照基准要选对**: 我一度拿新渲的帧比几小时前的 `frames_*` 目录, 判定"默认路径
  被改坏", 实际那期间 `gen_anime_slices.py` 已改过。**合法对照 = 同一输入 × git stash
  切回改动前的代码**, 那样验证是逐字节相同的。

### 固有代价
**暗列损失空间细节** —— 像素是被抖掉的, 不是变暗的。这是 **1-bit 内容的固有限制**。
要"变暗而不丢像素"只有 **BCM 多 bit-plane**(同一片分子帧, OE 时长 1:2:4:8 加权;
ICND2049 有内置双缓存对 BCM 友好), 但那是引擎级重做 + 数据量 ×plane 数 + 刷新率重算。

⚠ 径向补偿在 POV 显示上可能触及 **Voxon P3 专利**(`gen_anime_slices.py` 文件头原有
红线)。用户 2026-08-04 明确"先不管, 先看效果", **产品化前必须回头处理**。

## 用法
```bash
povstream.py render --anim glbanim --glb X.glb --frames N \
        --dual-face --radial-comp [--radial-floor 0.12]
```
默认关闭, 不给 `--radial-comp` 时逐字节等价旧行为。

⚠ **补偿效果只在旋转时存在** —— 轴心过亮和覆盖阶跃都是旋转积分的产物, 静止时
一个都不存在, 静态看片子判断不了。

## ✅ 2026-08-04 实测验证通过 (663 RPM, locked=1)

用户在真机上确认三条, **v3.1 偏心路线端到端成立**:

| 验证项 | 结果 |
|---|---|
| **中心盲柱** | ✅ **消了** —— 贴轴那面轴心是实的。这是 v3.1 偏心改造的唯一目的, **目的达成** |
| **径向补偿 `--radial-comp`** | ✅ **有用** —— 数据域抖动密度法确实改善了亮度不均。🔴 **但有 FTO 缺口**: 它命中 Voxon P3 的空间抖动(6-8)/亮度占空比(9-13)两组从属权, 而 FTO 备忘的方案A 不覆盖它 ⇒ 见 [[reference_fto_radial_comp_gap]]。**默认关闭, 别进出厂预设** |
| **`oe=111`** | ✅ **不会太暗** —— 663RPM 下每片可扫 0.84 遍(vs oe=187 的 0.58), 完整度换亮度这笔买卖划算 |

⇒ **抖动密度法是可用方案, 不是权宜之计。** 之前担心的"暗列丢细节"在实际观感上可接受。
⇒ `oe=111` 的固化决策得到实物背书, 不用回退。

⚠ **但这也让专利问题从"理论"变成"现实"** —— 径向补偿既然确实有效且会用在产品里,
Voxon P3 那条红线**必须在产品化前处理**, 不能再拖。
