# 供应商寄存器表 (2260lvds.xlsx) 与我们自推版本的差异

**2026-08-26 收到**。供应商(映己鸿鹄)提供的 `2260lvds.xlsx`，两列 238 行
(`reg_num` 十进制 0~237 / `reg_data` `0xNNNN`)，是他们**实际点亮这块 40×45 样板**
用的 mini-LVDS 配置。

导入脚本: `tools/import_vendor_regs.py` → `rtl/icnd2260_regs_vendor.mem`
顶层默认已切过去 (`icnd2260_lxb_lvds_top.v` 参数 `REG_MEM`)。

---

## 1. 它证实了什么

我们此前有 5 条无法验证的推断，这份表直接结掉两条半：

| 推断 | 结论 |
|---|---|
| **0x06[9]=1 是 mini-LVDS 使能** | ✅ 供应商 `0x06=0xaa44`，bit9=1 |
| **0x1a[9]=1 是 mini-LVDS 使能** | ✅ 供应商 `0x1a=0x0a48`，bit9=1，**与我们的 LVDS 版一模一样** |
| **0xb4[5:4]=10 是 3 通道** | ✅ 供应商 `0xb4=0x3020`，[5:4]=10 ⇒ **三对差分都要发数据** |

⇒ 我们对 §3「传输模式」表的理解是对的。**"寄存器配错了所以不亮"这条假设可以划掉。**

⚠ 反过来说：既然配置逻辑没错，那不亮的原因就更集中在**物理层**或**时序**上了。

## 2. 它推翻了什么

`REG_COUNT` 我们取 238，供应商也正好 238 (0x00~0xED) —— 长度对得上，
**"我们多写了寄存器把芯片写崩"这条也划掉**。

## 3. 我们推不出来的 48 处

### 3.1 三个颜色通道块 (0x20/0x30/0x40)，27 处

这三块结构完全相同，是 R/G/B 各一份。差异分两类：

| 偏移 | 三块是否一致 | 我们 → 供应商 | 判断 |
|---|---|---|---|
| `+0` | 一致 | `6020`→`6010` | 全局参数，与颜色无关 |
| `+2` | 一致 | `0006`→`0007` | 同上 |
| `+3` | 近似 | `0100`→`0200`/`0200`/`0300` | **每色递增**，像通道序号/相位 |
| `+4` | 一致 | `01cf`→`028f` | 同上 |
| `+b` | 一致 | `011f`→`0100` | 同上 |
| `+9` `+a` `+c` `+d` | **三块各不相同** | 见下 | **每色独立标定** |

```
        +9              +a              +c              +d
0x20  01d5->01cb     0806->0009     000d->0045     2218->2215
0x30  01d5->01d6     0b0b->080a     0019->0013     221f->2216
0x40  01d5->019b     0e0d->0b0a     001d->0017     2219->2215
```

`+9`/`+a`/`+c`/`+d` 三块取值互不相同 ⇒ 这是**与这块板上实际 LED 芯片的
正向压降/效率绑定的标定值**。手册 §11 给的是通用默认值，
**这类参数不可能从手册推出来** —— 必须由板子的实测数据决定。

### 3.2 全局寄存器，21 处

```
0x00: 3f3c -> 493c     0x02: 0c00 -> 0800     0x03: 003c -> 0034
0x04: 2d2d -> 2d00     0x06: d288 -> aa44     0x08: 5105 -> 5104
0x18: 0034 -> 002e     0x19: 0508 -> 0506     0x1d: 0000 -> 004c
0x50: 0a00 -> 0000     0x51: 0c00 -> 0000     0x59: 1404 -> 1424
0x6c: 004d -> 005b     0x6d: 004d -> 005b     0x7a: 000b -> 0002
0x7c: 0054 -> 0051     0x7d: 0054 -> 0051     0x8a: 0000 -> 0508
0x99: 22ac -> 22b1     0xb0: 0070 -> 0060     0xb4: 3028 -> 3020
```

`0x06` 一个寄存器就差了 8 位 (`XOR=0x78cc`)，远不止 LVDS 使能那一位。

## 4. ⚠ 这份配置的帧率只有 704 fps

```
0x00 = 0x493c → [14:8]=0x49=73 ⇒ 灰度分组数 = 74     (我们原来 64)
                [5:4]=11       ⇒ N = 8
0x01 = 0x0020 → Width_X = 32
G = 74 × 32 × 8 = 18,944
帧频 ≤ 600MHz / (18,944 × 45) = 704 fps
```

**离本项目 9,000 fps 的目标差一个数量级。**

这不是问题——供应商这份是为**常规显示**调的，不是为 POV。先用它把板点亮，
点亮之后再按 `docs/04_fps_sweep.md` 的办法压 `0x00`/`0x01` 换帧率
(灰度和帧率直接对换，`G` 减半帧率翻倍)。

⚠ 但要注意：**降 `G` 会不会连带影响那些每色标定值 (`+9/+a/+c/+d`)，我们不知道。**
真要往上压帧率时，这是个需要问供应商的点。

---

## 5. 还没解决的

这份表**没有**回答的问题（原 5 条推断里剩下的）：

1. 配置/VHEAD 是否走 B 对 (D0) —— 表里没有通道映射信息
2. RSYNC/配置段是否 4 沿/位
3. 转发时钟相位 (90°)
4. CHKSUM 的多项式/位序

⇒ **上一轮列的问题清单里，Q1(要一段波形) 仍然是最有价值的那条**，
因为剩下这 4 条全部要靠波形才能验证。Q5(通道映射) 也还没答。

## 6. 怎么用

```bash
python3 tools/import_vendor_regs.py            # 重新导入(脚本带自校验)
bash tools/run_sim.sh                          # 回归
# 出 bit (顶层默认已用 vendor 表)
vivado -mode batch -source tools/build_bit_dbg.tcl -tclargs 48 lvds
```

要切回自推的对照版做单变量对比：

```tcl
synth_design ... -generic REG_MEM="icnd2260_regs_lvds.mem"
```
