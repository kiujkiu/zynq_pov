# scatter — 体素表 → 体素网格 (ICND2260 目标架构的 scatter 环节)

```
PC 采样+体素化 →[VXT1 体素表]→ WiFi(PVS1) → ARM: **scatter 进网格** → 体素网格(DDR)
    → pov_slice_v2 切片 → 切片(DDR) → PL 出口 → mini-LVDS → 48× ICND2260
                          ↑ 已完成并验证, 本目录只读它不改它
```

本目录 = 上面加粗那一环, 外加它的发送端编码器和一套离线验证台。
**全部离线 (x86 + gcc), 不碰板子。**

| 文件 | 是什么 |
|---|---|
| `vox_table.h` | 🔴 **线上格式 VXT1 的权威定义** + 板端 scatter 接口 (含全部设计理由) |

| `gen_voxtab.py` | PC 侧: 点云 → 体素化 → VXT1 表 (+ 黄金网格 + 编码对比表) |

## 1. 线上格式 VXT1

细节在 `vox_table.h`, 这里只讲**为什么**。

```
PVS1 头 (16 B, 不变) : flags |= PVS_FLAG_VOXTAB(1<<8), n_slices=0,
                       raw_len = VXT1 体长, comp_len = 线上长
VXT1 体              : [24 B 头][颜色平面 n×u16 RGB565][索引平面 varint(delta-1)]
```

**与 PVS1 正交, 不是新协议。** 压缩位 (LZ4/ZLIB/MSTREAM) 语义一个字都不改 ——
它们说"载荷怎么解压", VOXTAB 说"解压出来的怎么解释"。接收端只在解压之后多一个
分支。`DELTA`/`DUAL_FACE`/`FOLD_A` 与 VOXTAB 组合非法 (理由见头文件), 必须 NAK。

### 三个设计决定, 每个都有实测支撑

**① 索引升序 + delta + LEB128 varint。**
排序在 PC 侧免费 (`np.nonzero` 天然升序), 换来三件事: 索引可编成小整数、
板端写网格地址单调递增、上一帧脏格表也是升序所以清理能和写入归并成一趟。
白拿的好处: 解出的索引**必然严格递增**, 板端只需检查最后一个 < 网格格数,
一次比较完成全部边界校验。实测索引 **1.02–1.11 B/格** (原始 4 B)。

**② 颜色平面与索引平面分开放, 不交错。** 这条不是"顺手", 是**决定 lz4 能不能用**:

| 内容 | 交错 6 B 记录 | 分平面 |
|---|---|---|
| globe 129K | zlib 3.31× / **lz4 1.48×** | zlib 32.3× / **lz4 30.7×** |
| globe 215K | zlib 3.18× / **lz4 1.48×** | zlib 8.28× / **lz4 7.06×** |
| anime 20K | zlib 1.60× / **lz4 1.04×** | zlib 2.67× / **lz4 2.31×** |

交错布局下 **lz4 几乎压不动** (1.0–1.5×), 而板端选的就是 lz4 (A9 实测解压
204.6 MB/s, 是 zlib 的 4 倍, 见 `protocol.h` 的 `PVS_FLAG_LZ4`)。
分平面后 lz4 追平 zlib 到 3% 以内 ⇒ **分平面是"用得上快解码器"的前提**。

**③ 颜色平面放在索引平面前面。** 头 24 B 是偶数 ⇒ 颜色平面天然 2 字节对齐,
板端可以直接 `uint16_t*`。反过来放, `idx_bytes` 变长会把颜色平面推到奇地址上,
A9 未对齐 u16 访问要么慢要么直接 abort。

### 实测压缩比 (192×192×216 网格, lz4-HC12 = 板端真正用的)

| 载荷 | 占据格 | VXT1 体 | 线上 (lz4) | B/格 | 压缩比 | @15 fps |
|---|---|---|---|---|---|---|
| anime 真实点云 | 19,936 | 61,831 | 51,728 | 2.59 | **2.31×** | 6.2 Mbps |
| globe 真实点云 | 128,944 | 399,731 | 25,199 | 0.20 | 30.7× | 3.0 Mbps |
| globe 合成加密 | 214,994 | 665,324 | 182,789 | 0.85 | 7.06× | 21.9 Mbps |

PC 编码耗时 (x86, VXT1 编码 + 压缩): 0.5+2.3 / 2.4+4.0 / 20.3+27.8 ms —— 都远小于
66.7 ms 的内容帧周期。⚠ 但**体素化本身** (numpy `add.at`) 要 ~1 s/帧, 现渲直推做不到,
和现有 lz4-HC 预压缩一样要离线预生成。

🔴 **压缩比强烈依赖内容, 2.3×–30× 都能测到。** 目标 "≥2.5×" 在 anime 上用 lz4
只到 **2.31×** (zlib 2.67× 达标)。说 "2.36 B/格" 那条对应表里的
"交错 + 整体 zlib", 分平面之后这个数字已经不再是基准。

## 2. scatter 放哪: **ARM**

### 实现要点 (这才是省钱的地方, 不是"选 ARM 还是 PL")

清理和写入**归并成一趟单调递增的扫描**:

```
prev 独有 → grid[i] = 0        (清)
两边都有 → grid[i] = color     (覆写即清理, 一次写干两件事)
cur  独有 → grid[i] = color    (写)
```

实测 (2°/帧 旋转, 相邻内容帧):

| 载荷 | 覆写(省掉的清理) | 真正要清 | 新增 |
|---|---|---|---|
| globe 215K | 85,284 (40%) | 129,710 | 129,514 |
| 1bit 191K | 107,397 (56%) | 84,089 | 83,972 |
| anime 20K | 1,567 (8%) | 18,369 | 18,369 |

### 🔴 "别整块 memset" 是对的, 但便宜的倍数不是 265×, 是 **6.5–64×**

会话里的 265× 是拿 "60 KB 写" 比 "15.9 MB 写" 算的 —— 忽略了**散写的粒度是
cache 行不是字节**。一次 2 B 散写在 A9 (行 32 B, 写分配) 上是 32 B 读 + 32 B 回写。
实测摸到的行数 (与机器无关的口径):

| 载荷 | 摸到 32 B 行 | 格/行 | 增量 DDR/帧 | 整清 DDR/帧 | 省 |
|---|---|---|---|---|---|
| globe 215K | 72,691 | 2.96 | **4.44 MB** | 34.8 MB | **7.8×** |
| globe 129K | 32,268 | 4.00 | 1.97 MB | 32.3 MB | 16.4× |
| anime 20K | 7,917 | 2.52 | 0.48 MB | 30.9 MB | 63.9× |
| 1bit 191K | 52,031 | 3.68 | 3.18 MB | 20.6 MB | 6.5× |

"2.96–4.00 格/行" 是升序扫描白赚的 —— 表面沿 y (最内维) 成段, 同一条行里常有
好几个占据格。随机顺序散写会退化到 1 格/行, DDR 流量翻 3–4 倍。

### ⚠ x86 墙钟在这里会骗人

本机 `memset` 有 20–26 GB/s, 整清 15.2 MB 只要 0.7 ms —— 于是"增量清理"在
x86 上看起来**毫无优势甚至更慢** (1.74 ms vs 1.14 ms)。而 Zynq-7020 的 A9 实测
memcpy 只有 ~442 MB/s (`pov_rxd` 的 cpy 20 ms / 8.85 MB), 差 **30–50 倍**。
⇒ 跨平台唯一可比的量是上面那张 DDR 流量表, 不是 x86 时间。

### 量化对比 (215K 格 / 内容帧 66.7 ms)

| | ARM (A9 666 MHz) | PL (HLS IP) |
|---|---|---|
| varint 解码 | ~2.0 ms (估) | 同样要做, 在 PL 里做也是一样的字节数 |
| 网格散写 | 4.44 MB DDR ÷ 442 MB/s = **10 ms**, 按访问模式差再打 1.5–2 折 ⇒ **10–20 ms** | 单拍 2 B 写不吃 cache, 但 DDR 仍按 BL8=32 B 成交 ⇒ 若不自己合并反而 **6.9 MB**, 比 ARM 还多 |
| 额外代价 | 定向 cache 维护 ~1–2 ms (估) | 占 1 个 HP 端口 + BD 资源 + 一致性设计 |
| **合计** | **12–22 ms (估)** = 预算的 18–33% | 更快, 但省下的是**已经有 3× 余量的一级** |

**选 ARM。三条依据**:

1. **12–22 ms / 66.7 ms ⇒ 余量 3.0–5.6×**, 已经超过 2× 目标。优化一个有 3× 余量
   的级没有收益。
2. **PL 端口是更稀缺的资源**: Zynq-7020 只有 4 个 HP。切片器要 2 个 (体素读 /
   切片写), 面板出口要 1 个, 只剩 1 个。把它花在一个已经够快的级上是坏交易。
3. **目标架构里 ARM 反而变闲了**: 现平台 ARM 每帧要 memcpy 20 ms 的切片;
   目标架构切片由 PL 从体素网格直接产出, ARM 的活只剩 TCP 收 + lz4 解压
   (3.3 ms) + scatter。

🔴 **对"12% 单核"那个粗算的核对: 偏乐观约 2–3 倍。** 差在同一个地方 ——
按字节数算 (150K×2 B = 300 KB) 而不是按 cache 行算 (4.44 MB)。真实值 18–33%。

### 🔴 一致性: 网格是 ARM 写、PL 读, 必须处理 (**未上板验证**)

grid 若走 cacheable, 切片器 IP 读到的可能是 stale。两个选项:

* **推荐**: 保持 cacheable, **用索引表做定向 flush** —— 我们恰好知道摸了哪 72,691
  条行, 按连续段 `Xil_DCacheFlushRange` 即可, 不必 flush 15.9 MB。可以直接融进
  归并循环 (扫过一条行就 flush 一条)。估 ~1–2 ms。
  这也与 [[feedback_fb_full_memset_cache_stale]] 的教训一致: **大块 memset+flush
  会和并发 PL 读打架出 stale 字节, 要细粒度**。
* 不推荐: 把 grid 整块设成 non-cacheable —— 散写就吃不到"2.96 格/行"的合并,
  DDR 流量退回 ~3–4 倍。

## 4. 余量表 (900 RPM / 体帧 30 Hz / 内容 15 fps / 周期 66.7 ms)

负载 = **215K 占据格** (13–22 万带的上沿), 目标网格 192×192×216。

| 级 | 需求 | 能力 | 余量 | |
|---|---|---|---|---|
| PC 体素化 | 66.7 ms | ~1 s/帧 (numpy) | 0.07× | ❌ 必须离线预生成 |
| PC VXT1 编码 + lz4 | 66.7 ms | 20 + 28 ms | 1.4× | ⚠ 预生成后无所谓 |
| **链路** | 21.9 Mbps | 125 Mbps | **5.7×** | ✅ |
| 板端 lz4 解压 (665 KB) | 3.3 ms | 66.7 ms | 20× | ✅ 按 204.6 MB/s 实测 |
| **ARM scatter + 清理** | **12–22 ms (估)** | 66.7 ms | **3.0–5.6×** | ✅ |
| ARM 定向 cache flush | 1–2 ms (估) | | | ⚠ 未上板 |
| **ARM 本级合计** | **16–27 ms (估)** | 66.7 ms | **2.5–4.2×** | ✅ 达标 |
| 网格 DDR 写带宽 | 4.44 MB × 15 = 67 MB/s | ~1 GB/s | ~15× | ✅ |

**⇒ 本级余量 2.5–4.2×, 达到 ≥2× 目标。** (⚠ A9 时间全是外推, 见下面"没做到的")

悲观组合 (anime 的颜色熵 × 215K 格 = 2.59 B/格 × 215K = 557 KB/帧):
链路 66.8 Mbps ⇒ 余量掉到 **1.87×**, 解压 8.7 ms ⇒ 7.7×。scatter 一级不受影响
(与线上大小无关)。

内容帧率若从 15 提到 30 fps (周期 33.3 ms): ARM 合计余量掉到 **1.2–2.1×** ——
贴边。但按 [[project_pov3d_link_budget_status]] 的口径, 900 RPM 下内容帧率上限
本来就是 15 fps, 所以这一档不用考虑。

## 5. 🔴 没做到 / 不确定 / 前提被推翻的

**(a) 所有 A9 时间都是外推, 一次都没上板** (另一个 agent 独占硬件)。
外推用了两个板上实测常数: `memcpy 442 MB/s`、`lz4 解压 204.6 MB/s`;
varint 解码按指令数估 (~6 cycle/值 × 215K ÷ 666 MHz ≈ 2 ms), 与 x86 时间 ×8 吻合。
**散写的实际 DDR 效率是最大的不确定项** —— 我按 memcpy 带宽再打 1.5–2 折,
真实值可能更差 (L2 预取对带洞的升序流不友好)。**这一项必须上板复测。**

**(b) "满屏模型 13–22 万占据体素" 的外推是错的。**
`占据体素数 ≤ 采样点数`, 而手上两个 `.bin` 只有 100,000 / 128,944 个点。
实测 (缩放到填满 192 网格): anime **19,936** 格 (与会话记录的 19,939 吻合),
globe **128,944** 格。会话里"按表面积 ∝ 尺度² 外推 anime ×6.9 → 138K"不成立 ——
放大模型不会凭空多出采样点。真要到 13–22 万必须**从 GLB 采 1.8M 点**,
而本机**没有 pygltflib**, 拿不到 GLB。
⇒ 22 万那一档是我用 `--jitter` 合成加密出来的 (globe ×2, σ=0.35 体素),
**几何是真的球面, 但密度是合成的**。请把它当负载模型, 不要当内容质量结论。

**(c) "PC 用 ssaa=3 覆盖率抗锯齿" 这个前提, 在生产默认路径上不成立。**
`gen_anime_slices.py` 的 `voxelize()` 调 `voxel_grid()` 时**没有传 ssaa**,
默认 1; `povstream.py --ssaa` 默认也是 **1**。所以现在跑的就是 ssaa=1。
另外实测: 用 100K 点的 `.bin` 配 ssaa=3, 覆盖率均值只有 **0.11** ——
整个模型颜色被压到 11% 亮度, 大量体素量化后直接变 0 (占据格 19,936 → 17,827)。
**ssaa 与采样密度强耦合, 点云 .bin 喂 ssaa>1 是个坑。**
⚠ 这不影响 VXT1 格式 (颜色里装什么它都不管), 但影响"抗锯齿信息不丢"这个说法的前提。

**(d) 一致性 (cache flush) 只有设计没有实现**, 见第 2 节末。
定向 flush 的 1–2 ms 是估算, 且 A9 上 `Xil_DCacheFlushRange` 逐段调用的开销没量过。

**(e) PL 方案只做了纸面估算, 没写 HLS 也没综合。** 结论"选 ARM"依据的是
"ARM 已有 3× 余量 + HP 端口更稀缺", 不是"PL 更慢"。如果将来占据格数涨到
~50 万以上 (ARM 会到 30–50 ms), 或 ARM 还要兼别的重活, 这个结论要重算。

**(f) 没有测过丢帧/乱序的真实恢复流程。** `VXT_FLAG_KEY` + `vox_scatter_desync()`
的机制在单测里验过 (负面用例后强制整清), 但**没有和 povstream 的 ACK/NAK
重传逻辑接起来**。接收端何时该请求关键帧, 是下一步的事。

**(g) 未与 `povstream.py` / `pov_rxd.c` 集成。** 本目录只交付格式 + 板端内核 +
验证台。协议位 `PVS_FLAG_VOXTAB` 定义在 `vox_table.h` 里, **没有去改
`mlkpai_fs03/stream/protocol.h`** (跨仓库, 且那边正在被动)。合入时要把这一位
挪进 protocol.h 并同步 `protocol.md`。

## 6. 验证板口径 vb358 (2026-10-10, 任务 1.4.2)

口径 (用户 10-10 定): 160×180 / **358 片/圈** / 720 RPM / 24 Hz / 双面 (面A 0 mm, 面B 13.4 mm, 面B 相位 179) / RGB565 体素表。
主机侧 profile 在 `mlkpai_fs03/tools/pov_profile.py` (povstream `--profile vb358` 用同一份);
切片器加了编译配置 `-DPV2_CFG_VB358` + `hls_proj/pov_slice_v2_lut_358.h` (由补写的 `tools/gen_pv2_lut.py` 生成,
该脚本对 360/603 两张旧表逐字节复现)。

🔴 **PVS_FLAG_VOXTAB 从 bit 7 挪到 bit 8** —— bit 7 早被 3-bit 色深 (PVS_FLAG_3BIT) 占了。

```bash
make CFG=vb358 vb_slice_all                      # (+ vb_slice_all_a64: 同源码 aarch64 交叉编)
python3 vb358_e2e.py [--host-dir <povstream render --profile vb358 的目录>]   # 对拍, PASS/FAIL
python3 vb358_budget.py [--vxt-dir <同上>]       # 载荷 / WiFi / DR1M90 切片带宽表
```

`vb358_e2e.py` = 主机编码 → C scatter (跨帧增量) → C `pov_slice_v2` 358 × 2 面全角度, 对独立 float64 参考
(面B 按"背对背: 垂距取负 + 手性取反"物理推, 不走 phase=179)。2026-10-10 结果: **PASS** ——
几何探针最大误差 0.64 px (切比雪夫) / 0.85 px (欧氏), 全部落在 "0.5 + Q8 表误差上界" 内;
最近邻命中 92.4% / 91.5% (Q8 角度表所致, Q12 可到 99.5%); 内容 8 帧 C 输出与预测逐字节 0 不符;
与浮点参考差 2–5% 亮像素, 全部可由 Q8 舍入解释。
⚠ 切片器列中心是 u = px − 80, 而 povstream 2047 渲染 (gas) 用 u = px − 79.5 —— 半像素系统差, 待板端定。
